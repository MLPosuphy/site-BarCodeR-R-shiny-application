Datos de entrada — Guías metodológicas

1. Presentación general#

La pestaña Input data permite introducir en BarCodeR uno o varios objetos phyloseq ya construidos.

Acepta objetos R serializados en los formatos .rds, .RData, .rda y .rdata.

La aplicación determina automáticamente si el archivo contiene:

  1. un único dataset phyloseq;
  2. un proyecto con varios datasets phyloseq;
  3. varios objetos compatibles entre los que el usuario debe elegir;
  4. un objeto no reconocido, en cuyo caso se rechaza la importación.

Esta pestaña no reconstruye un objeto phyloseq a partir de tablas independientes. Carga objetos R ya serializados.

2. Lugar de Input data en BarCodeR#

Necesidad Pestaña
Cargar un phyloseq existente Input data
Cargar varios phyloseq de un proyecto .rds Input data
Recuperar un phyloseq producido en el clúster OpenMetaBar
Construir o completar un phyloseq con tablas separadas Data Edition
Renombrar, duplicar, eliminar o exportar un dataset Datasets
Importar un proyecto completo con figuras e historial Datasets
Restaurar la copia interna del proyecto actual Datasets

2.1. Operaciones que ya no se realizan aquí#

La versión actual ya no permite eliminar, renombrar, duplicar o exportar datasets ni gestionar proyectos nombrados directamente desde Input data. Estas funciones se centralizan en Datasets.

3. Interfaz actual#

La interfaz contiene una sola zona principal:

Cargar un archivo (.rds / .RData / .rda)

Incluye una explicación de la detección automática, un selector de archivo, una descripción de la limpieza aplicada y un recordatorio sobre la gestión en Datasets.

Ya no existen selectores separados para dataset/proyecto, selección manual de la orientación de la OTU table, transposición de metadata, corrección taxonómica ni zona de eliminación.

4. Límite de tamaño#

El archivo se carga mediante un fileInput de Shiny. El límite global actual es:

500 MB

Un archivo superior normalmente no puede transferirse por este campo.

4.1. Tamaño en disco y memoria#

Un .rds puede estar comprimido. El objeto descomprimido puede ocupar mucho más que el archivo en disco.

Hay que disponer de memoria suficiente para el objeto cargado, los datasets existentes y las copias temporales creadas durante la lectura y la limpieza.

4.2. Aplicación ejecutada en un servidor#

Cuando BarCodeR se ejecuta a distancia, el archivo se envía al servidor Shiny. El tiempo depende del tamaño, la red, la carga del servidor y la memoria disponible.

La lectura y la limpieza son síncronas; la interfaz puede parecer bloqueada temporalmente con objetos grandes.

5. Formatos aceptados#

5.1. .rds#

Un .rds contiene un solo objeto R. BarCodeR lo lee con readRDS() y determina su tipo.

El nombre propuesto deriva del nombre del archivo sin extensión:

metabarcoding_coi.rds
→ metabarcoding_coi

5.2. .RData o .rda#

Un .RData puede contener varios objetos. BarCodeR:

  1. lo carga en un entorno temporal aislado;
  2. inspecciona cada objeto;
  3. conserva solo datasets o proyectos reconocidos;
  4. selecciona automáticamente el único objeto compatible;
  5. solicita una elección cuando hay varios.

Los objetos incompatibles se ignoran.

5.3. Extensiones no compatibles#

Input data no importa directamente .csv, .tsv, .xlsx, .biom, .qza, .zip, .RDS.gz, FASTA, FASTQ ni Newick.

Las tablas independientes deben tratarse en Data Edition. Los proyectos completos .zip deben importarse en Datasets.

6. Detección automática del contenido#

La detección se basa en la estructura real del objeto, no solo en el nombre o la extensión.

6.1. Dataset único#

Se reconoce como dataset un objeto que hereda de la clase phyloseq.

6.2. Proyecto#

Se reconoce como proyecto:

  • una lista con un elemento datasets;
  • una estructura histórica con ps_registry;
  • una lista no vacía cuyos elementos son todos phyloseq.

6.3. Detección estructural#

No es obligatorio que exista un número de versión, un campo format, un nombre de archivo específico o una clase propia.

Esto facilita la compatibilidad con antiguas copias, pero una lista arbitraria llamada datasets también puede interpretarse como proyecto.

7. Diferencia entre dataset y proyecto#

7.1. Dataset#

Un dataset es un único objeto phyloseq que puede contener otu_table, sample_data, tax_table, árbol filogenético y secuencias de referencia.

Solo la OTU table es obligatoria para la inserción en el registro general.

7.2. Proyecto .rds de datos#

Un proyecto cargado por Input data contiene principalmente una lista de datasets, el nombre del dataset activo y metadatos opcionales de guardado.

list(
  version = 2,
  format = "version_ok_project",
  saved_at = ...,
  datasets = ...,
  active_ds = ...
)

7.3. Proyecto completo .zip#

Un .zip completo puede incluir figuras, historiales, archivos de módulos, parámetros y manifiesto. Debe cargarse con Datasets → Importar un proyecto (.zip).

7.4. El proyecto actual no cambia#

Importar un proyecto .rds desde Input data no crea un nuevo proyecto nombrado, no cambia automáticamente el proyecto actual y no restaura figuras, historiales ni navegación completa. Solo añade o reemplaza datasets en memoria.

8. Cargar un archivo#

8.1. Selección#

El selector acepta un archivo por vez. Tras seleccionarlo, BarCodeR lee inmediatamente su contenido para decidir el flujo siguiente.

8.2. Error de lectura#

La importación se detiene si el archivo está corrupto, no es una serialización R válida, requiere una clase o paquete ausente, o no puede deserializarse.

El selector se reinicia para permitir volver a seleccionar el mismo archivo después de corregirlo.

9. .RData con varios objetos#

Cuando se detectan varios objetos compatibles aparece Elegir el objeto que se cargará.

Cada opción muestra el nombre R y el tipo detectado.

ps_coi       (dataset)
ps_16s       (dataset)
my_project   (project)

9.1. Utilizar el objeto#

Utilizar este objeto continúa con el flujo correspondiente.

9.2. Cancelar#

Cancelar cierra la ventana, vacía el selector y elimina el objeto temporal.

9.3. Cruz superior#

La cruz superior cierra la ventana, pero no realiza exactamente la misma limpieza interna que Cancelar. El mismo archivo puede no volver a activar el evento hasta seleccionar otro archivo o refrescar el campo. Es preferible usar Cancelar.

10. Cargar un dataset phyloseq único#

Cuando se detecta un dataset, BarCodeR abre Preparar la carga del dataset.

La ventana permite elegir el nombre, decidir entre añadir o reemplazar y revisar la limpieza automática.

11. Nombre del dataset#

11.1. Nombre propuesto#

En un .rds, deriva generalmente del archivo. En un .RData, se prioriza el nombre del objeto R.

11.2. Limpieza#

Se eliminan espacios externos, se sustituyen caracteres no permitidos por _, se eliminan _ en los extremos y se utiliza dataset si el resultado queda vacío.

Se conservan principalmente caracteres alfanuméricos, _ y -. El tratamiento de caracteres no ASCII también depende de la configuración regional de R.

11.3. Colisión de nombres#

En modo añadir, BarCodeR protege el dataset existente mediante un sufijo:

COI
COI_2
COI_3

12. Añadir o reemplazar#

12.1. Añadir#

Es el modo predeterminado. Conserva los datasets actuales, añade el nuevo, hace único su nombre y lo establece como activo.

12.2. Reemplazar#

Elimina de la memoria todos los datasets actuales, conserva solo el nuevo y lo establece como activo.

Atención: no se eliminan los archivos fuente del disco, pero pueden perderse datasets no guardados. Guardar el proyecto en Datasets antes de reemplazar.

12.3. Sesión vacía#

Si no existe ningún dataset, no se muestra la elección; la carga equivale a reemplazar una lista vacía.

13. Limpieza aplicada#

BarCodeR no reconstruye todo el objeto ni transpone automáticamente las tablas.

Realiza principalmente:

  1. identificación del eje de muestras;
  2. estandarización eventual de nombres;
  3. sincronización con metadata;
  4. sustitución de celdas metadata vacías por NA;
  5. verificación de determinados identificadores.

14. Orientación de la OTU table#

BarCodeR conserva la orientación y utiliza taxa_are_rows().

14.1. Taxones en filas#

Con taxa_are_rows(ps) == TRUE, los taxones están en filas y las muestras en columnas. Se limpian los nombres de columnas.

14.2. Taxones en columnas#

Con taxa_are_rows(ps) == FALSE, las muestras están en filas. Se limpian los nombres de filas.

14.3. Sin transposición#

La aplicación no fuerza ASV en filas, muestras en columnas ni una orientación común. La antigua documentación sobre una ventana de elección de orientación ya no es válida.

15. Estandarización de nombres de muestras#

15.1. Transformaciones#

Se intenta transliterar acentos, se eliminan espacios externos, se sustituyen espacios y caracteres inseguros por _, se fusionan _ repetidos, se eliminan los de los extremos, se rellenan nombres vacíos y se añaden sufijos para duplicados.

15.2. Ejemplos#

Antes Resultado posible
Station 01 Station_01
Station-01 Station_01
Échantillon A Echantillon_A
sample/1 sample_1
sample sample
vacío sample_1
dos sample sample, sample_1

15.3. Motivo#

Los nombres complejos pueden provocar problemas en fórmulas estadísticas, uniones, paquetes R, archivos, gráficos, exportaciones y selectores Shiny.

15.4. La limpieza puede cancelarse#

La limpieza de la OTU table solo se conserva si la metadata puede seguir alineada.

Si BarCodeR no puede establecer una correspondencia segura, puede revertir el renombrado. Se mantienen los nombres originales y se muestra una advertencia. La coherencia prima sobre la limpieza estética.

16. Tratamiento de metadata#

sample_data es opcional. Un phyloseq sin metadata puede importarse, pero no permite análisis que necesiten variables de muestras.

16.1. Alineación de rownames#

Si los rownames de metadata coinciden con los nombres originales de la OTU table, se aplican las mismas transformaciones.

Si no se demuestra la coincidencia directa, se intenta limpiar metadata por separado y solo se aplica si sigue siendo compatible.

Si la correspondencia es incierta, se conservan los nombres y se informa mediante una advertencia.

17. Celdas vacías de metadata#

Las cadenas vacías o compuestas solo por espacios se sustituyen por NA reales.

Original Después
"" NA
" " NA
"0" "0"
"NA" "NA"
NA real NA

La cadena literal "NA" no se convierte automáticamente.

17.1. Consecuencia sobre los tipos#

La implementación actual convierte cada columna de metadata a carácter antes de sustituir vacíos.

Columnas numéricas, enteras, lógicas, factores o fechas pueden volver como texto. Después de importar, hay que verificar los tipos en Description, Data Edition o R.

Es una transformación real de los datos, no solo visual.

18. Componentes no modificados#

Input data no modifica directamente abundancias, orientación, nombres de ASV, taxonomía, rangos, secuencias, árbol, ceros, taxones o muestras vacías, valores negativos/decimales ni NA de la OTU table.

No realiza una validación científica exhaustiva.

19. Control de coherencia de un dataset#

19.1. Clase phyloseq#

El objeto debe heredar de phyloseq.

19.2. OTU table obligatoria#

Debe existir una otu_table.

19.3. Identificadores de muestras#

Si existe sample_data, sus rownames deben corresponder al conjunto completo de muestras. El orden puede variar, pero no se acepta metadata parcial.

19.4. Identificadores taxonómicos#

Si existe tax_table, sus rownames deben corresponder a todos los taxones de la OTU table.

19.5. Controles no incluidos#

No se valida directamente la cobertura de refseq o árbol, la validez de secuencias, que los conteos sean enteros/no negativos, la coherencia biológica de taxonomía, duplicados taxonómicos ni profundidad mínima.

20. Importación rechazada#

Se rechaza cuando los identificadores no están alineados, falta la OTU table o el objeto no es phyloseq. No se añade ningún dataset y el archivo original no se modifica.

21. Informe tras cargar un dataset#

La ventana Dataset cargado y verificado presenta:

  • nombre final;
  • número de muestras;
  • número de taxones/ASV;
  • número total de acciones;
  • archivo y objeto de origen;
  • modo añadir/reemplazar;
  • total de datasets en memoria;
  • tablas Antes → Después para nombres OTU y metadata;
  • número de celdas vacías sustituidas;
  • advertencias y notas.

Solo se muestran las diez primeras modificaciones, aunque se conserva el total.

22. Cargar un proyecto .rds#

BarCodeR extrae los datasets phyloseq del proyecto.

22.1. Sesión vacía#

Se carga directamente en modo reemplazar y se muestra un informe.

22.2. Sesión con datasets#

La ventana Cargar un proyecto muestra datasets actuales, nombres entrantes y la elección añadir/reemplazar.

23. Añadir datasets de un proyecto#

Conserva los actuales, añade cada phyloseq, resuelve colisiones y adapta el dataset activo.

23.1. Colisión#

Un COI entrante puede convertirse en COI_2.

23.2. Dataset activo#

Si active_ds es válido, se activa el dataset correspondiente, utilizando su nombre final después de resolver colisiones. Si no, se activa el primer dataset importado.

24. Reemplazar por un proyecto#

Elimina los datasets en memoria, carga la lista importada y restaura active_ds si es válido; de lo contrario, selecciona el primero.

No elimina archivos del disco, pero puede perder datos no guardados de la sesión.

25. Nombres de datasets del proyecto#

Los nombres válidos se conservan, salvo colisiones.

Si faltan nombres o están vacíos, se generan:

dataset_1
dataset_2
dataset_3

Actualmente, un solo nombre ausente puede provocar la regeneración de todos los nombres.

26. Contenido no phyloseq#

En una estructura con datasets o ps_registry, solo se conservan finalmente los elementos que heredan de phyloseq.

La lista previa puede incluir nombres que no se cargarán. El informe final es la referencia para conocer el número real.

Un proyecto reconocido pero sin phyloseq válido puede dejar el registro vacío en modo reemplazar.

27. Limpieza de datasets de un proyecto#

Cada phyloseq recibe la misma limpieza de nombres y celdas vacías.

El informe resume, por dataset, muestras, taxones, nombres OTU modificados, nombres metadata modificados y celdas vacías sustituidas.

28. Diferencia de validación#

Un dataset único pasa explícitamente por bcr_guard_ps() antes de insertarse.

Los datasets de un proyecto se limpian, pero no se aplica explícitamente el mismo guard a cada uno antes de insertar la lista completa.

Al activar un dataset, BarCodeR realiza un control global. Después de importar un proyecto, revisar cada dataset importante en Description.

29. Memoria de la sesión#

Los datasets se guardan en datasets() y el nombre activo en active_ds().

Después de importar, el registro cambia, otros módulos ven el nuevo contenido y el proyecto queda marcado como modificado/no guardado.

29.1. Importar no equivale a guardar#

Usar Datasets → Guardar proyecto antes de cerrar.

30. Dataset activo#

El dataset recién importado se vuelve activo. Un proyecto restaura su active_ds cuando es posible o selecciona el primer dataset.

La selección puede cambiarse posteriormente desde el control global, Datasets o módulos sincronizados.

31. Garantías científicas no proporcionadas#

Una importación correcta solo confirma principalmente que el objeto es legible, es phyloseq, contiene OTU table y supera determinados controles de identificadores.

No garantiza conteos brutos, ausencia de transformaciones previas, eliminación de taxones/muestras vacíos, taxonomía válida, rangos ordenados, cobertura completa del árbol/secuencias, diseño experimental válido, réplicas suficientes, clases metadata preservadas ni adecuación a todos los análisis.

32. Verificaciones recomendadas#

Abrir Description y comprobar:

  • muestras, taxones y reads totales;
  • componentes disponibles;
  • nombres de muestras y ASV;
  • tipos de columnas metadata y valores ausentes;
  • orientación y valores de OTU table;
  • rangos taxonómicos y asignaciones;
  • cobertura del árbol y secuencias.

33. Gestión posterior#

Usar Datasets para seleccionar, renombrar, duplicar, eliminar, exportar, guardar, restaurar o cambiar de proyecto.

34. Resolución de problemas#

34.1. El archivo no aparece#

Verificar la extensión y que no esté comprimido adicionalmente.

34.2. Archivo superior a 500 MB#

Reducir el objeto, eliminar componentes innecesarios, dividir datasets, exportar uno por uno o cambiar el límite en un despliegue controlado.

34.3. Consumo de memoria elevado#

El archivo se expande al deserializarse. Liberar memoria.

34.4. Error al leer .rds#

obj <- readRDS("archivo.rds")
class(obj)

34.5. .RData sin objeto reconocido#

load("archivo.RData")
ls()
class(nombre_objeto)

34.6. Varios objetos#

Seleccionar el objeto deseado en la ventana.

34.7. Falso proyecto#

Guardar directamente el phyloseq:

saveRDS(mi_phyloseq, "dataset.rds")

34.8. OTU table ausente#

phyloseq::otu_table(ps)

34.9. IDs de muestras incoherentes#

setequal(
  phyloseq::sample_names(ps),
  rownames(as.data.frame(phyloseq::sample_data(ps)))
)

Debe devolver TRUE.

34.10. IDs taxonómicos incoherentes#

setequal(
  phyloseq::taxa_names(ps),
  rownames(as(phyloseq::tax_table(ps), "matrix"))
)

34.11. Metadata parcial#

Completar muestras, retirar coherentemente las no documentadas o reconstruir el objeto.

34.12. Nombres cambiados#

Consultar el informe Antes → Después.

34.13. Nombres no limpiados#

La limpieza probablemente se revirtió para preservar la correspondencia con metadata.

34.14. Variable numérica convertida en texto#

str(as.data.frame(phyloseq::sample_data(ps)))
metadata$Depth <- as.numeric(metadata$Depth)

34.15. Cadena "NA"#

metadata[metadata == "NA"] <- NA

34.16. Menos datasets de los esperados#

Algunos elementos no eran phyloseq o fueron ignorados.

34.17. Todos los nombres son dataset_1, etc.#

names(project$datasets) <- c("COI", "16S", "ITS")

34.18. Sufijo _2#

Se protegió un nombre existente en modo añadir.

34.19. Desaparición de datasets previos#

Se confirmó el modo reemplazar. Restaurarlos desde una copia.

34.20. Las figuras no se restauraron#

Un .rds de Input data contiene datos, no el proyecto completo. Importar el .zip en Datasets.

34.21. El mismo archivo no activa el evento#

La ventana anterior pudo cerrarse con la cruz. Seleccionar otro archivo temporalmente, reiniciar el campo o recargar la pestaña.

34.22. Sin metadata#

La importación puede funcionar, pero no los análisis basados en variables de muestras.

34.23. Sin taxonomía#

Las funciones dependientes de tax_table no estarán disponibles.

34.24. Sin árbol#

Las distancias dependientes del árbol, como determinadas UniFrac, no estarán disponibles.

34.25. Sin secuencias de referencia#

No estarán disponibles los análisis que utilizan directamente las secuencias.

35. Lista de comprobación antes de importar#

Archivo#

  • Formato .rds, .RData o .rda.
  • Tamaño inferior a 500 MB.
  • Memoria suficiente.
  • Lectura correcta en R.

Phyloseq#

  • OTU table presente.
  • IDs de muestras únicos.
  • IDs de taxones únicos.
  • Metadata completa si existe.
  • Taxonomía completa si existe.
  • Árbol y secuencias coherentes si existen.

Metadata#

  • Valores ausentes identificados.
  • Columnas numéricas conocidas.
  • Factores ordenados y fechas documentados.
  • Nombres alineados con la OTU table.

Sesión#

  • Datasets existentes guardados.
  • Elección añadir/reemplazar comprendida.
  • Colisiones de nombres previstas.

36. Lista después de importar#

  • Leer todo el informe.
  • Verificar renombrados.
  • Verificar muestras y taxones.
  • Verificar tipos metadata.
  • Verificar NA introducidos.
  • Abrir Description.
  • Revisar OTU table y taxonomía.
  • Revisar árbol y secuencias.
  • Guardar el proyecto.

37. Límites actuales#

  1. No hay validación científica exhaustiva.
  2. Las columnas metadata pueden convertirse a texto.
  3. No se transpone automáticamente.
  4. No se corrige la taxonomía.
  5. La validación de proyectos es menos estricta.
  6. El reconocimiento de proyectos es estructural.
  7. Cerrar con la cruz puede dejar estado temporal.
  8. El límite es 500 MB.

38. Flujo recomendado#

  1. Construir y verificar el phyloseq en R.
  2. Guardarlo con saveRDS().
  3. Abrir Input data.
  4. Elegir el archivo.
  5. Elegir añadir o reemplazar.
  6. Verificar el nombre.
  7. Confirmar.
  8. Leer el informe.
  9. Abrir Description.
  10. Verificar dimensiones y componentes.
  11. Verificar tipos metadata.
  12. Guardar el proyecto.

39. Preparar un dataset único#

library(phyloseq)

stopifnot(inherits(ps, "phyloseq"))
stopifnot(!is.null(otu_table(ps)))

if (!is.null(sample_data(ps, errorIfNULL = FALSE))) {
  stopifnot(setequal(
    sample_names(ps),
    rownames(as.data.frame(sample_data(ps)))
  ))
}

if (!is.null(tax_table(ps, errorIfNULL = FALSE))) {
  stopifnot(setequal(
    taxa_names(ps),
    rownames(as(tax_table(ps), "matrix"))
  ))
}

saveRDS(ps, "dataset_phyloseq.rds")

40. Proyecto de datos compatible#

project <- list(
  version = 2,
  format = "version_ok_project",
  saved_at = Sys.time(),
  datasets = list(
    COI = ps_coi,
    `16S` = ps_16s
  ),
  active_ds = "COI"
)

saveRDS(project, "project_data_only.rds")

Este archivo puede cargarse en Input data, pero no contiene necesariamente figuras ni historiales.

41. Principios de trazabilidad#

Conservar el archivo original, no sobrescribir exportaciones anteriores, anotar la fecha, conservar el nombre del objeto, revisar el informe, documentar los renombrados, verificar los tipos metadata, guardar el proyecto y distinguir el objeto fuente del objeto limpiado en memoria.

El objeto en BarCodeR puede diferir del archivo fuente por la limpieza de nombres, sincronización con metadata, sustitución de celdas vacías y conversión de columnas.

Fuentes internas verificadas#

  1. modules/data/mod_data_loader_ui.R — interfaz actual y extensiones aceptadas.
  2. modules/data/mod_data_loader_server.R — estado temporal, detección, limpieza, modales, inserción e informes.
  3. modules/_shared/_dataset_naming.R — nombres seguros y únicos.
  4. modules/_shared/_ps_guard.R — clase phyloseq, OTU table y coherencia de identificadores.
  5. modules/datasets/mod_datasets_server.R y mod_datasets_ui.R — formatos de proyecto.
  6. app.R — límite de 500 MB, registro datasets(), dataset activo y estado no guardado.
