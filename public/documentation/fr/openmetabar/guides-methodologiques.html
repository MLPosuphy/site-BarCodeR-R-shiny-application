OpenMetaBar — Guides méthodologiques

1. Présentation générale#

L’onglet OpenMetaBar permet de lancer et de suivre un pipeline complet de traitement de données de métabarcoding à partir de fichiers FASTQ.

L’analyse n’est pas exécutée directement dans l’application. BarCodeR agit comme une interface de préparation, de soumission et de suivi :

  1. l’utilisateur choisit le contexte biologique et technique de son analyse ;
  2. il sélectionne ses fichiers FASTQ, son plan expérimental et sa base de référence ;
  3. BarCodeR vérifie les fichiers et prépare leur transfert ;
  4. l’utilisateur configure les ressources du cluster et les paramètres du pipeline ;
  5. BarCodeR crée un dossier isolé pour le run ;
  6. le pipeline OpenMetaBar embarqué dans l’application est copié sur le cluster ;
  7. les images Singularity nécessaires sont vérifiées ou installées ;
  8. une tâche Slurm est soumise ;
  9. l’application suit l’exécution et détecte les fichiers produits ;
  10. un objet phyloseq peut ensuite être intégré dans BarCodeR.

OpenMetaBar couvre plusieurs technologies et plusieurs parcours d’analyse :

  • Oxford Nanopore Technologies, ou ONT ;
  • PacBio ;
  • Illumina ;
  • LotuS3 ;
  • NextITS ;
  • le parcours de rapport IDMABIO.

2. Ce qu’OpenMetaBar fait et ne fait pas#

2.1. Ce qu’OpenMetaBar automatise#

OpenMetaBar automatise notamment :

  • la préparation du dossier de travail ;
  • la validation initiale des fichiers ;
  • le transfert des fichiers locaux ;
  • la réécriture des chemins FASTQ dans le design file ;
  • la génération de la configuration Nextflow ;
  • la préparation des ressources Slurm ;
  • le déploiement du pipeline ;
  • la gestion des images Singularity ;
  • la soumission du job ;
  • le suivi de l’état Slurm ;
  • la détection des résultats ;
  • l’import d’un objet phyloseq.

2.2. Ce qui reste sous la responsabilité de l’utilisateur#

L’application ne peut pas déterminer automatiquement :

  • si le marqueur sélectionné correspond réellement aux amorces utilisées ;
  • si la longueur attendue saisie est biologiquement pertinente ;
  • si une base de référence est adaptée au marqueur et aux organismes étudiés ;
  • si les seuils de qualité sont adaptés à la technologie de séquençage ;
  • si le filtre codant est pertinent ;
  • si la méthode de regroupement choisie convient à l’objectif de l’étude ;
  • si les paramètres taxonomiques permettent une identification suffisamment fiable ;
  • si les ressources Slurm demandées sont adaptées au volume de données.

Principe important — Une valeur proposée par défaut dans l’application n’est pas nécessairement une recommandation universelle.

3. Vue d’ensemble du parcours#

Le parcours conseillé est le suivant :

  1. Vérifier ou établir la connexion au cluster.
  2. Définir le contexte de l’analyse.
  3. Valider le contexte.
  4. Choisir les FASTQ, le design file et la base de référence.
  5. Corriger ou créer le design file si nécessaire.
  6. Valider les fichiers et préparer leur transfert.
  7. Configurer le run et les ressources Slurm.
  8. Valider la configuration générale.
  9. Configurer les paramètres propres à la route sélectionnée.
  10. Examiner les aperçus facultatifs.
  11. Lancer l’analyse.
  12. Suivre les étapes et les journaux d’exécution.
  13. Examiner les résultats.
  14. Intégrer le phyloseq dans BarCodeR.
  15. Gérer le run depuis l’historique.

La validation du contexte peut être réalisée sans connexion au cluster. En revanche, la connexion devient nécessaire pour parcourir des fichiers distants, valider et transférer les fichiers, vérifier le dossier distant, détecter les partitions Slurm, préparer les conteneurs, soumettre le run, suivre son exécution et consulter les runs historiques.

4. Choisir le parcours d’analyse#

La combinaison technologie + marqueur + moteur détermine le sous-pipeline exécuté.

4.1. Routes disponibles#

Technologie Marqueur Moteur disponible Route principale
ONT COI LotuS3 ONT standard
ONT 16S LotuS3 ONT standard
ONT 18S LotuS3 ONT standard
ONT COI-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 16S-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 18S-idmabio LotuS3 + IDMABIO ONT IDMABIO
PacBio 16S LotuS3 PacBio 16S
PacBio ITS LotuS3 ou NextITS PacBio ITS
PacBio LSU LotuS3 ou NextITS PacBio LSU
Illumina 16S LotuS3 Illumina
Illumina ITS LotuS3 Illumina
Illumina LSU LotuS3 Illumina

Les variantes -idmabio ne sont proposées que lorsque l’application reconnaît une connexion au cluster biglogin compatible.

4.2. Conséquences du choix de la route#

Le contexte détermine :

  • si MiniBar est disponible ;
  • si le moteur NextITS peut être utilisé ;
  • quels paramètres sont affichés ;
  • quelles images Singularity sont obligatoires ;
  • quelles étapes du pipeline sont exécutées ;
  • quelles sorties peuvent être produites.

Modifier la technologie, le marqueur ou le moteur après validation invalide le contexte. Les étapes dépendantes doivent alors être vérifiées de nouveau.

5. Connexion au cluster#

5.1. Ouvrir la fenêtre de connexion#

Le bouton situé en haut de l’onglet indique l’état de la connexion :

  • Cluster non connecté : aucune connexion SSH active ;
  • Connexion active à vérifier : la connexion SSH existe, mais certains prérequis du cluster ne sont pas confirmés ;
  • Cluster connecté : la connexion et les principales commandes nécessaires ont été détectées.

Cliquer sur ce bouton ouvre la fenêtre de connexion.

5.2. Informations à fournir#

La connexion utilise l’adresse du serveur, le port SSH, le nom d’utilisateur et éventuellement un mot de passe. Le mot de passe peut être laissé vide lorsqu’une authentification par clé SSH est déjà configurée et fonctionnelle.

5.3. Contrôles effectués#

Après la connexion, BarCodeR vérifie notamment la disponibilité de Bash, find, tar, sbatch, squeue, sacct, scancel, sinfo, Rscript, des partitions Slurm accessibles et de certaines limites de temps, de mémoire et de processeurs.

Une connexion SSH peut donc être ouverte alors que le cluster n’est pas encore considéré comme prêt pour lancer OpenMetaBar.

5.4. Cas du cluster biglogin#

Sur l’infrastructure prévue par l’application, la connexion peut être réalisée directement ou au moyen d’un relais par bigm9 lorsque la connexion directe n’est pas utilisable. Ce mécanisme est géré automatiquement.

5.5. Déconnexion pendant un run#

Une déconnexion de l’application n’annule pas le job Slurm. Une fois soumis, le calcul continue sur le cluster. Le run pourra être retrouvé depuis l’historique lors d’une nouvelle connexion si l’utilisateur se reconnecte au même cluster, utilise un dossier racine compatible et dispose des droits requis.

6. Définir le contexte de l’analyse#

La première carte de configuration contient les paramètres qui déterminent la route du pipeline.

6.1. Technologie de séquençage#

Oxford Nanopore Technologies

Choisir ONT entraîne notamment l’affichage des marqueurs COI, 16S et 18S, l’accès éventuel aux variantes IDMABIO, l’affichage du démultiplexage MiniBar et l’utilisation de la route ONT avec LotuS3.

PacBio

Choisir PacBio entraîne l’affichage des marqueurs 16S, ITS et LSU, le choix LotuS3/NextITS pour ITS et LSU, l’absence de MiniBar et l’utilisation d’une route PacBio dédiée.

Illumina

Choisir Illumina entraîne l’affichage des marqueurs 16S, ITS et LSU, l’utilisation de LotuS3, l’absence de MiniBar et la prise en charge de fichiers simples ou appariés selon le design file.

6.2. Marqueur ou cible#

Le marqueur sert à choisir la route, proposer un type de base, proposer une région NextITS, identifier les variantes IDMABIO et adapter les paramètres visibles. Il ne vérifie pas que les amorces du design ciblent réellement ce marqueur.

Marqueur Type de base suggéré
COI BOLD
16S SILVA
18S PR2
ITS UNITE
LSU SILVA

Cette suggestion modifie le type déclaré de la base, mais ne sélectionne pas automatiquement un nouveau fichier FASTA.

6.3. Type de base de référence#

Les valeurs proposées sont BOLD, SILVA, PR2, UNITE, NCBI nt et personnalisée. Le type déclaré sert principalement à indiquer au pipeline comment interpréter les en-têtes du FASTA et construire la correspondance taxonomique.

Il faut distinguer le type de base déclaré et le fichier FASTA réellement sélectionné. Ils doivent être cohérents. Déclarer une base comme BOLD ne transforme pas un FASTA personnel en base BOLD.

6.4. Moteur d’analyse#

Le choix du moteur n’apparaît que pour PacBio + ITS et PacBio + LSU. Les choix sont LotuS3 et NextITS. Dans les autres contextes, le sélecteur n’est pas affiché et n’a pas d’effet sur la route.

6.5. Validation du contexte#

Cliquer sur Valider le contexte débloque le choix des fichiers. Modifier ensuite la technologie, le marqueur ou le moteur reverrouille cette étape.

7. Choisir les fichiers du run#

Après validation du contexte, le bouton Choisir les fichiers du run devient disponible. Trois catégories de fichiers doivent être définies : les FASTQ, le design file et la base de référence. Une base de chimères supplémentaire est demandée pour NextITS.

7.1. Choisir les FASTQ#

Origine locale

Les FASTQ locaux sont sélectionnés avec l’explorateur de fichiers de l’application. Ils ne sont pas envoyés comme un téléversement web classique : BarCodeR utilise leur chemin réel, puis les transfère vers le cluster.

Conséquences : la limite habituelle des téléversements Shiny ne s’applique pas, mais les fichiers doivent rester accessibles jusqu’à la fin du transfert.

Origine cluster

Les FASTQ peuvent déjà être présents sur le cluster. Ils peuvent être sélectionnés en indiquant un chemin ou avec l’explorateur distant. La connexion SSH doit être active.

Un ou plusieurs FASTQ

L’application accepte plusieurs fichiers et les conserve séparément. Ils ne sont pas concaténés automatiquement. Le nom de base est conservé : deux fichiers de dossiers différents portant exactement le même nom provoquent une collision.

Exemple problématique :

/run1/sample.fastq.gz
/run2/sample.fastq.gz

Extensions attendues : .fastq, .fastq.gz, .fq ou .fq.gz.

FASTQ déjà démultiplexés

Lorsque chaque fichier correspond déjà à un échantillon, désactiver MiniBar pour ONT, renseigner un échantillon par ligne et faire correspondre chaque ligne au bon FASTQ.

FASTQ non démultiplexés

Lorsqu’un fichier contient plusieurs échantillons identifiables par barcodes, activer MiniBar et renseigner les barcodes et amorces pour chaque échantillon. Plusieurs lignes du design peuvent pointer vers le même FASTQ.

7.2. Choisir le design file#

Le design file peut être local, distant ou créé/modifié dans l’éditeur intégré. Les formats TSV et CSV sont acceptés.

Colonnes requises par le pipeline

Colonne Rôle
Sample_ID Identifiant unique de l’échantillon
fastq_path Chemin vers le ou les FASTQ
barcodeF Barcode forward
barcodeR Barcode reverse
primerF Amorce forward
primerR Amorce reverse

Même lorsque les barcodes ne sont pas utilisés, les colonnes doivent exister. Une valeur explicite comme NA peut être utilisée plutôt qu’une cellule vide selon le fonctionnement attendu.

Attention — L’éditeur intégré peut considérer qu’un tableau à deux colonnes est éditable, mais la validation complète du pipeline exige les six colonnes exactes. Un design « cohérent » dans l’éditeur peut encore être refusé au lancement.

Identifiants d’échantillons

Ils doivent être renseignés, uniques et limités de préférence à A-Z, a-z, 0-9, ., - et _.

La correction automatique translittère les accents, remplace les caractères invalides, nettoie les séparateurs de bord et ajoute des suffixes en cas de doublon. La casse est conservée.

Colonne de chemin

La deuxième colonne doit être reconnue comme colonne de chemin. Les noms compris incluent path, fastq_path, filepath, file_path, input_dir, directory, dir et folder. Pour éviter toute ambiguïté, utiliser directement fastq_path.

Avant le lancement, cette colonne est réécrite sous le nom fastq_path et les chemins sont adaptés au dossier distant.

Fichiers appariés

Pour une paire Illumina, la cellule fastq_path peut contenir deux fichiers séparés par une virgule :

echantillon_R1.fastq.gz,echantillon_R2.fastq.gz

Les deux fichiers doivent avoir été sélectionnés et leurs noms doivent correspondre exactement.

Correspondance entre design et FASTQ

Chaque fichier référencé doit correspondre à un nom sélectionné. Les différences d’extension, de casse, de suffixe ou une faute de frappe peuvent provoquer une erreur.

Cas d’un FASTQ unique

Lorsque toutes les lignes correspondent au même fichier brut, l’application peut réécrire les chemins pour que chaque échantillon utilise ce FASTQ distant, notamment avant MiniBar.

7.3. Amorces dans le design file#

primerF et primerR sont utilisées pour l’orientation. Elles doivent être saisies en 5’ vers 3’, avec des caractères IUPAC valides et sans espace. Les bases dégénérées sont acceptées.

Lorsque l’orientation est activée, le pipeline recherche une paire d’amorces unique pour chaque FASTQ. Une erreur est produite si aucune paire n’est trouvée, si plusieurs paires distinctes correspondent au même FASTQ ou si une amorce contient un caractère invalide.

7.4. Barcodes dans le design file#

barcodeF et barcodeR sont utilisés par MiniBar. Des barcodes trop proches combinés à une tolérance élevée augmentent le risque de mauvaise attribution.

7.5. Choisir la base de référence#

La base peut être locale ou distante et doit être un FASTA compatible (.fa, .fna, .fasta, .fas, éventuellement compressé en .gz).

Elle sert à produire une version nettoyée du FASTA, une table taxonomique extraite des en-têtes et l’assignation taxonomique.

Vérifier que le fichier correspond au marqueur, que les séquences utilisent le bon alphabet, que les identifiants sont uniques, que les en-têtes contiennent une taxonomie exploitable, que le type déclaré correspond au format et que le fichier est lisible sur le cluster.

8. Utiliser l’éditeur de design#

8.1. Modifier les cellules#

Les cellules peuvent être modifiées directement. Après chaque modification, l’application réévalue la structure minimale, la colonne de chemin, les identifiants et la correspondance avec les FASTQ.

8.2. Ajouter ou supprimer des lignes#

Une ligne peut être ajoutée et plusieurs lignes peuvent être supprimées. Les lignes entièrement vides sont ignorées lors de l’enregistrement, mais déclenchent un avertissement.

8.3. Ajouter, renommer ou supprimer une colonne#

L’éditeur permet ces trois opérations. Au moins deux colonnes doivent être conservées. Pour un design complet, obtenir exactement Sample_ID, fastq_path, barcodeF, barcodeR, primerF, primerR.

8.4. Corriger les noms d’échantillons#

Le bouton de correction nettoie les caractères, évite les identifiants vides et rend les noms uniques. Vérifier les modifications, car ces identifiants apparaîtront dans les résultats et le phyloseq.

8.5. Générer un design depuis les FASTQ#

Cette option n’est disponible que lorsque MiniBar est désactivé. L’application crée initialement SampleID et path.

Ce design n’est pas encore complet. Il faut renommer les colonnes en Sample_ID et fastq_path, ajouter barcodeF, barcodeR, primerF, primerR, puis renseigner les valeurs nécessaires.

8.6. Enregistrer le design#

L’enregistrement est bloqué tant que l’éditeur détecte une erreur de structure. Il remplace la sélection par une copie locale temporaire design_edite.tsv. La validation complète du pipeline aura lieu au lancement.

9. Valider et préparer les fichiers#

Le bouton Valider et transférer exige une connexion active. Cette étape vérifie les sélections, l’existence des fichiers, le début des FASTQ, certains problèmes du design, les noms d’échantillons et l’espace disque distant. Elle transfère les fichiers locaux dans une zone temporaire et conserve les chemins des fichiers déjà distants.

Le contrôle de l’espace disque reste préventif et peut être indicatif selon le système. À la fin, le bouton principal indique Fichiers prêts.

10. Configurer le run et le cluster#

10.1. Dossier racine des runs#

Un sous-dossier unique est créé sous cette racine pour chaque run. L’utilisateur doit pouvoir créer, écrire, exécuter, lire et nettoyer les fichiers. Le pipeline embarqué est copié dans le dossier du run puis supprimé selon la logique de nettoyage.

10.2. Partition Slurm#

Lorsque sinfo est disponible, les partitions détectées sont proposées. La partition influence les ressources, la durée maximale, la priorité et les restrictions de compte. Une partition visible n’est pas forcément autorisée pour l’utilisateur.

10.3. Mémoire pour LotuS3#

La mémoire doit inclure une unité, par exemple 16G, 70G ou 120G. Ne pas saisir uniquement 70, qui peut être interprété comme environ 70 Mo par Slurm.

Une demande trop faible peut provoquer OUT_OF_MEMORY; une demande trop élevée peut augmenter le temps d’attente.

10.4. Cœurs pour LotuS3#

Le nombre de cœurs définit les processeurs Slurm, les threads LotuS3 et certaines ressources des processus enfants. Une demande élevée ne garantit pas une accélération proportionnelle et peut rendre le job plus difficile à planifier.

10.5. Module conteneur#

Ce champ doit correspondre exactement au module fournissant Singularity ou Singularity-CE, par exemple singularity-ce/4.1.0.

10.6. Module Nextflow#

Ce champ indique la version de Nextflow, par exemple nextflow/25.10.4. Un module inexistant ou incompatible empêche le lancement.

10.7. Nom du run#

Le nom facilite l’identification du dossier, du job Slurm et de l’historique. L’application ajoute automatiquement une date, un identifiant de session et un suffixe aléatoire. Éviter les noms trop longs, les caractères spéciaux et les informations sensibles.

10.8. Conserver les fichiers intermédiaires#

L’option de débogage conserve work/ après un succès. Ce dossier facilite le diagnostic et l’inspection des commandes, mais peut être très volumineux. En cas d’échec, les intermédiaires sont déjà conservés. work/ peut être supprimé plus tard depuis l’historique.

11. Comprendre les valeurs initiales#

L’application s’ouvre avec des paramètres initialement adaptés à ONT + COI : orientation activée, filtre de longueur activé, longueur 658, qualité minimale 20, filtre codant activé et table de traduction 5.

Ces valeurs ne conviennent pas automatiquement à 16S, 18S, ITS ou LSU. Pour ces marqueurs, réexaminer au minimum le filtre codant, la longueur, la table génétique, le type d’amplicon et le groupe taxonomique.

La première modification de certains paramètres affiche un avertissement indiquant que la valeur initiale est optimisée. Cela signifie seulement qu’une valeur initiale contrôlée existe, pas qu’elle est optimale pour tous les protocoles.

12. Démultiplexage MiniBar — routes ONT#

12.1. Activer ou désactiver MiniBar#

Activer MiniBar lorsqu’un FASTQ contient plusieurs échantillons distingués par barcodes et que le design contient les informations requises. MiniBar produit des FASTQ par échantillon et des métriques de reads démultiplexés et conservés. Les reads inconnus ou ambigus ne sont pas publiés comme échantillons attribués.

Désactiver MiniBar lorsque les FASTQ sont déjà séparés par échantillon ou que le démultiplexage a été réalisé en amont.

12.2. Méthode d’identification — M#

Les méthodes 1, 2 et 3 sont transmises directement à MiniBar avec -M. Elles modifient la stratégie interne d’attribution à partir des barcodes et amorces.

L’application ne détaille pas les différences algorithmiques. Conserver la méthode validée pour le protocole, ne pas changer de méthode entre lots comparés sans justification et vérifier les métriques après modification.

12.3. Erreurs maximales sur le barcode — e#

Une valeur faible augmente la spécificité mais peut perdre des reads bruités. Une valeur élevée récupère davantage de barcodes altérés mais augmente le risque de confusion entre barcodes proches. 0 impose un appariement exact.

12.4. Erreurs maximales sur l’amorce — E#

Une tolérance plus élevée augmente la récupération de reads bruités mais peut accroître les associations non spécifiques. Une tolérance faible renforce la spécificité mais peut éliminer des reads valides.

12.5. Paramètre MiniBar — l#

L’interface le présente comme une fenêtre de recherche, tandis que le schéma du pipeline le décrit comme une longueur minimale des reads. La valeur est transmise directement à -l.

En raison de cette incohérence, laisser le champ vide tant qu’une valeur n’a pas été validée, ne pas lui attribuer arbitrairement une signification et comparer les métriques avant/après toute modification.

13. Orientation des amplicons#

13.1. Lecture simple#

Pour un FASTQ simple, le pipeline retrouve les amorces, détecte les deux orientations, remet les séquences dans le sens primerF → primerR, retire les amorces et conserve la région interne. Les reads sans paire complète sont éliminés.

13.2. Amorces non dégénérées et dégénérées#

Avec des amorces composées uniquement de A/C/G/T, l’étape autorise actuellement jusqu’à une différence. Avec des codes IUPAC dégénérés, la recherche utilise la reconnaissance des motifs dégénérés sans activer ce mode de différence supplémentaire.

13.3. Lectures appariées#

Pour une paire FASTQ, l’étape d’orientation est ignorée et produit SKIPPED_PAIRED_END. Les reads ne sont donc pas réorientés ni débarrassés de leurs amorces par ce processus.

13.4. Route NextITS#

NextITS prend en charge ses propres traitements associés aux régions ITS et aux amorces ; cette étape générale ne s’applique pas de la même manière.

13.5. Quand désactiver l’orientation#

La désactiver si les amorces ont déjà été retirées, si toutes les séquences sont déjà orientées ou si le protocole amont garantit cette préparation.

14. Ordre des filtres#

Les filtres sont cumulatifs et appliqués dans cet ordre : qualité, longueur, codant. Chaque filtre reçoit uniquement les reads conservés par le précédent. Plusieurs réglages modérément stricts peuvent donc devenir très restrictifs. Le pipeline s’arrête si aucun read ne reste.

15. Filtre de longueur#

15.1. Activation et saisie#

Lorsque le filtre est désactivé, la longueur saisie n’est pas utilisée. Lorsqu’il est activé, fournir un ou plusieurs entiers séparés par des virgules, par exemple 480 ou 450,550.

15.2. Intervalle réellement utilisé#

Le pipeline applique une marge de ±100 nucléotides autour de chaque longueur.

Pour 658, l’intervalle est 558–758. Pour 500,800, les intervalles sont 400–600 et 700–900.

15.3. Choisir la longueur#

La valeur dépend de la région entre les amorces, de la présence des amorces au moment du filtre, de la variabilité biologique, de la technologie et des groupes ciblés. 658 correspond au contexte initial COI et ne doit pas être conservé automatiquement.

15.4. Champ vide ou invalide#

Dans le fonctionnement actuel, une valeur vide ou non interprétable peut être remplacée silencieusement par 658. Si le filtre est activé, ne pas laisser le champ vide sauf si cette valeur est réellement souhaitée.

15.5. Lectures appariées#

Le filtre est appliqué séparément à R1 et R2 avant resynchronisation. La longueur évaluée est celle de chaque read, et non celle de l’amplicon fusionné. Pour des reads de 250 nt, une longueur attendue de 658 éliminerait les deux membres.

15.6. Resynchronisation#

Après filtrage, les paires sont resynchronisées par identifiant. Les reads sans partenaire conservé deviennent orphelins. Seules les paires complètes poursuivent le pipeline.

16. Filtre de qualité#

Le seuil minimal est transmis à SeqKit. Une valeur élevée augmente la stringence et réduit les reads ; une valeur faible conserve davantage de profondeur mais plus de bruit. Le choix dépend de la technologie, de la génération de séquençage et du prétraitement.

Pour les paires, le filtre s’applique séparément à R1 et R2, puis les fichiers sont resynchronisés. Si un seul membre est éliminé, l’autre devient orphelin.

17. Filtre codant#

Le filtre conserve les reads possédant au moins un cadre de lecture traduisible sans codon stop interne selon la table sélectionnée. Il teste les trois cadres dans l’orientation fournie.

Il est principalement pertinent pour une région codante comme COI et généralement inadapté à 16S, 18S, ITS et LSU. Si l’orientation est désactivée, des séquences codantes en orientation inverse peuvent être rejetées.

Valeur Table génétique
1 Code standard
2 Mitochondries de vertébrés
5 Mitochondries d’invertébrés
11 Bactéries, archées et plastes

La table 5 est proposée pour un COI mitochondrial d’invertébrés, mais ne convient pas à toutes les séquences COI ni aux autres marqueurs.

Pour les paires, le filtre est appliqué séparément aux deux reads avant resynchronisation, ce qui doit être interprété avec prudence si chaque read ne couvre qu’une partie de la région codante.

18. LotuS3 — regroupement et assignation#

Les paramètres LotuS3 sont affichés pour toutes les routes sauf PacBio ITS/LSU avec NextITS comme moteur principal.

18.1. Plateforme#

Choix : auto, PacBio, 454, miSeq, hiSeq. En automatique, BarCodeR ne force pas la valeur. Une valeur explicite modifie les stratégies internes et doit rester cohérente avec la technologie et le prétraitement.

18.2. Type d’amplicon#

Choix : SSU, LSU, ITS, ITS1, ITS2, custom. Ce paramètre doit correspondre à la région réellement amplifiée, pas seulement au nom général du projet.

18.3. Groupe taxonomique#

Choix : auto, bacteria, fungi, eukarya. Une valeur explicite oriente certaines décisions taxonomiques. Le mode automatique est préférable si le contexte est hétérogène ou si aucune valeur n’a été validée.

18.4. Regroupement ou débruitage#

Choix : UPARSE, Swarm, CD-HIT, UNOISE, DADA2, VSEARCH. Ces méthodes ne produisent pas nécessairement les mêmes unités biologiques. Elles peuvent modifier le nombre d’unités, leurs abondances, la sensibilité aux séquences rares et le traitement des erreurs. Des résultats issus de méthodes différentes ne doivent pas être considérés comme directement équivalents.

18.5. Outil d’assignation taxonomique#

Choix : RDP classifier, BLAST, Lambda, UTAX, SINTAX, VSEARCH, USEARCH. Le choix modifie l’algorithme, la rapidité, la sensibilité, la gestion des séquences éloignées et les scores disponibles.

18.6. Seuil de confiance RDP#

Visible uniquement avec RDP_classifier. Une valeur élevée produit des assignations plus exigeantes mais davantage de non assignés ; une valeur basse augmente les assignations mais peut réduire leur robustesse.

18.7. Conserver les non classés#

0 ne conserve pas les unités non classées ; 1 les conserve. Les conserver permet d’étudier la diversité inconnue et de réassigner ultérieurement, mais exige une gestion explicite dans les analyses.

18.8. Exclusion taxonomique#

Le motif saisi exclut des taxons. Une expression trop générale peut éliminer de nombreuses assignations. Vérifier le vocabulaire de la base, tester le motif et documenter l’exclusion.

19. Sauvegarde des reads démultiplexés#

Mode Effet
0 Ne pas publier de FASTQ démultiplexés spécifiques
1 Conserver tous les reads démultiplexés non filtrés
2 Conserver les reads démultiplexés puis arrêter le pipeline
3 Conserver les reads démultiplexés filtrés en qualité

Le mode 2 ne doit pas être utilisé lorsqu’un phyloseq ou une analyse complète est attendu. Les modes 1 et 3 augmentent l’espace disque mais facilitent le contrôle et la réutilisation des reads.

20. LCA et assignation avancée#

20.1. Mode d’assignation#

Convention contre-intuitive : 0 active le LCA ; 1 utilise le meilleur hit BLAST.

Le LCA cherche un ancêtre commun partagé par plusieurs hits compatibles et fournit souvent une assignation plus prudente. Le meilleur hit peut être plus précis en apparence mais plus sensible à une référence erronée, une base déséquilibrée ou des hits équivalents.

20.2. Couverture minimale#

Valeur entre 0 et 1. Une couverture élevée exige qu’une grande partie de la séquence soit alignée ; une couverture faible accepte des correspondances partielles. Une forte identité sur une très petite portion n’équivaut pas à une forte identité sur tout l’amplicon.

20.3. Seuils d’identité par rang#

Exemple initial : 97,95,93,91,88,78. Ces seuils ne constituent pas une correspondance universelle entre identité et rang. Le niveau de divergence dépend du marqueur, du groupe, de la base et de la longueur. Les modifier change directement la profondeur taxonomique acceptée.

20.4. Fraction d’accord#

Une valeur élevée exige un consensus plus fort et peut remonter vers un rang supérieur. Une valeur faible accepte une décision avec moins d’accord et peut augmenter les conflits.

20.5. Arbre phylogénétique#

0 : aucun arbre ; 1 : FastTree ; 2 : IQ-TREE 2. La construction ajoute du calcul et nécessite un alignement exploitable. IQ-TREE 2 est généralement plus coûteux.

20.6. Chevauchement maximal des reads#

Ce paramètre concerne principalement les reads courts appariés. Il doit être cohérent avec la longueur des reads, celle de l’amplicon et le chevauchement théorique entre R1 et R2.

21. Route ONT standard#

Contextes : ONT + COI, 16S ou 18S.

Selon les options, la route réalise la validation du design, MiniBar éventuel, la récupération des FASTQ par échantillon, l’orientation, les filtres, la préparation de la correspondance, LotuS3, l’assignation et les rapports.

Pour COI, vérifier la longueur réelle, la présence des amorces, l’organisme cible, la table génétique, le filtre codant et la base. Pour 16S/18S, désactiver normalement le filtre codant, remplacer ou désactiver 658, choisir le type d’amplicon, le groupe et une base compatible.

22. Route ONT IDMABIO#

Contextes : COI-idmabio, 16S-idmabio, 18S-idmabio. Ces options n’apparaissent que sur un cluster reconnu compatible. La route est déclenchée par le suffixe du marqueur, pas par le sélecteur de moteur.

Elle reprend les étapes ONT et ajoute la validation des hits ZOTU, des sorties IDMABIO, des alignements MAFFT et un rapport Word.

22.1. Type de gène#

Choix : auto, codant, non codant. En automatique, COI est traité comme codant et les autres comme non codants. Une valeur forcée remplace cette déduction.

22.2. Hits BLAST conservés#

Définit le nombre maximal de hits conservés. Une valeur élevée augmente l’information, la taille et potentiellement le temps ; une valeur faible peut masquer des hits secondaires utiles.

22.3. Alignements par échantillon#

Détermine combien d’alignements sont présentés dans les sorties. Il ne doit pas être confondu avec le nombre total de hits conservés.

22.4. Langue du rapport#

Choix : français ou anglais. Cette option contrôle le rapport Word produit.

23. Route PacBio avec LotuS3#

Contextes : PacBio + 16S, ou PacBio + ITS/LSU avec LotuS3. MiniBar n’est pas utilisé.

Vérifier que les reads contiennent encore les amorces si l’orientation est activée, que la longueur correspond aux reads, que le filtre codant est désactivé pour 16S/ITS/LSU et que la qualité est adaptée aux reads PacBio corrigés.

Configurer ensuite la plateforme, le type d’amplicon, le groupe, la méthode de regroupement, l’outil taxonomique et les options LCA.

24. Route PacBio avec NextITS#

Disponible uniquement pour PacBio + ITS ou LSU avec moteur NextITS.

La route réalise la validation, les filtres activés, NextITS, ITSx, les corrections et regroupements, la détection de chimères, une assignation LotuS3 dédiée, la génération du phyloseq et les résumés.

24.1. Région ITS#

Choix : ITS1, ITS2, LSU, SSU, ALL. LSU propose LSU et ITS propose initialement ITS1, mais cette suggestion ne valide pas la région réellement amplifiée.

24.2. Groupe ITSx#

Choix : all, fungi, tracheophyta, metazoa. Un groupe trop restreint peut être inadapté à un échantillon environnemental hétérogène.

24.3. Clustering NextITS#

Choix : UNOISE, VSEARCH, Swarm. Le choix modifie le regroupement ou le débruitage. Les résultats de méthodes différentes ne sont pas directement identiques.

24.4. Option UNOISE#

Cette case active une étape de débruitage UNOISE. Elle est distincte du sélecteur général de méthode.

24.5. Correction des homopolymères#

Active le polissage des homopolymères. Cette option modifie les séquences et doit rester homogène entre les runs comparés.

24.6. Base de chimères#

Elle peut être locale ou distante et doit exister, être lisible, avoir le format attendu et correspondre au groupe et à la région. Le chemin initial proposé peut être propre à l’environnement de développement : sélectionner explicitement la base.

24.7. Cohérence des amorces#

La route attend un couple d’amorces cohérent. Des couples différents dans le même run peuvent provoquer une erreur ou un comportement non souhaité.

25. Route Illumina avec LotuS3#

Contextes : Illumina + 16S, ITS ou LSU.

Le design indique un fichier pour une lecture simple ou deux fichiers séparés par une virgule pour une paire. L’orientation est ignorée pour les paires : les amorces ne sont pas retirées par cette étape.

Les filtres de qualité, longueur et codant sont appliqués séparément à R1 et R2, puis les paires sont resynchronisées. Le filtre de longueur ne travaille pas sur un amplicon fusionné. Un read dont le partenaire est éliminé devient orphelin.

Pour 16S/ITS/LSU, désactiver normalement le filtre codant, remplacer ou désactiver 658, vérifier le type d’amplicon, le groupe et la base.

26. Aperçu du design et de la destination#

Les aperçus sont facultatifs et désactivés initialement. L’aperçu design/destination montre le nom du run, un Run ID d’exemple, le design, le futur dossier, les destinations des FASTQ, le chemin du design réécrit, la configuration, la technologie, le marqueur, le type et chemin de base, la partition, les ressources et le cache Singularity.

L’aperçu du design montre le contenu initial ; les chemins ne sont réécrits qu’au lancement.

27. Aperçu de la configuration générée#

Cet aperçu affiche l’overlay Nextflow construit à partir du formulaire : chemins, paramètres activés, valeurs numériques, paramètres LotuS3, IDMABIO, NextITS et dossier Singularity.

Le fichier peut contenir des paramètres d’autres routes ; leur présence ne signifie pas qu’ils seront tous utilisés. nf-schema valide néanmoins les valeurs émises, si bien qu’une valeur invalide peut bloquer le run avant l’exécution.

28. Vérifications avant le lancement#

Contexte#

  • technologie correcte ;
  • marqueur cohérent avec les amorces ;
  • moteur correct ;
  • type de base cohérent avec le FASTA.

FASTQ#

  • tous les fichiers sélectionnés ;
  • aucun nom de base en doublon ;
  • extensions correctes ;
  • ordre R1/R2 correct.

Design#

  • six colonnes obligatoires ;
  • identifiants uniques ;
  • chemins exacts ;
  • amorces en 5’ vers 3’ ;
  • barcodes renseignés si MiniBar ;
  • couples d’amorces cohérents.

Filtres#

  • longueur adaptée ;
  • filtre codant pertinent ;
  • table génétique correcte ;
  • qualité adaptée ;
  • orientation compatible.

Cluster#

  • connexion verte ;
  • dossier accessible ;
  • partition autorisée ;
  • mémoire avec unité ;
  • modules existants ;
  • espace suffisant.

NextITS#

  • base de chimères existante ;
  • région correcte ;
  • groupe ITSx adapté ;
  • amorces cohérentes.

29. Ce qui se passe au lancement#

BarCodeR relit le contexte, vérifie les FASTQ, bloque les doublons de noms, relit et contrôle le design, vérifie les identifiants, la base et la base de chimères, crée un Run ID, crée results/, work/ et meta/, réécrit le design, rassemble les FASTQ, transfère les fichiers, prépare les images, extrait le pipeline, génère la configuration et le script Slurm, écrit les métadonnées, soumet avec sbatch, récupère le Job ID et démarre le suivi.

Si un autre run est suivi dans la session, une confirmation est demandée. La nouvelle soumission n’annule pas automatiquement le précédent.

30. Images Singularity#

OpenMetaBar utilise selon la route des images pour SeqKit, LotuS3, les rapports, MiniBar, MAFFT, phyloseq et NextITS. Elles sont gérées dans <remote_root>/_barcoder_singularity.

L’application tente d’utiliser/copier une image partagée, de préparer ou télécharger l’image manquante, puis de vérifier sa présence et sa taille. Toutes les images ne sont pas requises pour chaque route : MiniBar pour ONT, MAFFT pour IDMABIO, NextITS et l’environnement phyloseq pour NextITS. Une image obligatoire absente bloque le lancement.

31. Lire la chronologie du run#

Les étapes affichées sont : FASTQ sélectionnés, connexion, design prêt, dossier distant, transferts, images Singularity, déploiement du pipeline, soumission sbatch et suivi Slurm.

La chronologie combine des actions locales, des opérations SSH, l’état de la soumission, l’état Slurm et la détection des fichiers. Un état en attente, en cours, en succès, en avertissement ou en erreur doit donc être interprété à l’échelle de l’étape concernée.

32. Comprendre les états Slurm#

PENDING#

Le job attend des ressources. Causes possibles : ressources indisponibles, priorité, partition chargée, mémoire/cœurs élevés, limite de compte ou dépendance. Lire la raison Slurm avant de modifier la configuration.

RUNNING#

Le job est en cours. Une absence temporaire de nouveaux fichiers ne signifie pas nécessairement un blocage.

COMPLETED#

Le script Slurm s’est terminé correctement. Vérifier encore le code de sortie Nextflow, les résultats, le phyloseq et les rapports.

FAILED#

Consulter le journal d’erreur, les sorties Slurm, .nextflow.log, le rapport et l’historique.

OUT_OF_MEMORY#

La mémoire a été dépassée. Identifier si le problème concerne la mémoire globale, un processus, LotuS3, un rapport ou NextITS avant d’augmenter une valeur.

TIMEOUT#

La durée maximale a été atteinte. Choisir une partition adaptée, réduire la complexité ou demander une limite supérieure.

CANCELLED#

Le job a été annulé manuellement, par un administrateur, par une règle ou par une dépendance.

État inconnu ou job absent#

Un job disparu de squeue peut encore avoir un état définitif dans sacct. BarCodeR interroge les deux lorsque possible.

33. Journal d’exécution#

33.1. Opérations locales#

Regroupe les actions de BarCodeR : sélection, validation, connexion, création, transfert, préparation, lancement et détection des fichiers.

33.2. Monitoring#

Regroupe le Job ID, l’état Slurm, la progression détectée, les nouvelles sorties, la fin du calcul et la présence du phyloseq.

33.3. Standard output et standard error#

Ils ne sont pas deux onglets principaux du journal courant, mais restent accessibles dans les détails historiques, les fichiers, l’aperçu d’erreur et les téléchargements.

33.4. .nextflow.log#

Ce fichier détaille les processus, commandes, erreurs, reprises, fichiers de travail et validations. C’est une source principale de diagnostic.

34. Résultats produits#

Selon la route, les résultats peuvent être organisés dans :

  • Steps/files : fichiers préparatoires et entrées publiées ;
  • Steps/demultiplexing_files : démultiplexage et métriques ;
  • Steps/filters : orientation, qualité, longueur, codant et orphelins ;
  • Steps/lotus3 : sorties LotuS3 ;
  • Steps/nextITS : sorties NextITS ;
  • Steps/lotus3_taxo : taxonomie associée à NextITS ;
  • Steps/phyloseq : génération ou stockage du phyloseq NextITS ;
  • Steps/tax_db : base nettoyée et taxonomie extraite ;
  • OMB_logs : résumés, rapports, timeline, trace, graphe, versions et paramètres ;
  • final_table/idmabio_outputs : tables, alignements et rapport IDMABIO.

La structure exacte dépend de la route et des options.

35. Intégrer un objet phyloseq#

BarCodeR recherche des fichiers .rds, .rda ou .RData susceptibles de contenir un phyloseq. La présence d’un nom évocateur ne garantit pas un objet valide.

Lors de l’import, l’application télécharge temporairement le fichier, l’ouvre, recherche les objets phyloseq, contrôle leur compatibilité, propose un choix si nécessaire et ajoute l’objet retenu.

Un nom unique est construit à partir du run, du fichier et éventuellement de l’objet. Les paramètres du run peuvent être associés à l’objet pour conserver la provenance.

Un phyloseq peut être détecté malgré un run en échec. Il peut être partiel ou avoir été produit avant l’étape fautive. Examiner les logs et le contenu avant utilisation.

36. Actions proposées après la soumission#

36.1. Relancer en ajustant#

Conserve les fichiers et paramètres, permet les modifications et prépare une nouvelle soumission. Le run précédent n’est pas annulé.

36.2. Nouvelle analyse — repartir de zéro#

Réinitialise les fichiers, le contexte, les paramètres d’analyse et la chronologie. Conserve la connexion et plusieurs réglages cluster. Le job déjà soumis continue et reste dans l’historique.

36.3. Ne pas relancer#

Ferme le panneau sans annuler ni modifier le suivi. Il peut être rouvert ultérieurement.

37. Historique des analyses#

Le scan parcourt les runs présents sous le dossier racine. Le résultat dépend du chemin, des droits, des métadonnées, des fichiers et de Slurm.

L’historique peut afficher Run ID, dossier, Job ID, état, dates, durée, nombre de FASTQ et d’échantillons, taille, mémoire, CPU, phyloseq et nettoyage.

37.1. Détails et reprise du suivi#

Les détails montrent paramètres, chemins, codes de sortie, informations Slurm, fichiers et erreurs. Reprendre le suivi reconnecte l’interface au run sans relancer le calcul.

37.2. Parcourir les fichiers#

Permet la recherche, l’ouverture de groupes, l’aperçu des 200 dernières lignes de fichiers texte, le téléchargement et l’import d’un phyloseq.

37.3. Annuler un job#

Utilise Slurm pour annuler le job principal et des enfants identifiables. Le dossier et les fichiers déjà produits restent présents.

37.4. Nettoyer un run#

Supprime les intermédiaires en conservant normalement results/ et meta/. Cette action irréversible libère de l’espace mais supprime le cache de reprise et les éléments de diagnostic.

37.5. Supprimer un run#

Supprime tout le dossier distant, y compris résultats, métadonnées, logs, intermédiaires et phyloseq. Sauvegarder les fichiers nécessaires avant.

Contexte#

  • FASTQ correctement référencés.
  • Barcodes et amorces corrects.
  • Couples d’amorces cohérents.

Paramètres#

  • Tolérances justifiées.
  • Orientation compatible.
  • Longueur adaptée et champ non vide si actif.
  • Qualité adaptée.
  • Filtre codant et table génétique pertinents.
  • Type d’amplicon et groupe corrects.
  • Méthode de regroupement et mode taxonomique documentés.

  • Région, groupe ITSx et base de chimères corrects.

  • Connexion verte.
  • Racine accessible.
  • Partition correcte.
  • Mémoire avec unité et cœurs réalistes.

  • Nom explicite.
  • Aperçu du design vérifié.
  • Configuration générée vérifiée.
  • Paramètres conservés avec le projet.

40. Principes d’interprétation et de reproductibilité#

Les résultats dépendent simultanément des fichiers bruts, du démultiplexage, des amorces, des filtres, de la méthode de regroupement, de la base, de l’algorithme taxonomique et des seuils. Deux runs utilisant des paramètres différents ne doivent pas être comparés sans tenir compte de ces différences.

Pour garantir la reproductibilité :

  • conserver le design file ;
  • conserver la base ou sa version ;
  • conserver les paramètres ;
  • conserver les rapports Nextflow ;
  • documenter toute modification des valeurs initiales ;
  • conserver les versions des outils ;
  • conserver les métriques de chaque étape ;
  • ne pas interpréter uniquement le phyloseq final.
