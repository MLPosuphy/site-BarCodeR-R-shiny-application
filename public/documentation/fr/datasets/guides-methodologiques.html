Datasets — Guides méthodologiques

1. Présentation générale#

L’onglet Datasets centralise la gestion des données déjà présentes dans BarCodeR.

Il permet de gérer deux niveaux distincts.

Niveau 1 — Les datasets#

Un dataset correspond à un objet phyloseq chargé dans la session actuelle.

L’onglet permet notamment de :

  • choisir le dataset actif ;
  • consulter la liste des datasets en mémoire ;
  • renommer un dataset ;
  • ajouter une note ou des tags ;
  • dupliquer un dataset ;
  • modifier son ordre dans la liste ;
  • exporter un dataset ;
  • supprimer un dataset de la mémoire.

Niveau 2 — Les projets#

Un projet BarCodeR correspond à un espace de travail enregistré sur le disque.

Il peut contenir :

  • les datasets ;
  • le dataset actif ;
  • l’état de navigation de l’application ;
  • certains paramètres d’interface ;
  • les historiques de figures ;
  • les fichiers produits et sauvegardés par les différents modules.

L’onglet permet notamment de :

  • sauvegarder le projet courant ;
  • recharger sa dernière sauvegarde ;
  • créer plusieurs projets ;
  • passer d’un projet à un autre ;
  • renommer un projet ;
  • dupliquer un projet complet ;
  • exporter un projet ;
  • importer un projet ;
  • supprimer un projet.

2. Définitions indispensables#

2.1. Dataset#

Dans BarCodeR, un dataset est un élément nommé de la liste réactive :

datasets()

Chaque élément est normalement un objet phyloseq.

datasets <- list(
  COI = ps_coi,
  `16S` = ps_16s,
  COI_filtered = ps_coi_filtered
)

Le nom du dataset sert à l’identifier dans toute l’application.

2.2. Dataset actif#

Le dataset actif est enregistré séparément dans :

active_ds()

Il désigne le dataset utilisé par défaut dans les autres onglets.

active_ds <- "COI"

Le dataset actif n’est pas une copie supplémentaire. Il s’agit uniquement du nom de l’objet actuellement sélectionné comme référence globale.

2.3. Registre des datasets#

Le registre correspond à l’ensemble des datasets présents en mémoire, avec leur nom, leur ordre, leurs attributs et le dataset actif.

Il ne correspond pas automatiquement à ce qui est enregistré sur le disque.

2.4. Session#

La session correspond à l’état actuel de l’application dans le navigateur.

Une modification effectuée dans le registre agit d’abord sur cette session. Tant que le projet n’a pas été sauvegardé, fermer l’application ou recharger une ancienne sauvegarde peut faire perdre ces modifications.

2.5. Projet#

Un projet est un dossier persistant situé dans l’arborescence de BarCodeR :

save/projects/<identifiant-interne-du-projet>/

Ce dossier peut contenir :

registry.rds
manifest.rds
ui_state.rds
barplot/
alpha_div/
venn_diag/
heat_tree/
tax_quality/
phylo_tree/
Ordination/
DAA/
Analyse/
multiview/
...

Le contenu exact dépend des modules utilisés.

3. Différence entre dataset et projet#

Action Dataset Projet
Contient un objet phyloseq Oui Oui, éventuellement plusieurs
Possède un nom dans l’application Oui Oui
Peut être actif Oui Oui, comme projet courant
Peut être dupliqué Oui Oui
Peut être exporté seul Oui Non applicable
Contient les historiques de figures Non Oui
Contient plusieurs datasets Non Oui
Est stocké automatiquement sur le disque Non Partiellement selon les modules
Nécessite une sauvegarde du registre Oui Oui
Peut être supprimé uniquement de la mémoire Oui Non
Peut être supprimé physiquement du disque Non depuis l’action dataset Oui

Une suppression de dataset et une suppression de projet sont donc deux opérations complètement différentes.

4. Organisation de l’onglet#

L’onglet contient trois grandes zones :

  1. Dataset actif global ;
  2. Registre des datasets ;
  3. Projets.

Chaque zone répond à un besoin différent.

5. Dataset actif global#

5.1. Rôle du sélecteur#

La première carte contient le sélecteur Dataset actif.

Le dataset sélectionné devient le dataset de travail par défaut de l’ensemble de l’application. Il est notamment utilisé par défaut dans Description, Data Edition, Filtration, Exploration et Analyse.

5.2. Synchronisation avec l’application#

Le sélecteur est synchronisé avec le dataset actif global, le sélecteur disponible dans la barre latérale de contrôle et les autres composants liés à active_ds().

Changer le dataset actif dans Datasets le change également dans les autres sélecteurs globaux.

5.3. Sélections locales dans les modules#

Certains modules permettent de choisir localement un autre dataset.

Dans ce cas :

  • le dataset actif reste la référence globale ;
  • le module peut temporairement utiliser un autre dataset ;
  • selon le module, la sélection locale peut ou non modifier active_ds().

Il faut donc toujours vérifier le dataset indiqué dans le module avant de lancer une opération.

5.4. Effets du changement de dataset actif#

Changer le dataset actif :

  • ne modifie aucune abondance ;
  • ne filtre aucune donnée ;
  • ne copie aucun objet ;
  • ne supprime aucun objet ;
  • modifie uniquement la référence globale utilisée par l’application.

Cette modification marque néanmoins la session comme ayant des changements non sauvegardés, car le choix du dataset actif est enregistré dans le projet.

6. Aucun dataset en mémoire#

Lorsque la session ne contient aucun dataset, le registre affiche qu’aucun dataset n’est en mémoire.

Les principales méthodes pour obtenir un dataset sont alors :

  • importer un objet avec Input data ;
  • récupérer un objet produit par OpenMetaBar ;
  • ouvrir un projet déjà enregistré ;
  • importer une archive de projet ;
  • restaurer une sauvegarde existante.

7. Le registre des datasets#

Le registre présente une ligne par dataset présent dans la mémoire de la session.

Il ne scanne pas directement les fichiers du disque. Les informations sont calculées à partir des objets actuellement présents dans :

datasets()

8. Colonnes du registre#

8.1. État actif#

Une étoile indique le dataset actif. Un cercle indique un dataset présent mais non actif.

L’étoile ne fournit aucune information sur la qualité du dataset, son niveau de filtration, sa date ou son statut de sauvegarde.

8.2. Nom#

Le nom est la clé utilisée dans la liste datasets().

Ce nom est utilisé dans les sélecteurs, les rapports, les exports, les historiques, la provenance des datasets filtrés, certaines légendes et certains noms de fichiers.

8.3. ASV#

La colonne ASV affiche en réalité la valeur retournée par :

phyloseq::ntaxa()

Il s’agit donc du nombre de taxons de l’objet.

Selon la méthode ayant produit le dataset, ces unités peuvent correspondre à des ASV, des OTU, des ZOTU ou d’autres unités taxonomiques ou séquentielles. L’intitulé « ASV » ne garantit pas la nature exacte des unités.

8.4. Échantillons#

La colonne affiche la valeur retournée par :

phyloseq::nsamples()

Elle représente le nombre d’échantillons présents dans l’objet au moment de l’affichage.

8.5. Provenance#

Trois provenances principales sont affichées.

Chargé

Le dataset ne possède pas d’attribut indiquant qu’il provient d’OpenMetaBar ou d’une filtration.

Il peut notamment avoir été chargé avec Input data, construit dans R, importé depuis un projet ou dupliqué à partir d’un dataset chargé.

OpenMetaBar

Le dataset possède l’attribut :

openmetabar_run

Il a donc été intégré depuis un run OpenMetaBar, ou est une copie d’un objet conservant cet attribut.

Filtré

Le dataset possède un filtration_log contenant un parent nommé.

La provenance Filtré est prioritaire sur OpenMetaBar. Un objet produit par OpenMetaBar puis filtré est donc affiché comme Filtré.

8.6. Parent#

La colonne Parent affiche le nom du dataset d’origine enregistré dans :

filtration_log$parent_dataset

Il s’agit d’un nom enregistré dans un attribut, pas d’un lien dynamique entre deux objets.

Si le parent est renommé depuis Datasets, BarCodeR met à jour ce nom dans les descendants reconnus. Si le parent est supprimé, le nom du parent est effacé dans les descendants concernés.

8.7. Note et tags#

La note et les tags sont lus dans l’attribut :

dataset_meta

Structure attendue :

list(
  note = "...",
  tags = c("tag1", "tag2")
)

Les notes et les tags font partie de l’objet phyloseq en mémoire. Ils sont donc inclus lors de l’export du dataset, de la sauvegarde du projet, de la duplication du dataset et de l’export du projet.

8.8. Modifié#

La date affichée est recherchée dans cet ordre :

  1. dernière entrée de edit_log ;
  2. date de filtration_log.

Elle ne représente pas nécessairement la dernière modification effectuée dans Datasets.

Les actions suivantes ne mettent pas directement à jour cette date : changement du nom, modification de la note, modification des tags, changement d’ordre et changement de dataset actif.

Une date ancienne ou absente ne signifie donc pas nécessairement que le dataset n’a jamais été manipulé.

8.9. Actions#

Chaque ligne contient les actions suivantes :

  • définir comme actif ;
  • modifier ;
  • dupliquer ;
  • exporter ;
  • monter ;
  • descendre ;
  • supprimer.

9. Rafraîchir le registre#

Le bouton Rafraîchir force le recalcul visuel du registre.

Il peut actualiser les nombres d’échantillons et de taxons, les attributs, les notes, les tags, la provenance et les dates affichées.

Il ne réalise pas une lecture de registry.rds, un scan des projets, un rechargement depuis le disque ou une restauration des données.

Pour recharger la sauvegarde du projet courant, utiliser Recharger depuis le disque.

10. Définir un dataset comme actif#

Cliquer sur l’étoile de la ligne définit immédiatement ce dataset comme actif.

Cette action :

  • met à jour active_ds() ;
  • synchronise le sélecteur global ;
  • modifie la référence utilisée dans les autres onglets ;
  • marque le projet comme modifié.

Elle ne sauvegarde pas automatiquement le choix sur le disque. Pour conserver ce choix au prochain démarrage, sauvegarder le projet.

11. Modifier un dataset#

Le bouton de modification ouvre une fenêtre contenant le nom du dataset, une note libre et des tags.

12. Renommer un dataset#

12.1. Nettoyage du nom#

Le nom est traité par la fonction commune :

bcr_clean_label()

Elle supprime les espaces externes, remplace certains caractères non autorisés par _, supprime les _ situés aux extrémités et utilise dataset si le résultat est vide.

Nom saisi Nom obtenu
COI brut COI_brut
COI / brut COI_brut
16S 16S
*** dataset

12.2. Caractères non ASCII#

Le nettoyage repose sur la classe locale [:alnum:]. Il ne garantit donc pas un nom entièrement ASCII.

Selon la configuration de R, des caractères accentués, chinois ou hindi peuvent être conservés.

Pour maximiser la portabilité entre systèmes, il est préférable d’utiliser des lettres ASCII, des chiffres, _ et -.

12.3. Collision de noms#

Si le nom existe déjà, un suffixe est ajouté.

COI
COI_2
COI_3

Le dataset existant n’est pas écrasé.

12.4. Mise à jour du dataset actif#

Si le dataset renommé était actif, son nouveau nom devient automatiquement la valeur de active_ds().

12.5. Mise à jour des descendants filtrés#

Si d’autres datasets déclarent le dataset renommé comme parent dans leur filtration_log, BarCodeR remplace l’ancien nom du parent par le nouveau.

Avant :
COI
└── COI_filtered, parent = COI

Après renommage de COI en COI_raw :
COI_raw
└── COI_filtered, parent = COI_raw

12.6. Ce qui n’est pas renommé#

Renommer un dataset dans le registre ne renomme pas automatiquement les fichiers précédemment exportés, le fichier RDS d’origine, les anciennes figures, les textes déjà intégrés dans d’anciens rapports, le nom du projet ou le slug interne du projet.

13. Ajouter une note#

La note est un texte libre associé au dataset.

Elle peut servir à enregistrer le traitement réalisé, une particularité du dataset, un contrôle à effectuer, la version d’une base, un statut de validation ou une restriction d’utilisation.

La note est débarrassée de ses espaces externes. Elle est stockée dans l’objet et non dans une base externe.

Modifier la note ne modifie pas directement la colonne Modifié du registre.

14. Ajouter des tags#

Les tags sont saisis sous forme de texte séparé par des virgules.

COI, PacBio, filtré, publication

Après traitement, ils deviennent :

c("COI", "PacBio", "filtré", "publication")

Les espaces externes sont supprimés. Les valeurs vides sont ignorées.

14.1. Limites des tags#

Dans l’implémentation actuelle :

  • les doublons ne sont pas supprimés automatiquement ;
  • la casse est conservée ;
  • une virgule ne peut pas faire partie d’un tag ;
  • aucun vocabulaire contrôlé n’est imposé.

Ainsi, COI, coi et Coi restent différents. Il est conseillé de définir une convention homogène.

15. Attribut dataset_meta#

Lors de l’enregistrement de la modification, BarCodeR remplace l’attribut dataset_meta par une liste contenant uniquement :

list(
  note = note,
  tags = tags
)

Si un objet externe utilisait déjà dataset_meta pour stocker d’autres informations personnalisées, ces champs supplémentaires peuvent être remplacés.

Les informations métier importantes ne devraient donc pas être stockées dans cet attribut sans tenir compte de ce comportement.

16. Dupliquer un dataset#

Le bouton Dupliquer crée une nouvelle entrée dans datasets().

16.1. Nom proposé#

Le nom initial proposé est :

<nom>_copie

En cas de collision, un suffixe est ajouté.

16.2. Contenu de la copie#

La copie reprend l’objet entier au moment de la duplication : OTU table, metadata, taxonomie, séquences, arbre, logs, provenance, note, tags et autres attributs.

16.3. Dataset actif#

La copie devient automatiquement le dataset actif.

16.4. Indépendance ultérieure#

La copie commence avec le même contenu que la source. Les modifications ultérieures appliquées à l’un des objets dans BarCodeR sont ensuite enregistrées dans l’entrée sélectionnée du registre.

16.5. Provenance de la copie#

La duplication ne crée pas une nouvelle provenance spécifique « Copie ».

La copie conserve les attributs de la source : la copie d’un dataset OpenMetaBar reste affichée comme OpenMetaBar, la copie d’un dataset filtré conserve son parent et la copie d’un dataset chargé reste affichée comme Chargé.

La source de la duplication n’est pas enregistrée séparément comme parent.

17. Modifier l’ordre des datasets#

Les flèches vers le haut et vers le bas modifient l’ordre des éléments dans la liste datasets().

La première ligne ne peut pas être montée. La dernière ligne ne peut pas être descendue.

17.1. Effets de l’ordre#

L’ordre peut influencer l’affichage du registre, l’ordre des sélecteurs, l’ordre de certains traitements multi-datasets, le dataset choisi par défaut lorsqu’aucun actif valide n’est disponible et le premier dataset sélectionné après certaines suppressions ou restaurations.

17.2. Persistance#

Le nouvel ordre reste uniquement en mémoire tant que le projet n’est pas sauvegardé.

18. Exporter un dataset individuel#

Le bouton d’export d’une ligne enregistre directement l’objet phyloseq correspondant.

Le fichier produit suit une structure proche de :

dataset_<nom>_<date-heure>.rds

18.1. Contenu#

L’export contient l’objet actuel en mémoire, avec ses tables, séquences, arbre, attributs, notes, tags, logs et provenance.

18.2. Éléments non contenus#

L’export individuel ne contient pas les autres datasets, le nom du projet, le dataset actif global, les figures du projet, les historiques des modules, les FASTQ d’origine, les fichiers du cluster OpenMetaBar ou la base taxonomique originale.

18.3. Réimportation#

Le fichier peut être réimporté avec Input data.

19. Supprimer un dataset de la session#

Le bouton de suppression retire le dataset de la liste en mémoire. La fenêtre rappelle qu’aucun fichier disque n’est modifié.

19.1. Effets immédiats#

Après confirmation :

  • le dataset disparaît de datasets() ;
  • il disparaît des sélecteurs ;
  • il ne peut plus être utilisé par les modules dans la session ;
  • le projet est marqué comme modifié.

19.2. Dataset actif supprimé#

Si le dataset supprimé était actif, le premier dataset restant devient actif, ou active_ds() devient vide si aucun dataset ne reste.

19.3. Parent d’un dataset filtré#

Si le dataset supprimé est déclaré comme parent par des datasets filtrés, leur champ parent_dataset est vidé.

La détection de la provenance Filtré exige actuellement un parent non vide. Après la suppression du parent, un descendant peut donc ne plus être affiché comme Filtré : il peut redevenir OpenMetaBar s’il possède aussi cet attribut, sinon apparaître comme Chargé.

19.4. Suppression en mémoire uniquement#

La sauvegarde précédente du projet n’est pas immédiatement modifiée.

Tant que le projet n’est pas sauvegardé, recharger depuis le disque peut faire réapparaître le dataset, fermer sans enregistrer peut annuler la suppression et ouvrir un autre projet peut déclencher une tentative de sauvegarde.

19.5. Rendre la suppression persistante#

Pour enregistrer la suppression dans le projet courant :

  1. supprimer le dataset ;
  2. vérifier le registre ;
  3. cliquer sur Sauvegarder le projet.

19.6. Supprimer le dernier dataset#

Après suppression du dernier dataset, la mémoire devient vide.

Cependant, la fonction de sauvegarde rapide refuse actuellement de sauvegarder un projet sans aucun dataset. Une ancienne sauvegarde non vide peut donc rester présente sur le disque.

Pour obtenir un espace de travail réellement vide et persistant, il est généralement plus clair de créer un nouveau projet.

20. État « modifications non enregistrées »#

BarCodeR maintient un indicateur global de modification du projet.

Cet indicateur devient actif lorsque la liste datasets() change ou lorsque le dataset actif change.

Exemples : import d’un dataset, création d’un dataset filtré, duplication, renommage, modification de note ou tags, changement d’ordre, suppression et changement du dataset actif.

20.1. Portée réelle de l’indicateur#

L’indicateur suit principalement le registre des datasets et le dataset actif.

Il ne constitue pas nécessairement un suivi exhaustif de tout ce qui existe dans le projet. Certaines figures sont enregistrées directement dans leur historique, certains paramètres d’interface ne déclenchent pas forcément l’état modifié et une modification saisie dans une fenêtre mais non confirmée n’est pas enregistrée.

L’indication « projet enregistré » signifie surtout que le registre en mémoire correspond à la dernière sauvegarde connue.

21. Section Projets#

La section Projets gère les espaces de travail persistants.

Elle comprend le nom du projet courant, la sauvegarde, la création d’un projet, la restauration, les exports, l’import et la liste des projets disponibles.

22. Projet courant#

Le projet courant est le projet dans lequel les opérations persistantes sont enregistrées.

BarCodeR conserve son identifiant dans :

save/projects/.current

Au prochain démarrage, l’application tente de rouvrir ce projet.

Si le projet pointé n’existe plus, BarCodeR revient au projet par défaut :

sans-titre

23. Nom visible et identifiant interne du projet#

Un projet possède un nom visible, un identifiant interne ou slug, et un dossier sur le disque.

Nom visible : Étude sol 2024
Slug : etude-sol-2024
Dossier : save/projects/etude-sol-2024/

23.1. Construction du slug#

Le slug est en minuscules, limité à des caractères ASCII, sécurisé pour un chemin, limité à 80 caractères et rendu unique.

Nom du projet Slug possible
Étude sol 2024 etude-sol-2024
Projet COI projet-coi
nom uniquement chinois projet-<empreinte>

23.2. Renommage ultérieur#

Renommer un projet modifie uniquement son nom visible.

Le slug et le dossier restent inchangés. Cela évite de casser les chemins déjà utilisés par les modules.

24. Structure d’un projet sur le disque#

Un projet est stocké sous :

save/projects/<slug>/

24.1. registry.rds#

Contient :

list(
  version = 2,
  format = "version_ok_project",
  saved_at = ...,
  datasets = ...,
  active_ds = ...
)

Il représente la dernière sauvegarde explicite du registre.

24.2. manifest.rds#

Contient notamment le nom visible, la date de création, la date de modification et le nombre de datasets enregistré.

Il permet d’afficher rapidement la liste des projets sans relire systématiquement tous les objets phyloseq.

24.3. ui_state.rds#

Peut contenir l’onglet principal, certains sous-onglets et certains paramètres d’interface.

La restauration de ces éléments dépend des réglages de l’application et des modules.

24.4. Dossiers des modules#

Les modules peuvent enregistrer leurs historiques dans des sous-dossiers, par exemple :

barplot/
alpha_div/
venn_diag/
heat_tree/
tax_quality/
phylo_tree/
Ordination/
DAA/
Analyse/
multiview/

Les fichiers peuvent inclure des images, des objets R, des paramètres, des métadonnées de figure et des exports intermédiaires.

25. Ce qu’un projet ne contient pas automatiquement#

Un projet BarCodeR ne constitue pas une copie automatique de tous les fichiers ayant servi à l’analyse.

Il ne contient pas nécessairement les FASTQ originaux, les fichiers BAM, les fichiers FASTA de référence, la base taxonomique, les fichiers de design OpenMetaBar, les résultats distants du cluster, les scripts externes, les fichiers importés avant leur conversion en phyloseq ou les bases de données utilisées par les outils.

Ces éléments doivent être archivés séparément.

Un phyloseq peut conserver certaines informations dans ses attributs, mais cela ne remplace pas l’archivage des fichiers sources.

26. Sauvegarder le projet#

Le bouton Sauvegarder le projet enregistre l’état courant du registre dans le projet ouvert.

26.1. Éléments sauvegardés#

L’opération enregistre principalement :

  • la liste des datasets ;
  • leur ordre ;
  • leurs objets complets ;
  • leurs attributs ;
  • le dataset actif ;
  • le nombre de datasets dans le manifeste ;
  • l’état de navigation disponible ;
  • certains paramètres d’interface.

26.2. Historiques de figures#

Les historiques de figures sont généralement enregistrés directement par les modules dans le dossier du projet.

Le bouton de sauvegarde ne recalcule pas ces figures. Il permet surtout de synchroniser le registre des datasets avec le disque.

26.3. Projet vide#

Le bouton refuse la sauvegarde si aucun dataset n’est présent.

26.4. Protection contre l’écrasement par une mémoire vide#

Une protection supplémentaire empêche d’écraser une sauvegarde non vide par une mémoire vide.

Cette situation peut se produire si registry.rds est devenu illisible, si l’application s’est ouverte sans pouvoir charger les données, ou si une opération essaie ensuite de sauvegarder automatiquement.

Dans ce cas, BarCodeR refuse l’écriture afin de préserver le fichier existant.

26.5. Succès#

Après une sauvegarde réussie :

  • le registre sur le disque correspond à la mémoire ;
  • l’état « modifications non enregistrées » est retiré ;
  • la date du projet est actualisée ;
  • le nombre de datasets du manifeste est mis à jour.

27. Sauvegarde disponible#

Sous les boutons, BarCodeR indique si une sauvegarde rapide existe et affiche sa dernière date d’écriture.

Cette date correspond à la date de modification du fichier registry.rds.

Elle ne représente pas nécessairement la dernière figure produite, la dernière analyse exécutée, la dernière modification d’un fichier d’historique ou la dernière action effectuée dans l’application.

28. Recharger depuis le disque#

Le bouton Recharger depuis le disque relit le fichier registry.rds du projet courant.

28.1. Conséquence#

La restauration remplace tous les datasets actuellement en mémoire par ceux de la sauvegarde.

Elle ne réalise pas une fusion.

28.2. Données perdues#

Les modifications non sauvegardées peuvent être perdues : nouveaux datasets, renommages, suppressions, duplications, modifications des tables, filtrations non sauvegardées, notes et tags, ordre des datasets et changement de dataset actif.

28.3. Dataset actif restauré#

Le dataset actif enregistré dans registry.rds est restauré.

S’il n’existe plus dans la liste sauvegardée, le premier dataset devient actif.

28.4. État sauvegardé#

Après restauration, la mémoire est considérée comme identique à la sauvegarde. Le voyant de modifications non enregistrées est donc réinitialisé.

28.5. Ce que la restauration ne fait pas#

Cette action ne recharge pas entièrement la page, ne change pas de projet, ne fusionne pas les datasets, ne réimporte pas une archive, ne restaure pas nécessairement immédiatement tous les paramètres d’interface et ne supprime pas les historiques déjà présents sur le disque.

29. Sauvegarde introuvable#

Si aucun registry.rds n’existe pour le projet courant, BarCodeR indique qu’aucune sauvegarde rapide n’a été trouvée.

Cela peut correspondre à un nouveau projet, un projet contenant uniquement des figures, un projet jamais sauvegardé, un fichier supprimé manuellement ou une importation partielle.

30. Sauvegarde illisible#

Si registry.rds existe mais ne peut pas être lu, BarCodeR peut ouvrir le projet avec une mémoire vide et afficher un avertissement persistant.

Cette situation peut être causée par un fichier corrompu, une écriture interrompue, un problème de disque, une incompatibilité R, une classe indisponible ou une copie incomplète.

30.1. Protection appliquée#

BarCodeR évite alors d’écraser silencieusement le fichier illisible avec une liste vide. La sauvegarde d’une mémoire vide est refusée.

30.2. Conduite à tenir#

  • ne pas supprimer immédiatement registry.rds ;
  • faire une copie du dossier du projet ;
  • essayer de lire le fichier dans R ;
  • vérifier les sauvegardes externes ;
  • importer une archive antérieure ;
  • charger un dataset valide avant de décider d’écraser la sauvegarde.

31. Exporter les données seules en .rds#

Le bouton Exporter les données seules, sans les figures (.rds) produit un fichier contenant la liste actuelle des datasets en mémoire, le dataset actif, la date d’export et la version du format.

list(
  version = 2,
  format = "version_ok_project",
  saved_at = Sys.time(),
  datasets = datasets(),
  active_ds = active_ds()
)

31.1. Différence avec la sauvegarde rapide#

L’export .rds est téléchargé sur le poste de l’utilisateur.

La sauvegarde rapide est écrite dans le dossier interne du projet sur la machine exécutant BarCodeR.

31.2. Contenu exclu#

L’export .rds ne contient pas les figures, les historiques, les fichiers propres aux modules, le manifeste, le nom visible du projet, l’état de navigation, les paramètres d’interface ou les fichiers sources externes.

31.3. Réimportation#

Ce fichier peut être chargé depuis Input data. Il ajoute ou remplace alors les datasets dans le projet courant.

32. Exporter le projet complet en .zip#

Le bouton Exporter le projet (.zip) archive l’ensemble du dossier du projet courant.

32.1. Contenu potentiel#

L’archive peut contenir registry.rds, manifest.rds, ui_state.rds, les historiques des figures, les exports internes des modules et les fichiers présents dans les sous-dossiers du projet.

32.2. Sauvegarde avant export#

Avant de créer l’archive, BarCodeR tente de sauvegarder le registre actuellement en mémoire.

L’objectif est que l’archive contienne les dernières modifications.

32.3. Échec de la sauvegarde préalable#

Si cette sauvegarde échoue ou est refusée, une erreur est signalée, mais l’export peut néanmoins continuer.

L’archive peut alors contenir la dernière version valide déjà présente dans registry.rds, et non l’état actuel de la mémoire.

Il faut donc lire les notifications avant de considérer l’archive comme à jour.

32.4. Projet vide#

L’export échoue si le dossier du projet n’existe pas ou ne contient aucun élément à archiver.

32.5. Nom du fichier#

Le fichier suit une structure proche de :

projet_<nom-normalisé>_<date-heure>.zip

33. Avertissement de taille#

BarCodeR affiche un avertissement lorsque le projet dépasse :

200 Mo

Cette taille inclut les figures et l’ensemble des fichiers du projet.

Le message indique que l’export peut être long, lourd à télécharger et difficile à partager.

33.1. Taille calculée#

La taille correspond à la somme des fichiers présents dans le dossier du projet.

Elle peut inclure de nombreuses images, des objets R volumineux, des exports multiples et des historiques anciens.

33.2. Actualisation#

Le calcul de taille est temporairement mis en cache pour éviter de reparcourir continuellement tous les fichiers.

Une modification récente peut donc mettre quelques secondes à apparaître.

33.3. Limite d’import#

La limite globale de téléversement de BarCodeR est actuellement de :

500 Mo

Une archive supérieure à 500 Mo peut être exportée, mais ne pourra normalement pas être réimportée par le sélecteur de fichiers sans modifier cette limite.

Pour les projets très volumineux : nettoyer les historiques inutiles, conserver une archive directement sur le serveur, copier manuellement le dossier du projet ou augmenter la limite dans un environnement contrôlé.

34. Importer un projet .zip#

Le champ Importer un projet (.zip) permet de charger une archive de projet complète.

34.1. Import dans un nouveau projet#

L’archive n’est jamais fusionnée avec le projet courant.

Elle est extraite dans un nouveau dossier de projet. Le projet courant reste ouvert.

Après l’import, il faut sélectionner le nouveau projet dans la liste puis cliquer sur Ouvrir.

34.2. Détection du projet#

BarCodeR recherche notamment registry.rds, manifest.rds et des dossiers d’historique connus.

L’archive peut contenir les fichiers directement à sa racine ou dans un dossier parent unique.

34.3. Nom du projet importé#

Le nom est lu dans manifest.rds lorsqu’il est disponible. Sinon, le nom utilisé est Projet importé.

34.4. Collision de noms#

Si un projet porte déjà le même nom, un suffixe est ajouté.

34.5. Projet sans registre#

Une archive contenant uniquement des dossiers d’historique reconnus peut être acceptée comme projet, même sans registry.rds.

Elle peut donc apparaître dans la liste avec zéro dataset.

34.6. Archive invalide#

L’import est refusé si le ZIP est illisible, si aucun contenu n’est extrait, si aucun marqueur de projet n’est trouvé, si la copie vers le dossier final échoue, si les permissions sont insuffisantes ou si le disque est plein.

35. Créer un nouveau projet#

Le bouton Nouveau projet ouvre une fenêtre demandant un nom.

35.1. Fonctionnement#

Après confirmation :

  1. un dossier de projet vide est créé ;
  2. le projet courant fait l’objet d’une tentative de sauvegarde ;
  3. le nouveau projet est défini comme projet courant ;
  4. la page est entièrement rechargée ;
  5. l’application revient dans l’onglet Datasets.

35.2. Nom obligatoire#

Un nom vide est refusé.

35.3. Nom déjà utilisé#

Deux projets ne peuvent pas avoir le même nom visible, sans distinction de casse ni d’espaces externes.

35.4. Projet initialement vide#

Le nouveau projet contient d’abord son dossier et son manifeste. Il ne possède pas encore nécessairement de registry.rds.

35.5. Vérification avant création#

Avant de changer de projet :

  • sauvegarder explicitement le projet courant ;
  • vérifier l’absence d’erreur ;
  • exporter les données importantes ;
  • fermer les autres onglets BarCodeR ouverts.

36. Ouvrir un autre projet#

Cliquer sur Ouvrir déclenche un changement complet de projet.

36.1. Étapes#

BarCodeR :

  1. tente de sauvegarder le projet courant ;
  2. écrit le nouvel identifiant dans .current ;
  3. mémorise que l’ouverture provient du gestionnaire de projets ;
  4. recharge entièrement la session ;
  5. initialise les modules sous le nouveau projet ;
  6. recharge le registre du nouveau projet ;
  7. revient sur l’onglet Datasets.

36.2. Pourquoi la page est rechargée#

De nombreux modules enregistrent leurs historiques dans un dossier calculé lors de leur initialisation.

Le rechargement complet garantit que les figures vont dans le bon projet, que les historiques lus sont ceux du bon projet, que les chemins des modules sont recalculés et que les ressources statiques sont reliées au bon dossier.

36.3. Échec de sauvegarde du projet courant#

Dans l’implémentation actuelle, l’ouverture du nouveau projet peut continuer même si la sauvegarde du projet courant a signalé une erreur.

Une notification rouge ne doit donc pas être ignorée.

Si la sauvegarde échoue, ne pas supposer que les modifications en mémoire sont conservées : réouvrir le projet précédent, vérifier son registre et restaurer un export si nécessaire.

37. Plusieurs onglets BarCodeR ouverts#

Le projet courant est partagé au niveau du processus R.

Si plusieurs onglets ou sessions utilisent la même instance, changer de projet dans l’un peut perturber les chemins utilisés par les autres.

BarCodeR détecte les autres sessions connues et affiche un avertissement.

37.1. Risque#

Les autres onglets peuvent continuer à afficher l’ancien projet, conserver des chemins initialisés pour l’ancien projet, enregistrer des figures dans un projet inattendu ou mélanger des états provenant de projets différents.

37.2. Recommandation#

Avant de changer de projet :

  1. sauvegarder ;
  2. fermer les autres onglets BarCodeR ;
  3. vérifier qu’aucun calcul n’est en cours ;
  4. ouvrir le projet cible depuis une seule session.

Le bouton Changer quand même doit rester exceptionnel.

38. Renommer le projet courant#

Le bouton Renommer change le nom visible du projet.

38.1. Ce qui change#

  • le nom affiché dans Datasets ;
  • le nom du manifeste ;
  • le nom utilisé pour les futurs exports.

38.2. Ce qui ne change pas#

  • le slug ;
  • le chemin du dossier ;
  • les chemins d’historique ;
  • le contenu du projet ;
  • les datasets ;
  • le dataset actif.
Avant :
Nom = Étude initiale
Dossier = save/projects/etude-initiale/

Après :
Nom = Étude finale
Dossier = save/projects/etude-initiale/

38.3. Collision#

Un nom déjà utilisé par un autre projet est refusé.

39. Liste des projets#

La section Vos projets affiche les projets enregistrés sur le disque.

Pour chaque projet, elle indique le nom visible, s’il est ouvert, le nombre de datasets sauvegardés, sa taille totale et sa date de modification.

39.1. Ordre de la liste#

Les projets sont triés de la date de modification la plus récente à la plus ancienne.

39.2. Nombre de datasets#

Le nombre provient en priorité du manifeste. Pour les anciens projets dont le manifeste ne contient pas ce champ, BarCodeR lit registry.rds.

Le nombre représente les datasets sauvegardés sur le disque, pas forcément l’état non sauvegardé de la mémoire.

39.3. Date de modification#

La date provient du manifeste du projet.

Elle est notamment actualisée lors d’une sauvegarde, d’un renommage, d’une création, d’une duplication et d’un import.

Elle ne correspond pas nécessairement à la dernière modification d’un fichier de figure.

40. Dupliquer un projet#

Le bouton Dupliquer copie l’intégralité du dossier d’un projet.

40.1. Contenu copié#

La copie peut inclure le registre, le manifeste, l’état d’interface, les datasets, les figures, les historiques et les autres fichiers présents.

40.2. Nom#

Le nom proposé est <nom du projet> (copie). En cas de collision, un suffixe supplémentaire est utilisé.

40.3. Date de création#

Le projet dupliqué reçoit sa propre date de création.

40.4. Duplication du projet courant#

Si le projet à dupliquer est ouvert, BarCodeR tente d’abord de le sauvegarder.

Cependant, le résultat de cette sauvegarde n’est pas bloquant dans le flux actuel de duplication.

Pour garantir que la copie inclut les toutes dernières modifications :

  1. cliquer d’abord sur Sauvegarder le projet ;
  2. vérifier le message de succès ;
  3. seulement ensuite cliquer sur Dupliquer.

40.5. Projet non courant#

La duplication d’un projet fermé copie son état enregistré sur le disque. Elle ne peut pas inclure des modifications qui existeraient uniquement dans une autre session non sauvegardée.

41. Supprimer un projet#

Seuls les projets non ouverts peuvent être supprimés.

41.1. Portée de la suppression#

La suppression retire physiquement le dossier :

save/projects/<slug>/

Elle supprime donc les datasets sauvegardés, le registre, le manifeste, les figures, les historiques, les paramètres et tous les fichiers présents dans le projet.

41.2. Action irréversible#

La suppression n’utilise pas une corbeille interne.

Elle est irréversible, sauf si une copie existe dans une archive ZIP, une sauvegarde système, un autre dossier ou un autre serveur.

41.3. Projet courant#

Le projet actuellement ouvert ne peut pas être supprimé.

Pour le supprimer : ouvrir un autre projet, revenir dans la liste, puis supprimer l’ancien projet.

41.4. Contrôle du résultat#

BarCodeR vérifie que le dossier a réellement disparu avant d’annoncer le succès.

Une erreur peut être causée par des permissions insuffisantes, un fichier verrouillé, un dossier utilisé ou une erreur du système de fichiers.

42. Différences entre les trois exports#

Export Contenu Figures Plusieurs datasets Réimport
Dataset individuel .rds Un phyloseq Non Non Input data
Données du projet .rds Liste des datasets + actif Non Oui Input data
Projet complet .zip Dossier du projet Oui Oui Datasets

42.1. Dataset individuel#

À utiliser pour transmettre un phyloseq, travailler dans R, archiver un objet précis ou réimporter un seul dataset.

42.2. Données seules du projet#

À utiliser pour sauvegarder plusieurs phyloseq dans un fichier compact, transférer uniquement les données, exclure les figures ou recharger les datasets dans un projet existant.

42.3. Projet complet#

À utiliser pour archiver l’ensemble de l’espace de travail, conserver les figures, déplacer un projet vers une autre installation ou créer un nouveau projet identique lors de l’import.

43. Projets et données OpenMetaBar#

Importer un phyloseq produit par OpenMetaBar dans BarCodeR ne copie pas automatiquement le dossier distant du run dans le projet local.

Le projet peut contenir l’objet phyloseq importé, ses attributs de provenance et les analyses et figures effectuées dans BarCodeR.

Il ne contient pas nécessairement les FASTQ, les logs complets du cluster, le dossier work/, les sorties Nextflow, les conteneurs, la base de référence ou le dossier distant du run.

Ces éléments doivent être archivés séparément depuis OpenMetaBar ou le cluster.

44. Projets et historiques de figures#

Les figures enregistrées dans les modules sont associées au projet courant au moment de leur sauvegarde.

Changer de projet modifie donc le dossier dans lequel les futurs historiques seront enregistrés.

Une figure seulement affichée à l’écran mais non enregistrée dans un historique peut ne pas être incluse dans le projet.

Il faut distinguer : résultat calculé en mémoire, figure enregistrée dans l’historique, figure exportée sur le poste et figure présente dans l’archive complète.

45. Emplacement physique des projets#

Les projets sont enregistrés relativement au dossier de travail de BarCodeR :

<dossier-de-BarCodeR>/save/projects/

45.1. Permissions#

La machine exécutant BarCodeR doit permettre la création de dossiers, l’écriture de fichiers RDS, la création de ZIP, la suppression de dossiers et la lecture des projets existants.

45.2. Déploiement Docker ou serveur#

Sur un environnement conteneurisé, le dossier doit être placé sur un volume persistant.

Sans volume persistant, les projets peuvent disparaître lors d’un redémarrage du conteneur, d’une mise à jour, d’un redéploiement ou d’une reconstruction de l’image.

45.3. Instance partagée#

Sur une instance partagée, les projets se trouvent sur le système de fichiers du serveur.

Le niveau d’isolation dépend de la configuration de déploiement. BarCodeR ne transforme pas automatiquement le gestionnaire de projets en espace privé par utilisateur.

Il faut donc contrôler les permissions, l’authentification, l’isolation des sessions, le stockage et les sauvegardes serveur.

46. Parcours recommandé pour un travail courant#

  1. Ouvrir ou créer le bon projet.
  2. Charger les données depuis Input data ou OpenMetaBar.
  3. Vérifier le registre.
  4. Choisir le dataset actif.
  5. Ajouter des notes et des tags.
  6. Réaliser les éditions et analyses.
  7. Créer des copies avant les modifications majeures.
  8. Sauvegarder régulièrement le projet.
  9. Exporter les datasets importants individuellement.
  10. Exporter périodiquement une archive ZIP complète.
  11. Stocker cette archive hors de l’installation BarCodeR.

47. Parcours recommandé avant une opération risquée#

Avant une filtration importante, une édition massive, une suppression, un remplacement, une restauration, un changement de projet ou une mise à jour de l’application :

  1. Sauvegarder le projet ;
  2. vérifier le message de succès ;
  3. exporter le dataset important ;
  4. exporter le projet complet si nécessaire ;
  5. vérifier la présence du fichier téléchargé.

48. Résolution des problèmes#

48.1. Un dataset n’apparaît pas dans le registre#

Causes possibles : import non terminé, objet refusé, dataset ajouté dans un autre projet, projet différent actuellement ouvert, dataset supprimé ou session rechargée sans sauvegarde.

Vérifier Input data, le projet courant, la sauvegarde sur disque et les notifications.

48.2. Le mauvais dataset est utilisé dans un module#

Le dataset actif global et la sélection locale du module peuvent être différents.

Vérifier les deux sélecteurs et définir explicitement le dataset actif.

48.3. Le changement de dataset actif n’est pas conservé#

Le projet n’a pas été sauvegardé après le changement. Cliquer sur Sauvegarder le projet.

48.4. Le nom saisi a été modifié#

Les espaces et caractères spéciaux ont été normalisés. Utiliser un nom simple avec lettres, chiffres, _ et -.

48.5. Un suffixe _2 a été ajouté#

Un dataset de même nom existait déjà. Utiliser un nom différent ou supprimer/renommer l’ancien dataset.

48.6. Une date de modification n’a pas changé#

La colonne ne suit que edit_log et filtration_log. Les notes, tags et renommages ne modifient pas cette date.

48.7. Un dataset dupliqué conserve la provenance de l’original#

La duplication copie l’objet et ses attributs. La provenance indique la manière dont l’objet initial a été produit, pas l’action de duplication.

48.8. Un dataset filtré n’est plus indiqué comme filtré#

Son parent a peut-être été supprimé et le nom du parent vidé. Examiner :

attr(ps, "filtration_log")

48.9. Un dataset supprimé réapparaît#

La suppression n’avait pas été sauvegardée et une ancienne version du registre a été restaurée. Supprimer de nouveau, puis sauvegarder le projet.

48.10. Impossible de sauvegarder un projet vide#

La sauvegarde rapide exige au moins un dataset. Créer un nouveau projet, conserver au moins un dataset ou supprimer le projet complet si l’objectif est de repartir de zéro.

48.11. La restauration a supprimé des modifications#

La restauration remplace la mémoire par registry.rds. Rechercher un export individuel, une archive ZIP, un autre projet ou les fichiers sources.

48.12. Aucun fichier de sauvegarde n’existe#

Le projet n’a jamais été sauvegardé. Ajouter au moins un dataset puis cliquer sur Sauvegarder le projet.

48.13. Le projet s’ouvre vide avec une erreur de registre#

registry.rds existe mais est illisible. Copier immédiatement le dossier du projet, ne pas écraser le fichier, tester readRDS() dans R et restaurer une archive si nécessaire.

48.14. Un nouveau projet porte un nom refusé#

Le nom est vide ou déjà utilisé, éventuellement avec une casse différente. Choisir un nom distinct.

48.15. Le projet a changé mais le dossier garde l’ancien nom#

Le renommage ne modifie que le nom visible. Ce comportement est normal et évite de casser les chemins.

48.16. L’ouverture d’un projet recharge toute l’application#

Les modules doivent être réinitialisés avec les chemins du nouveau projet. Les calculs ou modifications non confirmés peuvent être perdus.

48.17. Une erreur de sauvegarde apparaît pendant l’ouverture d’un projet#

Le changement de projet peut tout de même continuer. Noter le projet précédent, le rouvrir, vérifier les datasets et restaurer un export si nécessaire.

48.18. Avertissement sur plusieurs onglets ouverts#

Plusieurs sessions utilisent la même instance de BarCodeR. Fermer les autres onglets avant de changer de projet.

48.19. La duplication d’un projet ne contient pas les dernières modifications#

Le projet courant n’avait peut-être pas été correctement sauvegardé avant la duplication. Sauvegarder explicitement avant de dupliquer.

48.20. Impossible de supprimer le projet courant#

BarCodeR protège le projet ouvert. Ouvrir un autre projet, puis supprimer le premier.

48.21. La suppression d’un projet échoue#

Causes possibles : permissions insuffisantes, fichier verrouillé, dossier utilisé, erreur disque, antivirus ou répertoire réseau indisponible.

Vérifier le dossier save/projects/<slug>/ et les droits de l’utilisateur exécutant BarCodeR.

48.22. L’archive ZIP est très lourde#

Causes possibles : nombreuses figures, historiques anciens, datasets volumineux, exports dupliqués ou objets intermédiaires.

Supprimer les historiques inutiles, exporter les données seules, dupliquer puis nettoyer le projet ou archiver directement le dossier sur le serveur.

48.23. L’archive ZIP dépasse 500 Mo#

Elle peut ne pas être importable par l’interface actuelle.

Solutions : augmenter shiny.maxRequestSize, réduire l’archive, copier directement le projet dans save/projects/ ou utiliser un stockage externe.

48.24. L’archive importée n’apparaît pas automatiquement#

L’import crée un nouveau projet mais ne l’ouvre pas. Le sélectionner dans Vos projets, puis cliquer sur Ouvrir.

48.25. L’archive est déclarée invalide#

Causes possibles : ZIP corrompu, archive non produite par BarCodeR, projet trop profondément imbriqué, absence de registre, manifeste et historique reconnu, ou extraction échouée.

48.26. Le projet importé contient zéro dataset#

Causes possibles : absence de registry.rds, registre illisible, archive composée seulement de figures ou projet jamais sauvegardé.

Ouvrir le projet pour vérifier ses historiques, importer séparément les datasets ou retrouver une archive plus complète.

48.27. L’export ZIP n’inclut pas les dernières données#

La sauvegarde préalable a peut-être échoué ou été refusée. Toujours vérifier le message de sauvegarde avant de conserver l’archive comme référence.

48.28. Le nombre de datasets de la liste semble incorrect#

Causes possibles : manifeste non actualisé, sauvegarde non effectuée, ancien projet ou cache d’affichage. Sauvegarder, rafraîchir et vérifier registry.rds.

48.29. La taille du projet n’est pas immédiatement mise à jour#

Le calcul de taille est mis en cache pendant quelques secondes. Attendre puis rafraîchir.

48.30. Les projets disparaissent après un redéploiement#

Le dossier save/projects/ n’était pas situé sur un stockage persistant. Monter ce dossier dans un volume persistant et conserver des exports ZIP externes.

49. Checklist avant une sauvegarde#

  • Le bon projet est ouvert.
  • Les datasets attendus sont présents.
  • Le bon dataset est actif.
  • Les noms sont corrects.
  • Les notes et tags sont à jour.
  • Les suppressions sont volontaires.
  • Les duplications inutiles ont été retirées.
  • Les modifications des tables ont été confirmées.
  • Aucun calcul important n’est encore en attente.
  • Aucun message d’erreur n’est visible.

50. Checklist avant un changement de projet#

  • Sauvegarder le projet courant.
  • Vérifier le message de succès.
  • Exporter les datasets importants.
  • Fermer les modales ouvertes.
  • Terminer ou annuler les calculs.
  • Fermer les autres onglets BarCodeR.
  • Vérifier le nom du projet cible.
  • Accepter que la page soit rechargée.

51. Checklist avant la suppression d’un dataset#

  • Vérifier le nom exact.
  • Vérifier s’il est actif.
  • Vérifier s’il possède des descendants filtrés.
  • Exporter le dataset si nécessaire.
  • Sauvegarder une archive du projet.
  • Supprimer.
  • Vérifier le nouvel actif.
  • Sauvegarder le projet pour rendre la suppression persistante.

52. Checklist avant la suppression d’un projet#

  • Vérifier que ce n’est pas le projet courant.
  • Exporter une archive ZIP.
  • Vérifier le téléchargement de l’archive.
  • Vérifier les datasets importants individuellement.
  • Vérifier que les données brutes sont archivées ailleurs.
  • Vérifier les résultats OpenMetaBar sur le cluster.
  • Confirmer la suppression uniquement après ces contrôles.

53. Stratégie de sauvegarde recommandée#

Pour un projet important, conserver au minimum trois niveaux.

Niveau 1 — Sauvegarde interne régulière#

Cliquer régulièrement sur Sauvegarder le projet.

Niveau 2 — Export des datasets critiques#

Exporter individuellement les objets importants :

dataset_<nom>_<date>.rds

Niveau 3 — Archive complète externe#

Exporter périodiquement :

projet_<nom>_<date>.zip

puis conserver cette archive sur un NAS, un serveur institutionnel, une sauvegarde versionnée ou un support distinct de la machine exécutant BarCodeR.

La sauvegarde interne seule ne protège pas contre une panne disque, une suppression du dossier, un redéploiement, une erreur système ou la perte du serveur.

54. Principes de traçabilité#

Pour conserver un historique exploitable :

  • utiliser des noms de projet explicites ;
  • éviter les noms de datasets ambigus ;
  • ajouter des notes ;
  • utiliser des tags homogènes ;
  • conserver la provenance ;
  • dupliquer avant une modification majeure ;
  • sauvegarder après chaque étape importante ;
  • exporter les états de référence ;
  • noter la date et la version de BarCodeR ;
  • conserver les fichiers bruts séparément ;
  • ne pas confondre sauvegarde du projet et archivage scientifique complet.

55. Limites actuelles à connaître#

55.1. Les actions dataset agissent d’abord en mémoire#

Elles ne deviennent persistantes qu’après sauvegarde.

55.2. Un projet vide ne peut pas être sauvegardé rapidement#

Une ancienne sauvegarde peut donc rester présente après suppression de tous les datasets.

55.3. La date Modifié est partielle#

Elle ne suit pas toutes les actions du registre.

55.4. La provenance Filtré dépend du nom du parent#

Supprimer le parent peut modifier le badge du descendant.

55.5. La duplication conserve les attributs de provenance#

Il n’existe pas de provenance spécifique « copie ».

55.6. Les noms de datasets ne sont pas garantis ASCII#

Le résultat dépend en partie de la locale R.

55.7. Le changement de projet est global à l’instance R#

Plusieurs onglets ouverts peuvent interférer.

55.8. Une erreur de sauvegarde ne bloque pas toujours le changement de projet#

Les notifications doivent être lues attentivement.

55.9. La duplication du projet courant ne vérifie pas strictement le succès de la sauvegarde préalable#

Une sauvegarde manuelle est recommandée.

55.10. Le voyant de sauvegarde ne suit pas tous les fichiers du projet#

Il reflète principalement le registre et le dataset actif.

55.11. L’export ZIP n’inclut pas les fichiers externes#

Les données brutes et résultats distants doivent être archivés séparément.

55.12. Une archive supérieure à 500 Mo peut ne pas être importable par l’interface#

La limite globale de téléversement s’applique.

55.13. Le stockage doit être persistant#

Le dossier save/projects/ doit survivre aux redémarrages et mises à jour.
