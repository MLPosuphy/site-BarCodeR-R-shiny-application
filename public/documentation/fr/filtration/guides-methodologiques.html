Filtration — Guide méthodologique

1. Rôle général de l’onglet#

L’onglet Filtration permet de construire un sous-ensemble d’un objet phyloseq déjà chargé dans BarCodeR.

Il peut retirer :

  • des taxons selon leur annotation taxonomique ;
  • des ASV peu abondantes ou peu prévalentes ;
  • des échantillons selon leur profondeur, leur richesse, leur nom ou leurs métadonnées ;
  • des séquences ne respectant pas certains critères techniques.

Le résultat est d’abord construit sous la forme d’un objet temporaire :

ps_filtered

Ce résultat peut ensuite être examiné dans le résumé, enregistré sous un nouveau nom, utilisé pour remplacer son dataset parent, inspecté dans Description, comparé aux autres datasets et exporté.

Différence avec Data Edition#

Data Edition Filtration
Modifie directement les tables du dataset sélectionné Construit d’abord un objet temporaire dérivé
Les modifications sont immédiates dans datasets() Le parent reste inchangé pendant le paramétrage
Adapté aux corrections de cellules et de structure Adapté au retrait d’échantillons ou de taxons selon des critères
Journalise les éditions dans edit_log Journalise la filtration dans filtration_log

Tant que le résultat n’est pas enregistré, il n’apparaît pas dans Datasets, n’est pas accessible aux autres modules, n’est pas sauvegardé sur le disque et peut être perdu lors du rechargement de la session.

2. Fonctionnement automatique et cycle de vie du résultat#

Il n’existe pas de bouton Appliquer les filtres. La filtration est recalculée automatiquement lorsqu’un paramètre actif change, par exemple lors de l’activation d’un bloc, d’un changement de seuil, d’une sélection taxonomique, de l’ajout d’une condition de metadata ou d’un changement de dataset.

Sur un dataset volumineux, chaque modification peut déclencher la lecture de l’OTU table, le calcul des abondances et de la prévalence, plusieurs appels à prune_taxa() ou prune_samples(), l’analyse des séquences et la reconstruction du journal et du résumé. Il est préférable de modifier les paramètres progressivement et d’attendre la fin du recalcul avant de poursuivre.

Le parent reste intact pendant le réglage#

dataset parent
      ↓
calcul réactif
      ↓
dataset filtré temporaire

Le dataset parent n’est remplacé qu’au moment de l’enregistrement, si le résultat est enregistré sous le même nom.

Attention au champ de nom vide#

Le champ d’enregistrement est vide par défaut. Une valeur vide signifie :

Enregistrer le résultat sous le nom du parent et remplacer le parent.

Cette opération ne demande pas de confirmation supplémentaire. Pour conserver le dataset brut, saisir explicitement un nouveau nom, par exemple COI_raw et COI_filtered.

L’enregistrement modifie uniquement la mémoire de BarCodeR. Il faut ensuite utiliser Datasets → Sauvegarder le projet pour rendre le résultat persistant.

3. Ordre d’application des filtres#

Les filtres sont toujours appliqués dans l’ordre suivant :

1. Taxonomie
2. Abondance des ASV
3. Échantillons
4. Séquences

Cet ordre est fixe. Il ne dépend pas de l’ordre dans lequel les boxes sont ouvertes ou paramétrées.

Conséquences#

Chaque bloc travaille sur le résultat du bloc précédent. Par exemple :

  1. suppression des chloroplastes ;
  2. recalcul du total et de la prévalence des ASV restantes ;
  3. recalcul des reads et de la richesse des échantillons ;
  4. retrait des échantillons insuffisants ;
  5. retrait des séquences ne respectant pas les critères techniques.

Les seuils appliqués aux échantillons ne portent donc pas nécessairement sur les valeurs du dataset brut affichées dans Description.

Un seul passage, sans convergence#

Le pipeline ne recommence pas depuis le début après la dernière étape. Cela signifie notamment que :

  • la suppression d’échantillons peut rendre certaines ASV moins prévalentes que le seuil choisi, sans qu’elles soient supprimées une seconde fois ;
  • la filtration des séquences peut réduire les reads ou la richesse de certains échantillons sous les seuils choisis, sans que ces échantillons soient retirés ;
  • des taxons ou échantillons à zéro peuvent subsister dans le résultat final.

Un second passage de filtration peut donc retirer davantage d’éléments que le premier.

4. Sélection du dataset et persistance des paramètres#

Le sélecteur principal est synchronisé avec le dataset actif global. Changer de dataset dans Filtration modifie active_ds(), change le dataset actif dans les autres onglets et peut marquer le projet comme non sauvegardé.

Les paramètres ne sont pas tous réinitialisés#

Lors du changement de dataset, plusieurs réglages peuvent rester actifs :

  • seuils d’abondance ;
  • seuils d’échantillons ;
  • critères de séquences ;
  • mots-clés taxonomiques ;
  • conditions avancées ;
  • nom d’enregistrement.

Les listes dépendantes du dataset sont actualisées, notamment les rangs taxonomiques, les valeurs taxonomiques, les noms des échantillons et les variables de metadata.

Une condition avancée peut néanmoins rester présente alors que sa variable n’existe plus dans le nouveau dataset. Dans ce cas, le calcul peut être bloqué jusqu’à suppression ou correction de la condition.

Après chaque changement de dataset, vérifier l’ensemble des blocs avant d’enregistrer.

5. Lecture de l’état de l’interface#

Chaque bloc possède un état visuel.

Couleur Signification
Gris Aucun paramètre actif ou modifié
Orange Des paramètres ont été modifiés, mais le bloc n’est pas activé
Vert La case d’activation du bloc est cochée

Une bordure verte ne garantit pas qu’un filtre retire réellement des éléments. Par exemple, le bloc ASV peut être activé avec tous les seuils à zéro : il apparaît vert, mais ses critères restent neutres.

Le bandeau global tente de distinguer les blocs réellement paramétrés, mais un dataset peut néanmoins recevoir un filtration_log sans qu’aucun élément ait été supprimé.

Aperçus graphiques#

Les histogrammes des seuils sont calculés sur le dataset parent sélectionné, et non sur l’objet progressivement filtré. Ils montrent notamment :

  • total des reads par ASV ;
  • prévalence ;
  • abondance relative maximale ;
  • reads par échantillon ;
  • richesse par échantillon ;
  • longueur ;
  • GC.

La ligne de seuil permet d’examiner la distribution initiale, mais ne représente pas toujours les valeurs réellement utilisées après les étapes précédentes. Le résumé avant/après constitue la principale prévisualisation du résultat final.

6. Filtration taxonomique#

La filtration taxonomique nécessite une tax_table. Elle permet d’exclure certaines valeurs d’un rang, de conserver uniquement certaines valeurs et d’exclure des annotations contenant des mots-clés.

Paramètres présélectionnés#

Les mots-clés suivants sont sélectionnés par défaut :

chloroplast
mitochondria

Ils ne sont pas appliqués tant que le bloc n’est pas activé. En revanche, cocher simplement Activer la filtration peut immédiatement retirer les taxons correspondant à ces termes.

Ces mots-clés ne sont pas des contaminants universels. Ils peuvent représenter le signal biologique recherché selon le marqueur et l’objectif de l’étude.

Exclusion et conservation par rang#

Pour le rang taxonomique choisi :

  • Exclure supprime les ASV dont la valeur correspond exactement à une valeur sélectionnée ;
  • Garder uniquement conserve les ASV correspondant à une valeur sélectionnée.

L’ordre interne est :

1. Exclusion
2. Conservation
3. Recherche par mots-clés

Des critères contradictoires peuvent supprimer l’ensemble des taxons.

Recherche par mots-clés#

Les mots-clés sont recherchés dans toutes les colonnes taxonomiques, sans distinction de casse, comme sous-chaînes et avec un motif combiné par |.

Ainsi, chloroplast peut correspondre à Chloroplast, chloroplastidae ou Unclassified chloroplast sequence. La recherche ne se limite pas au rang sélectionné.

Taxonomie absente#

Si le bloc est activé sans taxonomie disponible, le filtre est ignoré. Les autres blocs peuvent néanmoins continuer à produire un résultat. Il faut vérifier le résumé réel plutôt que se fier uniquement à l’état vert de la box.

7. Filtration des ASV selon l’abondance#

Trois critères sont disponibles et sont appliqués successivement :

1. Total de reads
2. Prévalence
3. Abondance relative maximale

Ces critères supposent que les valeurs de l’OTU table sont interprétables comme des abondances. Ils peuvent être trompeurs sur des données CLR, des abondances relatives, des données logarithmiques, des valeurs négatives ou des matrices déjà normalisées.

Total de reads par ASV#

Pour chaque ASV :

Total = somme des abondances dans les échantillons présents à cette étape

La règle appliquée est stricte :

Total > seuil

Avec un seuil de 10, un total égal à 10 est supprimé et un total égal à 11 est conservé.

Prévalence#

La prévalence correspond au nombre d’échantillons où l’abondance est strictement supérieure à zéro. La règle est :

Prévalence ≥ seuil

Avec un seuil de 3, une ASV présente dans exactement trois échantillons est conservée.

Un seuil absolu doit être interprété en fonction du nombre total d’échantillons. Une présence dans trois échantillons représente 30 % d’un projet de dix échantillons, mais seulement 3 % d’un projet de cent échantillons.

Abondance relative maximale#

Pour chaque ASV, BarCodeR calcule son abondance relative dans chaque échantillon, puis retient sa valeur maximale :

Maximum de : abondance de l’ASV / abondance totale de l’échantillon × 100

La règle est :

Abondance relative maximale ≥ seuil

Ce filtre permet de conserver une ASV globalement rare mais localement importante.

Le calcul est effectué après les filtres de total et de prévalence. La suppression de taxons modifie donc les dénominateurs et augmente mécaniquement la part relative des taxons restants.

8. Filtration des échantillons#

Les critères sont appliqués dans cet ordre :

1. Reads minimaux
2. Richesse minimale
3. Noms des échantillons
4. Condition simple de metadata
5. Conditions avancées

Reads minimaux#

Le nombre de reads est recalculé après les filtres taxonomiques et d’abondance :

Reads = somme des abondances des taxons encore présents

La règle est inclusive :

Reads ≥ seuil

Richesse minimale#

La richesse correspond au nombre de taxons dont l’abondance est strictement supérieure à zéro. La règle est :

Richesse ≥ seuil

La richesse peut différer de celle affichée dans Description pour le dataset parent.

Filtration par noms#

Les noms correspondent exactement à sample_names(ps). Il n’existe pas de recherche partielle ou insensible à la casse.

  • Garder conserve uniquement les noms sélectionnés ;
  • Exclure retire les noms sélectionnés.

Cette étape est appliquée après les seuils de reads et de richesse. Un échantillon sélectionné avec Garder peut donc avoir déjà été supprimé.

Condition simple de metadata#

Le module distingue principalement les colonnes numériques et les facteurs ou chaînes de caractères. Les dates, colonnes logiques et classes particulières peuvent ne pas être correctement reconnues dans le filtre simple.

Variables numériques

Les opérateurs disponibles sont ≥, >, ≤, < et entre. L’option entre inclut les deux limites. Si les limites sont inversées, BarCodeR utilise automatiquement la plus petite et la plus grande.

Les valeurs proposées initialement, comme la médiane ou les quartiles, sont uniquement des valeurs pratiques. Elles ne constituent pas des recommandations scientifiques.

Avec Garder, les valeurs manquantes sont généralement retirées. Avec Exclure, elles sont généralement conservées, car elles ne satisfont pas la condition avant inversion.

Variables catégorielles

Les comparaisons sont exactes après conversion en texte. Elles sont sensibles à la casse, aux espaces et à l’orthographe.

Plusieurs valeurs sélectionnées dans une même condition sont combinées avec une logique OU.

Les valeurs manquantes sont généralement supprimées avec Garder et conservées avec Exclure.

9. Conditions avancées de metadata#

Chaque condition avancée définit une variable, une action Garder ou Exclure, une comparaison ou plusieurs valeurs et un bouton de suppression.

Toutes les conditions sont combinées entre elles avec une logique ET.

Exemple :

Garder Campagne = 2026
ET
Exclure Site = contrôle
ET
Garder Profondeur ≥ 50

Une logique OU entre deux variables distinctes n’est pas proposée.

Pour une variable catégorielle, plusieurs modalités sélectionnées dans une même ligne constituent toutefois un OU interne, par exemple Site = A ou B.

Les variables non reconnues comme numériques sont traitées comme du texte. Une date peut donc être sélectionnée comme catégorie, mais pas filtrée comme véritable intervalle temporel.

Condition incomplète#

Une condition avancée incomplète peut empêcher complètement la construction du résultat temporaire, même si les autres filtres sont valides. Il faut alors compléter la condition ou la supprimer.

10. Filtration technique des séquences#

La filtration technique utilise refseq(ps) et peut appliquer des critères de longueur, GC, bases ambiguës et homopolymères. Elle est appliquée en dernier.

Absence ou mauvais alignement des séquences#

Si refseq est absente, le bloc est ignoré et une ligne est ajoutée au journal.

BarCodeR essaie d’aligner les séquences sur taxa_names(ps) :

  • si les séquences n’ont pas de nom mais sont aussi nombreuses que les taxons, l’ordre est supposé identique ;
  • si elles sont nommées, leurs noms sont mis en correspondance avec les taxons.

Si aucune séquence ne peut être alignée, le bloc est ignoré.

Si la couverture est partielle, les ASV possédant une séquence sont évaluées et les ASV sans séquence sont conservées sans être testées.

Les graphiques de longueur et de GC utilisent un alignement plus strict et peuvent être absents alors que le filtre est appliqué partiellement.

Longueur#

Les limites sont inclusives :

Longueur minimale ≤ longueur ≤ longueur maximale

Une valeur maximale égale à zéro désactive la limite haute. Si le minimum est supérieur au maximum, toutes les séquences peuvent être rejetées.

GC#

Le GC utilisé par le filtre est calculé sur les bases A, C, G et T :

G + C
────────────── × 100
A + C + G + T

Les bases ambiguës ne sont pas incluses dans ce dénominateur. Les limites minimale et maximale sont inclusives. Les valeurs neutres sont 0 % et 100 %.

Bases ambiguës#

Les caractères comptabilisés sont :

N R Y S W K M B D H V

Les gaps, points ou autres symboles ne sont pas explicitement comptés par ce critère.

Dans l’implémentation actuelle, Maximum d’ambiguïtés = 0 désactive le filtre. Cela ne permet pas d’exiger strictement zéro base ambiguë.

Homopolymères#

BarCodeR recherche la plus longue série de caractères identiques consécutifs. Par exemple, AAAATCG possède un homopolymère maximal de 4.

Tous les caractères peuvent être concernés, y compris les bases ambiguës ou les symboles répétés. La séquence est conservée si la longueur maximale observée est inférieure ou égale au seuil. Une valeur de zéro désactive également ce critère.

Conséquence de l’ordre#

Après la filtration technique, les seuils d’échantillons ne sont pas recalculés. Des échantillons peuvent donc finir sous le seuil de reads, sous le seuil de richesse ou avec zéro read.

11. Protection contre les résultats vides et limites de validation#

Avant une opération qui supprimerait tous les taxons ou tous les échantillons, BarCodeR interrompt le calcul et affiche une erreur.

Cette protection garantit uniquement qu’au moins un taxon et un échantillon restent disponibles. Elle ne garantit pas :

  • un nombre suffisant de réplicats ;
  • une profondeur minimale finale ;
  • une richesse minimale finale ;
  • l’absence d’échantillons à zéro ;
  • l’absence de taxons à zéro ;
  • l’adéquation du résultat à une analyse statistique.

Le résultat final doit être contrôlé dans Description.

12. Journal de filtration et provenance#

Le résultat reçoit un attribut :

attr(ps, "filtration_log")

Il peut contenir le nom du parent, la date, les dimensions avant et après, des lignes descriptives, les paramètres structurés, les taxons supprimés et les échantillons supprimés.

Paramètres structurés#

Les paramètres sont enregistrés dans :

filtration_log$params

Ils comprennent notamment les blocs activés, le rang taxonomique, les valeurs exclues ou conservées, les mots-clés, les seuils d’abondance, les filtres de noms, les conditions de metadata et les paramètres de séquences.

Cette structure est la source la plus fiable pour reproduire ou auditer la filtration.

Langue du journal#

Les textes sont enregistrés dans la langue active au moment du calcul et ne sont pas retraduits ensuite.

La colonne Blocs actifs du tableau récapitulatif recherche actuellement certaines expressions françaises dans les textes du journal. Elle peut donc afficher — pour un dataset filtré dans une autre langue. Les paramètres structurés restent plus fiables que cette colonne.

Tables des éléments supprimés#

Les tables removed_taxa et removed_samples utilisent les métriques du dataset parent avant tous les filtres.

Un échantillon retiré parce qu’il ne possède plus que 800 reads après retrait taxonomique peut donc apparaître avec 5 000 reads dans la table des supprimés.

Les tables ne donnent pas toujours une cause individuelle exacte pour chaque ligne. Les étapes du journal indiquent surtout les effets globaux.

Filtrations successives#

Un nouveau passage remplace l’ancien filtration_log. L’historique précédent n’est pas empilé.

Pour conserver chaque étape, utiliser des noms séparés :

COI_raw
COI_tax
COI_abundance
COI_final

Attributs conservés ou potentiellement perdus#

BarCodeR recopie explicitement openmetabar_run et edit_log.

Les opérations de pruning peuvent supprimer d’autres attributs non standards, notamment dataset_meta, les notes et tags ou des attributs personnalisés. Ces informations doivent être vérifiées après filtration.

13. Enregistrement du résultat et risques d’écrasement#

Trois cas sont possibles.

Nom saisi Comportement
Champ vide ou nom du parent Remplacement immédiat du parent
Nouveau nom Création d’un nouveau dataset
Nom d’un autre dataset Demande de confirmation avant remplacement

Le nom est normalisé avec le helper commun de BarCodeR. Contrairement à Input data, aucun suffixe _2 n’est ajouté automatiquement en cas de collision.

Enregistrement en mémoire uniquement#

Le bouton Enregistrer modifie datasets(). Il ne sauvegarde pas le projet sur le disque.

Le résultat enregistré devient le dataset actif.

Réapplication automatique des filtres#

Comme le sélecteur Filtration suit le dataset actif, le résultat enregistré devient immédiatement le nouveau parent du module. Les filtres restant actifs, ils sont réappliqués automatiquement :

parent brut
    ↓
premier résultat enregistré
    ↓
mêmes filtres encore actifs
    ↓
nouveau résultat temporaire

Un second clic sur Enregistrer peut donc retirer davantage d’éléments.

Après l’enregistrement :

  1. ne pas recliquer immédiatement ;
  2. désactiver les filtres ou quitter l’onglet ;
  3. vérifier le résultat dans Description ;
  4. sauvegarder le projet dans Datasets.

14. Inspection des datasets et exports#

La partie inférieure affiche les datasets présents dans le registre, mais pas le résultat temporaire non enregistré.

Le tableau peut indiquer le nom, le statut filtré, le parent, la date, les dimensions avant et après, les nombres supprimés et les blocs actifs.

Un dataset est affiché comme filtré dès qu’un filtration_log existe, même si aucun élément n’a réellement été supprimé.

Si le résultat écrase son parent sous le même nom, il peut apparaître comme son propre parent.

Si le dataset est ensuite modifié dans Data Edition, ses dimensions actuelles peuvent ne plus correspondre uniquement à la filtration consignée.

Panneau de détail#

Le panneau permet d’examiner le journal, les paramètres, les taxons et échantillons supprimés, l’OTU table, la taxonomie, la metadata, les séquences et différents histogrammes.

Quelques particularités doivent être connues :

  • l’histogramme nommé Reads représente en réalité le total par taxon ;
  • l’histogramme logarithmique utilise log10(total + 1) ;
  • le GC affiché dans le détail divise par la longueur totale de la chaîne et peut différer du GC utilisé pour filtrer ;
  • l’OTU table est systématiquement transposée pour le détail, sans normalisation fiable de son orientation ;
  • certains panneaux peuvent être vides ou produire une erreur si le composant correspondant est absent.

Exports TSV#

Les noms sont génériques :

otu_table.tsv
taxonomy.tsv
metadata.tsv

Ils ne contiennent pas le nom du dataset ni la date. Les rownames sont exportés comme première colonne, parfois sans nom explicite.

L’OTU table est également transposée systématiquement dans cet export. Son orientation dépend donc de l’orientation initiale du phyloseq.

Export BIOM#

Le fichier BIOM contient uniquement la matrice d’abondance. Il ne contient pas automatiquement la taxonomie, la metadata, les séquences, l’arbre ou le journal.

L’orientation stockée est utilisée directement. Si les taxons sont en colonnes, le fichier peut être inversé.

Si biomformat n’est pas disponible, BarCodeR produit actuellement un fichier portant l’extension .biom mais contenant un message texte. Ce fichier n’est pas un BIOM valide.

15. Interprétation scientifique et stratégie recommandée#

BarCodeR ne peut pas déterminer automatiquement les seuils adaptés. Ils dépendent notamment du marqueur, de la technologie, du protocole, du nombre d’échantillons, de la profondeur, des contrôles, de la diversité attendue, du pipeline et de l’objectif scientifique.

Taxons rares#

Une ASV rare peut être une erreur, une contamination, un artefact, un véritable taxon rare ou un événement biologique important. La rareté seule ne justifie pas automatiquement une suppression.

Groupes expérimentaux#

Un seuil global peut déséquilibrer fortement les groupes. Il faut vérifier après filtration le nombre d’échantillons par groupe, les contrôles conservés, le nombre de réplicats et la profondeur de chaque groupe.

Comparaison de stratégies#

Pour comparer deux méthodes de filtration, partir du même dataset parent :

COI_raw → méthode A
COI_raw → méthode B

Éviter COI_raw → méthode A → méthode B, sauf si l’objectif est explicitement une filtration progressive.

Parcours conseillé#

  1. Sauvegarder le projet.
  2. Conserver le dataset brut.
  3. Sélectionner le parent.
  4. Vérifier tous les paramètres hérités.
  5. Activer un seul bloc à la fois.
  6. Examiner les dimensions après chaque bloc.
  7. Ajouter progressivement les autres critères.
  8. Vérifier les groupes et les contrôles.
  9. Saisir un nouveau nom.
  10. Enregistrer une seule fois.
  11. Quitter ou désactiver les filtres.
  12. Vérifier le résultat dans Description.
  13. Vérifier les zéros, les notes, les tags et la provenance.
  14. Sauvegarder le projet.
  15. Exporter le dataset final.

16. Résolution des problèmes et contrôles#

Problèmes de paramétrage#

Symptôme Cause probable Action
Des filtres anciens sont appliqués au nouveau dataset Les paramètres persistent Vérifier tous les blocs après changement
Box verte mais aucune suppression Bloc activé avec critères neutres Vérifier les seuils et le résumé
Box orange Paramètres modifiés, bloc désactivé Activer ou remettre les valeurs neutres
Activation taxonomique supprime immédiatement des ASV Mots-clés présélectionnés Vérifier chloroplast et mitochondria
Résultat indisponible Condition avancée incomplète ou filtre trop strict Compléter, supprimer ou assouplir
Tous les taxons ou échantillons seraient supprimés Critères contradictoires ou excessifs Réduire les seuils et vérifier les valeurs

Problèmes liés aux seuils#

Symptôme Explication
Une ASV ayant exactement le seuil total est supprimée Le total utilise >
Une ASV peu abondante passe le seuil relatif Elle est importante dans au moins un échantillon
Un échantillon au-dessus du seuil graphique est supprimé Le seuil réel est appliqué après retrait des taxons
Une valeur manquante est supprimée avec Garder Elle ne satisfait pas la condition
Une valeur manquante reste avec Exclure Elle ne correspond pas au critère avant inversion
Les conditions avancées sont très restrictives Elles sont combinées par ET
Impossible de créer un OU entre variables Cette logique n’est pas proposée directement

Problèmes de séquences#

Maximum d’homopolymère à zéro ne filtre pas Zéro désactive le filtre

Checklist avant filtration#

  • Vérifier le dataset et le projet actifs.
  • Sauvegarder le projet.
  • Conserver une version brute.
  • Vérifier que les abondances sont adaptées aux seuils.
  • Vérifier l’orientation de l’OTU table.
  • Vérifier taxonomie, metadata et RefSeq.
  • Définir l’objectif de chaque filtre.
  • Vérifier les paramètres hérités d’un autre dataset.

Checklist avant enregistrement#

  • Lire le résumé complet.
  • Vérifier ASV et échantillons avant/après.
  • Vérifier les étapes ignorées.
  • Vérifier les conditions avancées.
  • Saisir un nouveau nom pour conserver le parent.
  • Cliquer une seule fois sur Enregistrer.
  • Ne pas confondre enregistrement et sauvegarde du projet.

Checklist après enregistrement#

  • Ouvrir Description.
  • Vérifier les dimensions.
  • Vérifier les reads et la richesse.
  • Vérifier les taxons et échantillons à zéro.
  • Vérifier les effectifs par groupe.
  • Vérifier taxonomie, RefSeq et arbre.
  • Vérifier notes, tags et journal.
  • Sauvegarder dans Datasets.
  • Exporter le dataset final.

17. Limites principales du module#

Les principales limites à conserver en tête sont les suivantes :

  • recalcul automatique potentiellement coûteux ;
  • histogrammes basés sur le parent brut ;
  • ordre des filtres imposé ;
  • absence de réévaluation itérative des seuils ;
  • absence de nettoyage final des zéros ;
  • paramètres persistants lors du changement de dataset ;
  • mots-clés taxonomiques présélectionnés ;
  • gestion limitée des dates et classes particulières ;
  • logique ET uniquement entre les conditions avancées ;
  • impossibilité d’imposer zéro ambiguïté avec le contrôle actuel ;
  • conservation possible d’ASV sans séquence ;
  • remplacement du journal précédent ;
  • absence de cause individuelle systématique ;
  • métriques des supprimés calculées sur le parent brut ;
  • perte possible d’attributs personnalisés ;
  • écrasement du parent sans confirmation lorsque le nom est vide ;
  • réapplication automatique des filtres après enregistrement ;
  • absence de sauvegarde sur disque depuis le bouton Enregistrer ;
  • détection multilingue imparfaite des blocs actifs ;
  • orientations d’export parfois ambiguës ;
  • export BIOM minimal et dépendant de biomformat.
