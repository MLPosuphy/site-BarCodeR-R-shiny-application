Input data — Guides méthodologiques

1. Présentation générale#

L’onglet Input data permet d’introduire dans BarCodeR un ou plusieurs objets phyloseq déjà construits.

Il accepte des objets R sérialisés dans les formats suivants :

  • .rds ;
  • .RData ;
  • .rda ;
  • .rdata.

L’application détermine automatiquement si le fichier contient :

  1. un seul dataset phyloseq ;
  2. un projet contenant plusieurs datasets phyloseq ;
  3. plusieurs objets compatibles parmi lesquels l’utilisateur doit choisir ;
  4. un objet non reconnu, auquel cas l’import est refusé.

L’onglet ne reconstruit pas un objet phyloseq à partir de tables indépendantes. Il charge des objets R déjà sérialisés.

2. Place d’Input data dans BarCodeR#

Input data est l’une des portes d’entrée des données dans BarCodeR.

Besoin Onglet à utiliser
Charger un objet phyloseq existant Input data
Charger plusieurs phyloseq contenus dans un projet .rds Input data
Récupérer un phyloseq produit sur le cluster OpenMetaBar
Construire ou compléter un phyloseq à partir de tables séparées Data Edition
Renommer, dupliquer, supprimer ou exporter un dataset Datasets
Importer une archive complète avec les figures et l’historique Datasets
Recharger la sauvegarde interne du projet courant Datasets

2.1. Ce qu’Input data ne gère plus#

Dans la version actuelle, Input data ne permet plus directement :

  • de supprimer un dataset ;
  • de renommer un dataset déjà chargé ;
  • de dupliquer un dataset ;
  • d’exporter un dataset ;
  • de gérer les projets nommés de BarCodeR.

Ces opérations sont centralisées dans l’onglet Datasets.

3. Interface actuelle#

L’interface d’Input data contient une seule zone principale :

Charger un fichier (.rds / .RData / .rda)

Elle comprend :

  • un rappel du fonctionnement automatique ;
  • un sélecteur de fichier ;
  • une indication sur le nettoyage appliqué ;
  • un rappel indiquant que la gestion des datasets se fait dans l’onglet Datasets.

Il n’existe plus :

  • de sélecteur séparé « Charger un dataset » ;
  • de sélecteur séparé « Charger un projet » ;
  • de choix manuel de l’orientation de l’OTU table ;
  • de case permettant de transposer la metadata ;
  • de case permettant de corriger la taxonomie ;
  • de zone de suppression.

Le type du fichier est déterminé automatiquement après sa lecture.

4. Limite de taille du fichier#

Le fichier est chargé par un composant Shiny fileInput.

La limite globale configurée dans BarCodeR est actuellement :

500 Mo

Un fichier dépassant cette limite ne peut normalement pas être transféré par ce champ.

4.1. Taille sur le disque et taille en mémoire#

Un fichier .rds peut être compressé. Sa taille sur le disque peut donc être nettement inférieure à la taille de l’objet une fois chargé dans R.

Par exemple, un fichier de 300 Mo peut nécessiter beaucoup plus de 300 Mo de mémoire vive lors de :

  • son transfert ;
  • sa décompression ;
  • sa lecture ;
  • sa copie lors du nettoyage ;
  • son insertion dans le registre des datasets.

Il faut donc disposer de suffisamment de mémoire pour contenir simultanément :

  • l’objet chargé ;
  • les datasets déjà présents ;
  • les copies temporaires créées pendant le traitement.

4.2. Application exécutée sur un serveur distant#

Lorsque BarCodeR est exécuté sur une autre machine, le fichier est envoyé au serveur Shiny.

Le temps de chargement dépend alors :

  • de la taille du fichier ;
  • de la vitesse du réseau ;
  • de la charge du serveur ;
  • de la mémoire disponible.

La lecture et le nettoyage sont synchrones. L’interface peut donc paraître momentanément figée pendant l’import d’un objet volumineux.

5. Formats de fichiers acceptés#

5.1. Fichier .rds#

Un fichier .rds contient un seul objet R.

L’application le lit avec readRDS() puis détermine sa nature.

Le nom proposé pour le dataset est dérivé du nom du fichier, sans extension.

Exemple :

metabarcoding_coi.rds

donnera initialement :

metabarcoding_coi

5.2. Fichier .RData ou .rda#

Un fichier .RData peut contenir plusieurs objets R.

BarCodeR :

  1. charge le fichier dans un environnement temporaire isolé ;
  2. inspecte chaque objet ;
  3. conserve uniquement les objets reconnus comme dataset ou projet ;
  4. sélectionne automatiquement l’objet s’il n’y en a qu’un ;
  5. demande à l’utilisateur de choisir s’il y en a plusieurs.

Les objets non compatibles présents dans le fichier sont ignorés.

5.3. Extensions non prises en charge#

Input data n’accepte pas directement :

  • .csv ;
  • .tsv ;
  • .xlsx ;
  • .biom ;
  • .qza ;
  • .zip ;
  • .RDS.gz ;
  • FASTA ;
  • FASTQ ;
  • Newick.

Les tables indépendantes doivent être traitées dans les modules adaptés de Data Edition.

Les archives .zip d’un projet BarCodeR complet doivent être importées dans Datasets.

6. Détection automatique du contenu#

Le type de contenu est déterminé par la structure réelle de l’objet et non uniquement par son nom ou son extension.

6.1. Dataset unique#

Un objet est reconnu comme dataset lorsqu’il hérite de la classe :

phyloseq

6.2. Projet#

Un objet est reconnu comme projet dans l’un des cas suivants :

Structure moderne

L’objet est une liste contenant un élément :

datasets

Structure historique

L’objet est une liste contenant un élément :

ps_registry

Liste simple de phyloseq

L’objet est une liste non vide dont tous les éléments sont des objets phyloseq.

6.3. Détection structurelle#

La reconnaissance d’un projet ne dépend pas obligatoirement :

  • d’un numéro de version ;
  • d’un champ format particulier ;
  • du nom du fichier ;
  • d’un nom de classe spécifique.

Elle repose principalement sur la présence et la structure des listes.

Cela permet de relire plusieurs anciennes formes de sauvegarde, mais signifie également qu’une liste arbitraire nommée datasets peut être interprétée comme un projet.

7. Différence entre dataset et projet#

7.1. Dataset#

Un dataset correspond à un seul objet phyloseq.

Il peut contenir :

  • une otu_table ;
  • une sample_data ;
  • une tax_table ;
  • un arbre phylogénétique ;
  • des séquences de référence.

Seule l’OTU table est réellement obligatoire pour l’import dans le registre général.

7.2. Projet .rds chargé par Input data#

Un projet .rds contient principalement :

  • une liste de datasets ;
  • le nom du dataset actif ;
  • éventuellement des métadonnées de sauvegarde.

Le format produit par le bouton Exporter les données seules, sans les figures (.rds) dans l’onglet Datasets contient actuellement une structure proche de :

list(
  version = 2,
  format = "version_ok_project",
  saved_at = ...,
  datasets = ...,
  active_ds = ...
)

7.3. Projet complet .zip#

Un projet .zip exporté depuis l’onglet Datasets peut également contenir :

  • les datasets ;
  • l’historique des figures ;
  • les fichiers associés aux modules ;
  • les paramètres sauvegardés ;
  • le manifeste du projet.

Cette archive complète n’est pas importée par Input data.

Elle doit être chargée dans Datasets → Importer un projet (.zip).

7.4. Input data ne change pas le projet courant de l’application#

Importer un projet .rds depuis Input data :

  • ne crée pas un nouveau projet nommé dans le gestionnaire ;
  • ne change pas automatiquement le projet courant ;
  • ne restaure pas les figures ;
  • ne restaure pas les historiques des modules ;
  • ne restaure pas toute la navigation.

Il ajoute ou remplace uniquement les datasets présents dans la mémoire du projet actuellement ouvert.

8. Charger un fichier#

8.1. Sélection du fichier#

Cliquer sur le sélecteur et choisir un seul fichier compatible.

Le champ n’accepte qu’un fichier à la fois.

Après la sélection, BarCodeR lit immédiatement le contenu afin de déterminer le parcours suivant.

8.2. En cas d’erreur de lecture#

L’import est interrompu si :

  • le fichier est corrompu ;
  • le fichier n’est pas un fichier R valide ;
  • l’extension ne correspond pas au contenu ;
  • l’objet a été sérialisé avec une classe ou un package indisponible ;
  • une dépendance nécessaire à la désérialisation manque.

Le champ de fichier est alors réinitialisé, ce qui permet de sélectionner de nouveau le même fichier après correction.

9. Fichier .RData contenant plusieurs objets#

Lorsque plusieurs objets compatibles sont détectés, une fenêtre intitulée Choisir l’objet à charger est affichée.

Chaque choix indique :

  • le nom de l’objet R ;
  • son type détecté : dataset ou projet.

Exemple :

ps_coi       (dataset)
ps_16s       (dataset)
my_project   (project)

9.1. Utiliser l’objet choisi#

Cliquer sur Utiliser cet objet poursuit le parcours correspondant.

9.2. Annuler#

Le bouton Annuler :

  • ferme la fenêtre ;
  • vide le sélecteur de fichier ;
  • supprime l’objet temporaire de la zone d’attente.

9.3. Utilisation de la croix supérieure#

La croix située en haut de la fenêtre ferme visuellement la modale, mais ne réalise pas exactement le même nettoyage que le bouton Annuler dans l’implémentation actuelle.

Après une fermeture par la croix, il peut être nécessaire de :

  • sélectionner un autre fichier ;
  • puis sélectionner de nouveau le fichier initial ;
  • ou actualiser le champ ;

pour redéclencher l’événement.

Pour abandonner proprement une sélection en cours, utiliser de préférence le bouton Annuler.

10. Charger un dataset phyloseq unique#

Lorsqu’un dataset est détecté, BarCodeR ouvre une fenêtre Préparer le chargement du dataset.

Cette fenêtre permet principalement de :

  • choisir le nom du dataset ;
  • décider s’il faut l’ajouter ou remplacer les données en mémoire ;
  • consulter le nettoyage automatique qui sera appliqué.

11. Nom du dataset#

11.1. Nom proposé#

Pour un .rds, le nom est généralement dérivé du nom du fichier.

Pour un .RData, le nom de l’objet R est utilisé en priorité.

11.2. Nettoyage du nom#

Lors de la confirmation, le nom est nettoyé afin de pouvoir être utilisé dans l’application.

Les opérations comprennent notamment :

  • suppression des espaces en début et en fin ;
  • remplacement de caractères non autorisés par _ ;
  • suppression des _ situés aux extrémités ;
  • utilisation de dataset si le résultat est vide.

Les caractères conservés sont principalement :

  • les caractères alphanumériques ;
  • _ ;
  • -.

Le comportement exact des caractères non ASCII dépend également de la locale R utilisée.

11.3. Collision avec un nom existant#

En mode ajout, si un dataset portant déjà ce nom existe, BarCodeR ajoute automatiquement un suffixe.

COI
COI_2
COI_3

L’objet existant n’est donc pas écrasé silencieusement en mode ajout.

12. Ajouter ou remplacer#

Lorsque des datasets sont déjà présents, deux modes sont proposés.

12.1. Ajouter le dataset à la session courante#

Ce mode est sélectionné par défaut.

Il :

  • conserve tous les datasets présents ;
  • ajoute le nouveau dataset ;
  • rend son nom unique si nécessaire ;
  • définit le nouveau dataset comme dataset actif.

12.2. Remplacer ce qui est actuellement en mémoire#

Ce mode :

  • retire tous les datasets actuellement présents de la mémoire ;
  • conserve uniquement le nouveau dataset ;
  • définit ce dataset comme actif.

Attention : le remplacement agit sur la mémoire de la session courante. Il n’efface pas directement les fichiers sources sur le disque, mais les datasets non sauvegardés ou non exportés peuvent être perdus.

Avant de remplacer, il est recommandé de sauvegarder le projet courant dans l’onglet Datasets.

12.3. Session initialement vide#

Lorsqu’aucun dataset n’est présent, le choix ajout/remplacement n’est pas affiché.

Le chargement est traité comme un remplacement d’une liste vide.

13. Nettoyage réellement appliqué au phyloseq#

Le nettoyage est ciblé.

BarCodeR ne reconstruit pas entièrement l’objet et ne transpose pas automatiquement ses tables.

Les principales opérations sont :

  1. identification de l’axe des échantillons dans l’OTU table ;
  2. standardisation éventuelle des noms d’échantillons ;
  3. synchronisation de ces noms avec la metadata ;
  4. remplacement des cellules vides de la metadata par NA ;
  5. vérification de la cohérence de certains identifiants.

14. Orientation de l’OTU table#

BarCodeR conserve l’orientation existante de l’OTU table.

Il utilise taxa_are_rows() pour déterminer où se trouvent les échantillons.

14.1. Taxons en lignes#

Lorsque taxa_are_rows(ps) == TRUE, les taxons sont en lignes et les échantillons sont en colonnes.

Les noms d’échantillons à nettoyer sont donc les noms de colonnes.

14.2. Taxons en colonnes#

Lorsque taxa_are_rows(ps) == FALSE, les taxons sont en colonnes et les échantillons sont en lignes.

Les noms d’échantillons à nettoyer sont donc les noms de lignes.

14.3. Aucune transposition#

L’application ne force pas :

  • les ASV en lignes ;
  • les échantillons en colonnes ;
  • une orientation commune à tous les datasets.

Elle respecte la propriété taxa_are_rows de chaque objet.

L’ancienne documentation indiquant qu’une modale permettait de choisir l’orientation n’est plus conforme au module actuel.

15. Standardisation des noms d’échantillons#

Les noms d’échantillons de l’OTU table sont examinés et éventuellement modifiés.

15.1. Transformations appliquées#

La fonction réalise notamment :

  1. une tentative de translittération des caractères accentués ;
  2. la suppression des espaces externes ;
  3. le remplacement des espaces internes par _ ;
  4. le remplacement des caractères autres qu’alphanumériques ou _ par _ ;
  5. la fusion de plusieurs _ successifs ;
  6. la suppression des _ en début et en fin ;
  7. le remplacement des noms vides ;
  8. l’ajout de suffixes en cas de doublon.

15.2. Exemples#

Avant Après possible
Station 01 Station_01
Station-01 Station_01
Échantillon A Echantillon_A
sample/1 sample_1
sample sample
nom vide sample_1
deux fois sample sample, sample_1

15.3. Pourquoi les noms sont nettoyés#

Des noms complexes peuvent provoquer des problèmes dans :

  • les formules statistiques ;
  • les jointures entre tables ;
  • certains packages R ;
  • les noms de fichiers ;
  • les graphiques ;
  • les exports ;
  • les sélections Shiny.

15.4. Nettoyage non garanti dans tous les cas#

Le nettoyage de l’OTU table n’est conservé que si la metadata peut rester correctement alignée.

Lorsque BarCodeR ne peut pas établir de manière sûre la correspondance entre les noms de l’OTU table et les rownames de la metadata, il peut annuler le renommage de l’OTU table.

Dans ce cas :

  • les noms d’origine sont conservés ;
  • l’objet reste cohérent ;
  • un avertissement est affiché dans le rapport.

La cohérence entre les tables est prioritaire sur le nettoyage esthétique des identifiants.

16. Traitement de la metadata#

La sample_data est facultative.

Un phyloseq sans metadata peut être importé, mais les analyses nécessitant des variables d’échantillons resteront indisponibles.

16.1. Alignement des rownames#

Lorsque la metadata est présente, BarCodeR essaie d’aligner ses rownames sur les noms d’échantillons de l’OTU table.

Cas sûr

Lorsque les rownames de la metadata correspondent aux noms originaux de l’OTU table :

  • les mêmes transformations sont appliquées ;
  • l’OTU table et la metadata restent synchronisées.

Cas de repli

Lorsque la correspondance directe n’est pas démontrée, BarCodeR tente de nettoyer la metadata séparément.

Ce nettoyage n’est appliqué que si les nouveaux noms restent compatibles avec ceux de l’OTU table.

Correspondance incertaine

Si la correspondance n’est pas sûre :

  • la metadata conserve ses noms ;
  • le renommage de l’OTU table peut être annulé ;
  • un avertissement est inscrit dans le rapport.

17. Cellules vides de la metadata#

Les cellules contenant une chaîne vide ou uniquement des espaces sont remplacées par de vrais NA.

Valeur d’origine Valeur après import
"" NA
" " NA
"0" "0"
"NA" "NA"
vrai NA NA

La chaîne de caractères "NA" n’est pas automatiquement transformée en valeur manquante.

17.1. Conséquence sur les types des colonnes#

Dans l’implémentation actuelle, chaque colonne de la metadata passe par une conversion en caractères avant le remplacement des valeurs vides.

Cela signifie que des colonnes initialement :

  • numériques ;
  • entières ;
  • logiques ;
  • facteurs ;
  • dates ;

peuvent revenir dans la sample_data sous forme de colonnes de caractères.

Une variable numérique devenue texte peut ne plus être directement utilisable comme variable quantitative. Une variable de date peut perdre sa classe Date. Un facteur peut perdre l’ordre de ses niveaux.

Après l’import, il faut donc vérifier les types des colonnes dans Description, Data Edition, ou dans R avant l’utilisation du fichier.

Ce comportement doit être considéré comme une transformation réelle des données, et pas uniquement comme un remplacement visuel des cellules vides.

18. Éléments du phyloseq qui ne sont pas modifiés#

Input data ne modifie pas directement :

  • les abondances de l’OTU table ;
  • l’orientation de l’OTU table ;
  • les noms des taxons ou ASV ;
  • les valeurs de la taxonomy table ;
  • les noms des rangs taxonomiques ;
  • les séquences de référence ;
  • l’arbre phylogénétique ;
  • les zéros ;
  • les taxons sans reads ;
  • les échantillons sans reads ;
  • les valeurs négatives ou décimales ;
  • les NA éventuellement présents dans l’OTU table.

Il ne réalise donc pas un contrôle scientifique exhaustif de l’objet.

19. Vérification de cohérence d’un dataset unique#

Après le nettoyage, un garde de cohérence est appliqué.

19.1. Classe phyloseq#

L’objet doit être un véritable objet phyloseq.

19.2. OTU table obligatoire#

L’objet doit contenir une otu_table.

Sans OTU table, les analyses principales de BarCodeR sont impossibles.

19.3. Correspondance des échantillons#

Si une sample_data est présente, ses rownames doivent correspondre à l’ensemble des noms d’échantillons de l’objet.

La comparaison est réalisée comme un ensemble : l’ordre peut être différent, mais les identifiants doivent correspondre.

Une metadata partielle ne couvrant qu’une partie des échantillons est refusée par ce garde.

19.4. Correspondance des taxons#

Si une tax_table est présente, ses rownames doivent correspondre aux noms des taxons de l’OTU table.

Une taxonomie ne couvrant qu’une partie des ASV est refusée.

19.5. Éléments non contrôlés par ce garde#

Le contrôle général d’Input data ne vérifie pas directement :

  • la couverture des taxons dans refseq ;
  • la couverture des taxons dans l’arbre ;
  • la validité des séquences ;
  • la nature entière des abondances ;
  • l’absence de valeurs négatives ;
  • la cohérence biologique de la taxonomie ;
  • la présence de doublons taxonomiques ;
  • la profondeur minimale des échantillons.

Ces points peuvent être contrôlés dans d’autres modules ou en amont.

20. Import refusé pour incohérence#

L’import d’un dataset unique est refusé lorsque les identifiants ne sont pas alignés.

Le message peut indiquer :

  • une différence entre sample_data et l’OTU table ;
  • une différence entre tax_table et l’OTU table ;
  • l’absence d’OTU table ;
  • un objet non phyloseq.

Aucun dataset n’est alors ajouté à la session.

Le fichier d’origine n’est pas modifié.

21. Rapport après import d’un dataset#

Lorsque l’import réussit, une fenêtre intitulée Dataset chargé et vérifié est affichée.

21.1. Indicateurs généraux#

Le rapport présente notamment :

  • le nom du dataset ;
  • le nombre d’échantillons ;
  • le nombre de taxons ou ASV ;
  • le nombre total d’actions réalisées.

Le nombre d’actions est calculé à partir :

  • des noms modifiés dans l’OTU table ;
  • des noms modifiés dans la metadata ;
  • des cellules vides remplacées.

Une même correction de nom peut être comptée une fois dans l’OTU table et une fois dans la metadata.

21.2. Source du chargement#

Le rapport indique :

  • le nom du fichier ;
  • le nom de l’objet R pour un .RData ;
  • le mode ajout ou remplacement ;
  • le nombre total de datasets en mémoire.

21.3. Détail des renommages#

Le rapport affiche des tableaux Avant → Après pour :

  • les noms d’échantillons de l’OTU table ;
  • les rownames de la metadata.

L’aperçu est limité aux dix premières modifications.

Le nombre total de modifications reste indiqué lorsque la liste est plus longue.

21.4. Cellules vides#

Le rapport indique combien de cellules vides de la metadata ont été remplacées par NA.

21.5. Avertissements#

Un bloc spécifique apparaît lorsque le nettoyage n’a pas pu être appliqué sans risque.

Exemple :

Les noms d’échantillons de l’OTU table n’ont pas été standardisés, car ils ne correspondaient pas de façon sûre à la metadata.

21.6. Notes#

Les notes peuvent indiquer :

  • qu’aucune modification n’était nécessaire ;
  • que la metadata était absente ;
  • que les noms ont été synchronisés ;
  • que certains noms ont volontairement été conservés.

22. Charger un projet .rds#

Lorsqu’un projet est détecté, BarCodeR récupère les datasets phyloseq qu’il contient.

22.1. Session vide#

Si aucun dataset n’est déjà présent, le projet est chargé directement en mode remplacement.

Aucune fenêtre ajout/remplacement n’est nécessaire puisqu’il n’y a rien à préserver en mémoire.

Un rapport de restauration est ensuite affiché.

22.2. Session contenant déjà des datasets#

Une fenêtre intitulée Charger un projet affiche :

  • la liste des datasets actuellement en mémoire ;
  • la liste des noms détectés dans le projet chargé ;
  • le choix entre ajout et remplacement.

23. Ajouter les datasets d’un projet#

Le mode ajout :

  • conserve les datasets déjà présents ;
  • ajoute chaque phyloseq importé ;
  • résout automatiquement les collisions de noms ;
  • adapte le dataset actif.

23.1. Collision de noms#

Si le projet contient un dataset COI alors que COI existe déjà :

COI
COI_2

Le rapport utilise le nom final attribué.

23.2. Dataset actif après ajout#

Si le projet contient un active_ds valide, le dataset correspondant devient normalement actif après son ajout.

Si ce nom a été modifié pour éviter une collision, le nouveau nom est utilisé.

Si aucun actif valide n’est défini, le premier dataset importé devient actif.

24. Remplacer par les datasets d’un projet#

Le mode remplacement :

  • retire tous les datasets actuellement en mémoire ;
  • charge la liste importée ;
  • restaure le dataset actif du projet si son nom est valide ;
  • sinon sélectionne le premier dataset importé.

Le remplacement ne supprime pas directement des fichiers sur le disque.

Il peut néanmoins entraîner la perte de datasets non sauvegardés dans le projet courant.

25. Noms des datasets d’un projet#

Si la liste de datasets possède des noms valides, ils sont conservés, sous réserve de collision en mode ajout.

Si les noms de la liste sont absents, vides ou partiellement manquants, l’application attribue des noms génériques :

dataset_1
dataset_2
dataset_3

Dans l’implémentation actuelle, la présence d’au moins un nom manquant peut entraîner la régénération de l’ensemble des noms de la liste, et pas uniquement du nom manquant.

26. Contenu non-phyloseq dans un projet#

Pour les structures contenant un élément datasets ou ps_registry, le projet est reconnu à partir de la présence de cette liste.

Au moment du chargement, seuls les éléments héritant réellement de phyloseq sont conservés.

Les autres éléments sont ignorés.

26.1. Conséquence#

La liste affichée avant l’import peut inclure des noms qui ne seront finalement pas chargés si leur contenu n’est pas un phyloseq.

Le rapport final doit être utilisé comme source de vérité pour connaître le nombre réel de datasets restaurés.

26.2. Projet ne contenant aucun phyloseq valide#

Un projet structurellement reconnu mais ne contenant aucun phyloseq exploitable peut produire un rapport indiquant zéro dataset restauré.

En mode remplacement, une telle structure peut aboutir à une liste de datasets vide.

Il faut donc vérifier le contenu du projet avant de confirmer un remplacement.

27. Nettoyage des datasets d’un projet#

Chaque objet phyloseq du projet passe par le même nettoyage général :

  • noms d’échantillons de l’OTU table ;
  • rownames de la metadata ;
  • cellules vides transformées en NA.

Le rapport de projet présente un résumé par dataset :

  • nombre d’échantillons ;
  • nombre de taxons ;
  • nombre de noms OTU modifiés ;
  • nombre de noms de metadata modifiés ;
  • nombre de cellules vides remplacées.

Contrairement au rapport d’un dataset unique, le rapport de projet n’affiche pas l’intégralité des tableaux avant/après pour chaque dataset.

28. Différence de contrôle entre dataset et projet#

Un dataset unique passe explicitement par le garde général bcr_guard_ps() avant son insertion.

Le chargement d’un projet nettoie chaque phyloseq, mais n’appelle pas actuellement ce garde de manière explicite pour chaque élément avant d’insérer l’ensemble du projet.

28.1. Filet de sécurité global#

Lorsque le dataset actif change, BarCodeR vérifie néanmoins sa cohérence.

Si le dataset actif importé depuis un projet est incohérent, une notification d’avertissement peut apparaître.

Les autres datasets du projet seront vérifiés lorsqu’ils deviendront actifs.

28.2. Conséquence pratique#

Après l’import d’un projet, il est recommandé de sélectionner chaque dataset important et de vérifier :

  • l’absence d’avertissement de cohérence ;
  • le contenu de Description ;
  • les dimensions ;
  • les tables présentes ;
  • les correspondances d’identifiants.

29. Import et mémoire de la session#

Les datasets sont stockés dans un registre réactif en mémoire :

datasets()

Le nom du dataset actif est stocké séparément :

active_ds()

Après un import :

  • le registre est modifié ;
  • le dataset importé ou actif est sélectionné ;
  • les autres onglets accèdent à ce nouveau contenu ;
  • l’état du projet courant devient modifié et non sauvegardé.

29.1. L’import n’est pas une sauvegarde#

Charger un fichier dans Input data ne sauvegarde pas automatiquement le registre dans le projet courant.

Pour conserver l’état après fermeture, utiliser Datasets → Sauvegarder le projet.

Le voyant global de sauvegarde indique normalement que des modifications sont en attente.

30. Dataset actif#

Le dataset actif est celui utilisé par défaut par de nombreux modules.

Après l’import d’un dataset unique, le dataset importé devient actif.

Après le remplacement par un projet, le dataset actif enregistré dans le projet est restauré s’il existe ; sinon le premier dataset est choisi.

Après l’ajout d’un projet, le dataset actif importé devient généralement actif ; sinon le premier dataset nouvellement ajouté est choisi.

Le dataset actif peut ensuite être changé depuis :

  • le contrôle global de l’application ;
  • l’onglet Datasets ;
  • certains modules synchronisés.

31. Ce que l’import ne garantit pas scientifiquement#

Un import réussi signifie principalement que :

  • l’objet est lisible ;
  • il s’agit d’un phyloseq ;
  • une OTU table est présente ;
  • certains identifiants sont cohérents.

Cela ne garantit pas que :

  • les abondances sont des comptes bruts ;
  • les données n’ont pas déjà été transformées ;
  • les taxons sans reads ont été supprimés ;
  • les échantillons vides ont été supprimés ;
  • la taxonomie est correcte ;
  • les rangs sont ordonnés ;
  • les séquences correspondent aux ASV ;
  • l’arbre contient tous les taxons ;
  • le plan expérimental est valide ;
  • les groupes ont suffisamment de réplicats ;
  • les variables numériques ont conservé leur classe ;
  • les données sont adaptées à chaque analyse statistique.

32. Vérifications recommandées après l’import#

Après le chargement, ouvrir l’onglet Description.

32.1. Dimensions#

  • nombre d’échantillons ;
  • nombre de taxons ;
  • nombre total de reads.

32.2. Tables présentes#

  • OTU table ;
  • metadata ;
  • taxonomy table ;
  • arbre ;
  • séquences de référence.

32.3. Identifiants#

  • noms des échantillons ;
  • noms des ASV ;
  • éventuels renommages automatiques ;
  • doublons ou suffixes ajoutés.

32.4. Metadata#

  • types des colonnes ;
  • valeurs manquantes ;
  • variables quantitatives ;
  • facteurs ;
  • dates ;
  • groupes expérimentaux.

32.5. OTU table#

  • orientation ;
  • valeurs négatives ;
  • valeurs décimales ;
  • NA ;
  • échantillons à zéro read ;
  • taxons à zéro read.

32.6. Taxonomie#

  • rangs disponibles ;
  • noms des colonnes ;
  • valeurs non assignées ;
  • correspondance avec les ASV.

32.7. Arbre et séquences#

  • couverture des ASV ;
  • noms cohérents ;
  • disponibilité pour les modules qui les utilisent.

33. Gestion ultérieure des datasets#

Après l’import, utiliser l’onglet Datasets pour :

  • sélectionner le dataset actif ;
  • renommer un dataset ;
  • dupliquer un dataset ;
  • supprimer un dataset ;
  • exporter un dataset seul ;
  • exporter les données du projet ;
  • exporter un projet complet ;
  • sauvegarder le projet courant ;
  • restaurer la sauvegarde interne ;
  • changer de projet BarCodeR.

34. Résolution des problèmes#

34.1. Le fichier n’apparaît pas dans le sélecteur#

Causes possibles : extension non acceptée, fichier compressé, format différent de .rds, .RData ou .rda.

Correction : vérifier l’extension réelle du fichier.

34.2. Le fichier dépasse la taille autorisée#

La limite globale est de 500 Mo.

Solutions possibles : réduire l’objet, retirer les composants inutiles, séparer les datasets, exporter un dataset à la fois ou modifier la limite de l’application dans un environnement maîtrisé.

34.3. Le fichier est très petit mais consomme beaucoup de mémoire#

Le fichier est compressé et l’objet décompressé est beaucoup plus volumineux.

Libérer de la mémoire et éviter de conserver simultanément plusieurs copies volumineuses.

34.4. Erreur lors de la lecture du .rds#

Causes possibles : fichier corrompu, fichier incomplet, classe indisponible ou format différent malgré l’extension.

obj <- readRDS("fichier.rds")
class(obj)

34.5. Le .RData ne contient aucun objet reconnu#

Le fichier ne contient ni phyloseq, ni projet avec datasets, ni projet avec ps_registry, ni liste composée uniquement de phyloseq.

load("fichier.RData")
ls()
class(nom_objet)

34.6. Plusieurs objets apparaissent#

Ce comportement est normal pour un .RData contenant plusieurs objets compatibles. Sélectionner l’objet souhaité dans la modale.

34.7. L’objet est détecté comme projet alors que ce n’en est pas un#

L’objet est probablement une liste contenant un élément datasets ou ps_registry.

Recréer un fichier contenant directement l’objet phyloseq souhaité :

saveRDS(mon_phyloseq, "dataset.rds")

34.8. Import refusé : OTU table manquante#

phyloseq::otu_table(ps)

34.9. Import refusé : identifiants d’échantillons incohérents#

setequal(
  phyloseq::sample_names(ps),
  rownames(as.data.frame(phyloseq::sample_data(ps)))
)

Le résultat attendu est TRUE.

34.10. Import refusé : identifiants taxonomiques incohérents#

setequal(
  phyloseq::taxa_names(ps),
  rownames(as(phyloseq::tax_table(ps), "matrix"))
)

34.11. Une metadata partielle est refusée#

Le garde actuel exige la correspondance complète lorsque sample_data est présente.

Compléter les échantillons manquants, retirer proprement les échantillons non documentés ou reconstruire l’objet avec des tables alignées.

34.12. Les noms d’échantillons ont changé#

BarCodeR a standardisé les espaces, accents, tirets, caractères spéciaux ou doublons. Consulter le rapport avant/après affiché après l’import.

34.13. Les noms n’ont pas été nettoyés#

BarCodeR n’a pas pu réaligner la metadata de manière certaine et a annulé le renommage de l’OTU table.

Aligner manuellement les noms dans l’objet source, puis réexporter le phyloseq.

34.14. Une variable numérique est devenue texte#

Le nettoyage des cellules vides convertit actuellement les colonnes de metadata en caractères.

str(as.data.frame(phyloseq::sample_data(ps)))
metadata$Depth <- as.numeric(metadata$Depth)

Vérifier préalablement que les valeurs sont réellement numériques.

34.15. La chaîne "NA" n’est pas considérée comme manquante#

Seules les chaînes vides ou composées d’espaces sont remplacées.

metadata[metadata == "NA"] <- NA

Cette opération doit être réalisée avec prudence pour ne pas modifier une valeur textuelle légitime.

34.16. Le projet charge moins de datasets que prévu#

Certains éléments peuvent ne pas être des phyloseq ou avoir été ignorés. Comparer le nombre attendu avec le rapport final.

34.17. Les noms d’un projet ont tous été remplacés par dataset_1, etc.#

Au moins un nom de la liste était absent ou vide.

names(project$datasets) <- c("COI", "16S", "ITS")

34.18. Un dataset a reçu un suffixe _2#

Un dataset de même nom était déjà présent et le mode ajout a été choisi. Ce comportement protège l’objet existant.

34.19. Tous les datasets précédents ont disparu#

Le mode remplacement a probablement été confirmé. Restaurer le projet depuis le disque, recharger un export .rds, importer une archive .zip ou recharger les datasets sources.

34.20. Le projet .rds n’a pas restauré les figures#

Le format .rds chargé par Input data contient les données seules. Utiliser l’archive complète .zip dans l’onglet Datasets pour restaurer les figures et les historiques.

34.21. Le même fichier ne redéclenche pas l’import#

La modale précédente a peut-être été fermée avec la croix supérieure au lieu du bouton Annuler. Utiliser Annuler lors du prochain abandon, sélectionner temporairement un autre fichier ou actualiser l’onglet.

34.22. Le phyloseq importé n’a pas de metadata#

Ce n’est pas obligatoirement une erreur. Les analyses nécessitant des variables d’échantillons resteront indisponibles jusqu’à l’ajout d’une metadata.

34.23. Le phyloseq importé n’a pas de taxonomie#

L’import peut réussir, mais les analyses et visualisations nécessitant une tax_table ne pourront pas fonctionner correctement.

34.24. Le phyloseq importé n’a pas d’arbre#

L’import peut réussir. Les méthodes nécessitant un arbre, notamment certaines distances UniFrac, seront indisponibles.

34.25. Le phyloseq importé n’a pas de séquences de référence#

L’import peut réussir. Les analyses utilisant directement les séquences ne seront pas disponibles.

35. Checklist avant l’import#

Fichier#

  • Le fichier est un .rds, .RData ou .rda.
  • Sa taille est inférieure à 500 Mo.
  • La mémoire disponible est suffisante.
  • Le fichier peut être lu dans R.

Objet phyloseq#

  • Une OTU table est présente.
  • Les IDs des échantillons sont uniques.
  • Les IDs des taxons sont uniques.
  • La metadata couvre tous les échantillons si elle est présente.
  • La taxonomie couvre tous les taxons si elle est présente.
  • Les séquences et l’arbre sont cohérents s’ils sont présents.

Metadata#

  • Les valeurs manquantes sont identifiées.
  • Les colonnes numériques sont reconnues.
  • Les facteurs ordonnés sont documentés.
  • Les dates sont documentées.
  • Les noms d’échantillons sont cohérents avec l’OTU table.

Session courante#

  • Les datasets déjà présents ont été sauvegardés.
  • Le choix ajout/remplacement est compris.
  • Les collisions de noms sont anticipées.

36. Checklist après l’import#

  • Lire entièrement le rapport de nettoyage.
  • Vérifier les renommages d’échantillons.
  • Vérifier le nombre d’échantillons.
  • Vérifier le nombre de taxons.
  • Vérifier les types des colonnes de metadata.
  • Vérifier les cellules transformées en NA.
  • Ouvrir Description.
  • Vérifier l’OTU table.
  • Vérifier la taxonomie.
  • Vérifier les séquences et l’arbre.
  • Sauvegarder le projet depuis Datasets.

37. Limites actuelles à connaître#

37.1. Pas de contrôle scientifique exhaustif#

L’import ne vérifie pas la validité biologique des données.

37.2. Conversion des colonnes de metadata#

Toutes les colonnes passent actuellement par une représentation textuelle lors du nettoyage des cellules vides.

37.3. Pas de transposition#

L’orientation existante est conservée.

37.4. Pas de correction taxonomique#

Les rangs taxonomiques et les valeurs ne sont pas nettoyés.

37.5. Validation moins stricte pour les projets#

Le garde d’intégrité explicite est appliqué aux datasets uniques, mais pas individuellement à tous les phyloseq d’un projet avant leur insertion.

37.6. Projet structurellement reconnu#

Une liste possédant datasets ou ps_registry peut être reconnue même si son contenu n’est pas entièrement valide.

37.7. Fermeture par la croix#

La croix supérieure ne réinitialise pas toujours tout l’état temporaire comme le bouton Annuler.

37.8. Taille maximale de 500 Mo#

Le chargement de projets de données très volumineux peut nécessiter une autre stratégie.

38. Parcours recommandé#

Le parcours le plus sûr est :

  1. construire et vérifier l’objet phyloseq dans R ;
  2. l’enregistrer avec saveRDS() ;
  3. ouvrir Input data ;
  4. charger le fichier ;
  5. choisir ajout ou remplacement ;
  6. vérifier le nom du dataset ;
  7. confirmer l’import ;
  8. lire le rapport complet ;
  9. ouvrir Description ;
  10. contrôler les dimensions et les tables ;
  11. vérifier les types de metadata ;
  12. sauvegarder le projet dans Datasets.

39. Exemple de préparation d’un dataset unique#

library(phyloseq)

stopifnot(inherits(ps, "phyloseq"))
stopifnot(!is.null(otu_table(ps)))

if (!is.null(sample_data(ps, errorIfNULL = FALSE))) {
  stopifnot(
    setequal(
      sample_names(ps),
      rownames(as.data.frame(sample_data(ps)))
    )
  )
}

if (!is.null(tax_table(ps, errorIfNULL = FALSE))) {
  stopifnot(
    setequal(
      taxa_names(ps),
      rownames(as(tax_table(ps), "matrix"))
    )
  )
}

saveRDS(ps, "dataset_phyloseq.rds")

40. Exemple de projet de données compatible#

project <- list(
  version = 2,
  format = "version_ok_project",
  saved_at = Sys.time(),
  datasets = list(
    COI = ps_coi,
    `16S` = ps_16s
  ),
  active_ds = "COI"
)

saveRDS(project, "project_data_only.rds")

Ce fichier peut être chargé dans Input data.

Il ne contient pas nécessairement les figures et historiques de BarCodeR.

41. Principes de traçabilité#

Pour conserver une provenance claire :

  • garder le fichier source original ;
  • ne pas écraser l’export précédent ;
  • noter la date d’export ;
  • conserver le nom de l’objet ;
  • vérifier le rapport de nettoyage ;
  • documenter les noms automatiquement modifiés ;
  • vérifier les types de metadata ;
  • enregistrer le projet BarCodeR après l’import ;
  • distinguer l’objet source de l’objet nettoyé en mémoire.

L’objet présent dans BarCodeR peut différer du fichier source à cause :

  • du nettoyage des noms d’échantillons ;
  • de la synchronisation avec la metadata ;
  • du remplacement des cellules vides ;
  • de la conversion des colonnes de metadata.
