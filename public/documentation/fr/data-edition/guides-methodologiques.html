Data Edition — Guides méthodologiques

1. Présentation générale#

L’onglet Data Edition permet de modifier directement les composants internes d’un dataset phyloseq déjà chargé dans BarCodeR : métadonnées, abondances, taxonomie, séquences de référence et arbre phylogénétique.

Il permet également d’importer ou d’exporter des composants, de supprimer certains slots, de renommer automatiquement les ASV et de conserver un journal descriptif des opérations.

2. Principe fondamental : les modifications sont immédiates#

Data Edition n’est pas un brouillon séparé. La majorité des actions modifient immédiatement le dataset sélectionné dans datasets() : édition de cellule, ajout ou suppression de colonne, fusion, renommage d’ASV, remplacement taxonomique, import complet ou suppression d’un composant.

3. Le bouton « Enregistrer » ne valide pas les modifications#

Les modifications sont déjà appliquées avant le clic. Le bouton Enregistrer sert à réinscrire l’état courant sous le même nom, à créer une nouvelle entrée ou à remplacer une autre entrée du registre. Il ne sauvegarde pas le projet sur le disque.

4. Conséquence importante pour la version originale#

Si COI_raw est édité puis enregistré sous COI_edited, COI_raw a déjà été modifié. COI_edited reçoit seulement une copie du même état modifié.

Avant une édition importante, dupliquer le dataset dans Datasets, puis éditer uniquement la copie.

5. Effet sur les fichiers sources#

Data Edition ne modifie pas les fichiers .rds, .RData, CSV, FASTA, Newick ou les résultats distants. Il modifie l’objet en mémoire. Pour rendre les changements persistants, sauvegarder le projet ou exporter le dataset.

6. Organisation de l’onglet#

L’onglet contient : sélection du dataset, édition des métadonnées, édition OTU, édition taxonomique, import/export/suppression des composants, logs et enregistrement dans le registre.

7. Dataset à éditer#

Le sélecteur contient les datasets présents dans le registre et est synchronisé avec active_ds(). Changer de dataset dans Data Edition change donc le dataset actif global.

8. Changement de dataset pendant une édition#

Changer de dataset recharge les états locaux des trois éditeurs et réinitialise les états initial, précédent et les aperçus. L’état initial correspond au moment où le sous-module charge le dataset, pas forcément au fichier d’origine.

9. Réinitialisation après un aller-retour entre datasets#

Après avoir modifié COI, ouvert 16S, puis rouvert COI, l’état initial local de COI correspond à sa version déjà modifiée. Réinitialiser ne revient plus à la version antérieure à la première édition.

10. Éditions et persistance du projet#

Chaque action met à jour datasets() et marque potentiellement le projet comme non sauvegardé. Pour conserver les changements après fermeture, utiliser Datasets → Sauvegarder le projet.

11. Différence entre les deux types d’import#

Les boutons Fusionner des éditeurs ajoutent seulement des colonnes absentes en utilisant les identifiants communs. L’import complet remplace entièrement le composant sélectionné dès le choix du fichier.

12. Ce que Data Edition n’est pas conçu pour faire#

Data Edition n’est pas l’outil principal pour filtrer des taxons ou échantillons, normaliser, transformer les abondances ou appliquer des seuils biologiques. Ces opérations relèvent surtout de Filtration ou de pipelines dédiés.

13. Historique des modifications#

Les actions peuvent ajouter une entrée à attr(ps, "edit_log"), comprenant date, dataset, table, action, description, dimensions avant/après et avertissements.

14. Le journal n’est pas une sauvegarde#

Le journal ne contient pas les anciennes tables complètes. Il permet un audit descriptif, mais ne constitue pas un versionnement ni un mécanisme général de restauration.

15. Langue du journal#

Les actions et avertissements enregistrés dans edit_log restent en français, quelle que soit la langue de l’interface.

16. Les trois vues des logs#

Dernière action globale montre la dernière action réalisée depuis l’ouverture du module. Historique complet affiche edit_log. Résumé synthétique agrège nombres d’actions, tables concernées, avertissements et période.

17. Actions comptées dans le total#

Le total peut inclure éditions, ajouts, suppressions, imports, exports, annulations, réinitialisations, enregistrements, renommages et synchronisations automatiques.

18. Annulation : une seule étape#

Chaque sous-module conserve un seul état précédent. Le bouton Annuler ne parcourt pas tout le journal. Des clics répétés peuvent alterner entre deux états récents.

19. Réinitialisation#

Réinitialiser restaure l’état local capturé au chargement du dataset dans le sous-module. L’action est immédiate, journalisée et annulable, mais ne garantit pas un retour au fichier original.

20. Édition des métadonnées — présentation#

Cette section agit sur sample_data(ps) et permet de modifier les valeurs, ajouter, supprimer ou renommer une variable, fusionner un fichier, annuler et réinitialiser.

21. Création automatique d’une metadata absente#

Si aucune metadata exploitable n’existe, l’ouverture crée automatiquement une sample_data minimale avec une colonne SampleID et une ligne par échantillon. Cette création peut modifier le dataset sans action explicite et sans entrée de journal dédiée.

22. Identifiants des échantillons#

Les vrais identifiants sont les rownames alignés sur sample_names(ps). La colonne SampleID est une variable ordinaire : modifier ses cellules ne renomme pas les échantillons de l’OTU table.

23. Table metadata éditable#

Les cellules sont modifiables directement. La modification est appliquée lors de sa validation ; il n’existe pas de bouton global d’application.

24. Traitement des facteurs#

Les facteurs sont convertis localement en caractères. Après la première réécriture, leurs niveaux et leur ordre peuvent être perdus.

25. Traitement des colonnes de listes#

Les colonnes de listes sont converties en texte, avec concaténation des éléments par virgule. Cette conversion peut être irréversible.

26. Édition d’une colonne numérique#

Le module essaie de préserver les colonnes numériques. Une valeur numérique valide reste numérique ; une cellule vide devient NA_real_. Une valeur non numérique peut convertir toute la colonne en texte et déclencher un avertissement.

27. Conséquence d’une conversion numérique vers texte#

Une covariable devenue character peut ne plus être utilisable comme variable continue dans les analyses statistiques. Vérifier les types après édition.

28. Colonnes logiques, dates et classes particulières#

Le traitement explicite concerne surtout les colonnes numériques. Les classes logical, Date, POSIXct, facteurs ordonnés ou classes personnalisées peuvent être perdues lors d’une édition.

29. Ajouter une colonne de metadata#

La nouvelle colonne est remplie avec NA. Son nom doit commencer par une lettre ASCII et contenir uniquement lettres, chiffres ou _, sans point et sans doublon.

30. Suggestions de noms compatibles#

Lorsqu’un nom est invalide, une suggestion normalisée peut être affichée, mais elle n’est pas appliquée automatiquement.

31. Renommer une colonne de metadata#

Le renommage conserve les valeurs, exige un nom valide et unique, mais ne renomme ni les rownames ni les noms d’échantillons.

32. Conséquence du renommage sur les analyses#

Les paramètres ou formules utilisant l’ancien nom ne sont pas mis à jour. Les modules concernés devront être reconfigurés.

33. Supprimer une colonne de metadata#

La suppression utilise le nom exact et est sensible à la casse. Des suggestions peuvent être proposées en cas de différence de casse ou de nom proche.

34. Suppression de la dernière colonne#

Aucune protection générale ne garantit qu’une colonne reste présente. Pour retirer complètement la metadata, utiliser la suppression du composant complet.

35. Cohérence des lignes de metadata#

À chaque application, les échantillons manquants sont ajoutés avec NA, la table est réordonnée selon sample_names(ps) et les lignes supplémentaires sont écartées.

36. Fusionner un fichier dans la metadata#

Les fichiers CSV, TSV et TXT sont acceptés. Le séparateur peut être virgule, point-virgule ou tabulation.

37. Détection automatique du séparateur metadata#

Le module analyse jusqu’à trente lignes non vides et compare régularité et nombre de champs. La détection peut être indiquée comme incertaine et corrigée manuellement.

38. Première colonne comme identifiants#

Lorsque l’option est activée, la première colonne devient les rownames du fichier. Sans cette option, les rownames numériques empêchent généralement la correspondance avec les échantillons.

39. Fusion metadata : comportement réel#

La fusion utilise les rownames communs, ajoute uniquement les colonnes absentes, remplit les échantillons communs et laisse NA pour les autres.

40. Colonnes déjà présentes#

Les colonnes existantes ne sont pas mises à jour. Si le fichier ne contient aucune nouvelle colonne, rien n’est modifié.

41. Échantillons supplémentaires dans le fichier de fusion#

Les identifiants absents du phyloseq sont ignorés et ne créent pas de nouveaux échantillons.

42. Échantillons absents du fichier de fusion#

Ils restent dans le dataset et reçoivent NA dans les nouvelles colonnes.

43. Édition de l’OTU table — présentation#

Cette section permet d’éditer une cellule, ajouter ou supprimer une colonne, fusionner un fichier, trier l’affichage, renommer les ASV, ajuster l’orientation déclarée, annuler et réinitialiser.

44. Orientation de l’OTU table#

L’éditeur conserve taxa_are_rows(otu_table(ps)). Si les taxons sont en lignes, les colonnes sont des échantillons. Sinon, les colonnes sont des taxons.

45. Le sélecteur « ASV en colonnes » n’est pas une transposition#

Le switch sert surtout au renommage automatique. Le modifier seul ne transpose pas la matrice et ne change pas immédiatement taxa_are_rows.

46. Risque d’un mauvais choix d’axe#

Un mauvais axe peut renommer les échantillons comme ASV, changer l’orientation déclarée et désynchroniser taxonomie, séquences et arbre.

47. Table OTU éditable#

Chaque cellule est modifiable et l’application reconstruit ensuite une matrice numérique.

48. Conversion numérique de l’OTU table#

Toute la table est convertie en numérique après l’action. Les valeurs non convertibles deviennent NA avec avertissement.

49. Valeurs vides dans l’OTU table#

Les cellules vides, espaces ou NA sont signalées mais ne sont pas automatiquement remplacées par zéro.

50. Valeurs non numériques#

Les textes tels que absent, low ou ? deviennent généralement NA après conversion.

51. Valeurs négatives et décimales#

Elles ne sont pas bloquées. Le module autorise donc techniquement comptes, proportions, valeurs transformées ou CLR, même si certaines analyses ne les accepteront pas.

52. Ajouter une colonne dans l’OTU table#

Avec taxons en lignes, une colonne ajoute un échantillon. Avec taxons en colonnes, elle ajoute un taxon. La colonne est initialisée avec NA.

53. Risques de l’ajout d’un échantillon#

Ajouter une colonne d’échantillon ne crée pas la ligne correspondante dans sample_data, ce qui peut désynchroniser le phyloseq.

54. Risques de l’ajout d’un taxon#

Ajouter un taxon ne crée ni taxonomie, ni séquence, ni feuille d’arbre. RefSeq ou l’arbre peuvent être supprimés s’ils deviennent incomplets.

55. Recommandation pour les ajouts structurels#

Pour ajouter de nouveaux taxons ou échantillons, reconstruire plutôt un phyloseq complet dans R et vérifier tous les identifiants.

56. Supprimer une colonne dans l’OTU table#

Selon l’orientation, cette action retire un échantillon ou un taxon. La metadata ou la taxonomie ne sont pas systématiquement synchronisées par cette action générique.

57. Utiliser Filtration pour les suppressions biologiques#

Pour retirer proprement des échantillons ou taxons selon des critères, utiliser Filtration, qui produit un sous-dataset documenté et cohérent.

58. Tri naturel des ASV#

Le tri affiche ASV1, ASV2, ASV10 dans l’ordre numérique naturel, sans modifier l’ordre interne.

59. Édition avec le tri activé#

Le module reporte la cellule affichée vers l’identifiant d’origine pour appliquer la modification au bon taxon.

60. Fusionner un fichier dans l’OTU table#

La fusion détecte le séparateur, utilise les rownames, recherche les lignes communes et ajoute uniquement de nouvelles colonnes.

61. Sens des colonnes importées#

Le sens des colonnes dépend de l’orientation actuelle. Le module ne déduit pas s’il s’agit d’échantillons ou de taxons.

62. Lignes supplémentaires dans le fichier OTU fusionné#

Les lignes absentes de la table courante sont ignorées et ne créent pas de nouveaux identifiants.

63. Lignes actuelles absentes du fichier#

Les nouvelles colonnes restent NA pour les lignes non présentes dans le fichier.

64. Renommage automatique des ASV#

Le renommage combine un préfixe, l’axe déclaré et les identifiants actuels.

65. Conservation des numéros finaux#

Si tous les identifiants finissent par des nombres uniques, ces nombres sont conservés : ASV128 peut devenir Feature128.

66. Renommage séquentiel#

Si au moins un identifiant ne possède pas de numéro final exploitable, tous sont renommés selon l’ordre interne : Feature1, Feature2, etc.

67. Collision des nouveaux noms#

Si les nouveaux noms ne sont pas uniques, un renommage séquentiel de repli est utilisé.

68. Validation du préfixe#

Le préfixe est seulement débarrassé de ses espaces externes. Utiliser un préfixe simple tel que ASV, OTU, ZOTU ou Feature.

69. Propagation du renommage des ASV#

Si les anciens identifiants sont uniques, les nouveaux noms sont propagés vers tax_table, refseq et les feuilles de l’arbre.

70. Doublons d’identifiants avant renommage#

En présence de doublons, la propagation est désactivée et le résultat peut rester incohérent. Corriger les doublons en amont.

71. Réalignement des séquences après modification OTU#

Les séquences sont nommées par ordre si elles n’ont pas de noms et si leur nombre correspond. Si elles couvrent les taxons, elles sont réordonnées. Si certaines ASV n’ont pas de séquence, toute refseq est supprimée.

72. Réalignement de l’arbre après modification OTU#

Les feuilles supplémentaires sont supprimées. Si certains taxons OTU manquent dans l’arbre, l’arbre entier est supprimé.

73. Package ape absent#

Si ape n’est pas disponible pendant une modification OTU, l’arbre est supprimé avec avertissement.

74. Taxonomie après modification structurelle OTU#

La propagation taxonomique est explicite lors du renommage des ASV, mais pas systématique pour tous les ajouts ou suppressions. Vérifier les identifiants après toute modification structurelle.

75. Édition de la taxonomie — présentation#

Cette section agit sur tax_table(ps) : édition de cellule, ajout ou suppression de rang, fusion de rangs, remplacement automatique, annulation et réinitialisation.

76. Taxonomie absente#

Si aucune table n’existe, utiliser l’import complet pour ajouter une taxonomie.

77. Confirmation avant la première édition taxonomique#

La première tentative affiche une fenêtre d’information et n’exécute pas l’action. Fermer la fenêtre puis répéter l’action.

78. Nouvelle confirmation après changement de dataset#

La confirmation est réinitialisée lorsque le dataset change et peut donc réapparaître.

79. Édition d’une cellule taxonomique#

La valeur est enregistrée comme texte. Aucune validation nomenclaturale ou taxonomique n’est effectuée.

80. Aucune vérification de hiérarchie#

Le module ne vérifie pas qu’une espèce appartient au genre, qu’un genre appartient à la famille ou que les noms sont valides.

81. Ajouter un rang taxonomique#

Une colonne remplie de NA est ajoutée à la fin. Le nom doit suivre les mêmes règles strictes que les colonnes metadata.

82. Ordre des rangs#

Aucun ordre taxonomique n’est imposé. Conserver manuellement un ordre cohérent du type Kingdom, Phylum, Class, Order, Family, Genus, Species.

83. Renommer un rang taxonomique#

Il n’existe pas de bouton direct. Il faut créer un nouveau rang, transférer les valeurs puis supprimer l’ancien, ou effectuer l’opération dans R.

84. Supprimer un rang#

La suppression est immédiate avec le nom exact. Des suggestions peuvent être affichées en cas de casse différente ou de nom proche.

85. Suppression de tous les rangs#

Aucune protection globale ne l’empêche. Pour retirer toute la taxonomie, supprimer plutôt le composant complet.

86. Tri taxonomique par ASV#

Le tri naturel modifie seulement l’affichage et utilise la première séquence numérique trouvée dans l’identifiant.

87. Synchronisation après renommage des ASV#

Lorsque les rownames taxonomiques changent avec le même nombre de lignes, le sous-module met à jour ses états locaux et ajoute une entrée de synchronisation au journal.

88. Limite de la synchronisation taxonomique#

Un remplacement complet conservant les mêmes identifiants peut ne pas actualiser immédiatement les valeurs affichées. Changer temporairement de dataset puis revenir.

89. Fusionner un fichier dans la taxonomie#

La fusion ajoute uniquement les colonnes absentes, utilise les taxons communs et laisse NA pour les autres.

90. Pas de détection automatique du séparateur taxonomique#

Le séparateur doit être choisi manuellement : virgule, point-virgule ou tabulation.

91. Colonnes taxonomiques existantes#

Une fusion ne remplace pas un rang existant tel que Genus. Utiliser l’import complet pour remplacer toute la table.

92. Remplacement automatique des valeurs#

Plusieurs motifs, par exemple NA, unidentified, unclassified, unknown ou missing, peuvent être remplacés par une valeur commune.

93. Recherche exacte et insensible à la casse#

Les motifs sont comparés après suppression des espaces et passage en minuscules. La recherche est exacte, pas une recherche de sous-chaîne générale.

94. Motif NA#

Le motif NA correspond à une vraie valeur manquante et à la chaîne textuelle NA, avec variations de casse et d’espaces.

95. Motif vide#

Un motif vide cible les chaînes vides ou composées uniquement d’espaces.

96. Portée du remplacement#

Le remplacement agit sur tous les rangs simultanément. Il n’existe pas de ciblage par colonne.

97. Prévisualisation obligatoire#

Le module calcule le nombre total de cellules, le détail par motif et par colonne, puis demande confirmation.

98. Motifs qui se chevauchent#

Une même cellule peut être comptée dans plusieurs motifs, même si le total global utilise l’union des cellules.

99. Valeur de remplacement non vide#

La valeur de remplacement doit contenir du texte ; une chaîne vide est refusée.

100. Conséquences scientifiques du remplacement#

Remplacer NA par Unassigned transforme une absence d’annotation en vraie modalité. Cela modifie la complétude, les agglomérations et les graphiques.

101. Regroupement des taxons non assignés#

Plusieurs taxons portant la même valeur textuelle peuvent être regroupés par tax_glom() comme une catégorie réelle. Ce comportement diffère de la conservation de NA.

102. État taxonomique initial et réinitialisation#

L’état initial est recapturé lors du chargement local du dataset. Un aller-retour entre datasets peut donc modifier la référence de Réinitialiser.

103. Importation, exportation et suppression — présentation#

Cette section agit sur des composants complets d’un phyloseq existant : metadata, OTU, taxonomie, RefSeq et arbre.

104. Importation automatique#

L’import démarre dès la sélection du fichier, sans bouton de confirmation supplémentaire ni aperçu général.

105. Limite de taille#

Les imports utilisent fileInput et sont soumis à la limite globale de BarCodeR, environ 500 Mo.

106. Détection du séparateur des imports complets#

Pour les tables, le module examine surtout la première ligne : point-virgule prioritaire, puis tabulation, sinon virgule. Cette détection est moins robuste que celle des fusions.

107. Import complet de metadata#

La première colonne contient les identifiants. Les identifiants inconnus provoquent un refus ; les échantillons absents sont ajoutés avec NA. La metadata précédente est entièrement remplacée.

108. Import complet de l’OTU table#

Le fichier est interprété avec taxons en lignes et échantillons en colonnes, puis taxa_are_rows = TRUE est imposé.

109. Identifiants acceptés pour l’import OTU#

Les taxons et échantillons du fichier doivent être des sous-ensembles des identifiants existants. L’import ne crée pas de nouveaux identifiants.

110. Identifiants manquants dans l’import OTU#

Les taxons ou échantillons absents sont ajoutés avec des zéros, puis la table est réordonnée selon l’objet actuel.

111. Conversion numérique de l’import OTU#

Toute la table est convertie en numérique. Les valeurs non convertibles deviennent NA, mais l’import peut continuer avec avertissement.

112. Import complet de taxonomie#

La première colonne contient les taxons. Les taxons inconnus sont refusés ; les taxons manquants sont ajoutés avec NA. La table précédente et ses anciens rangs sont remplacés.

113. Import de RefSeq#

Les fichiers FASTA doivent utiliser des identifiants correspondant aux taxons et couvrir tous les taxons. Les fichiers partiels ou contenant des identifiants inconnus sont refusés.

114. Import de l’arbre#

Les fichiers Newick doivent contenir exactement une couverture complète des taxons. Une feuille inconnue ou un taxon manquant provoque le refus.

115. Remplacement complet des composants#

Le composant précédent n’est pas conservé comme snapshot. Seuls les dimensions, le fichier et les avertissements sont journalisés.

116. Rafraîchissement des éditeurs après import complet#

Les sous-éditeurs peuvent conserver une copie locale ancienne lorsque le dataset ne change pas. Après un import ou une suppression, sélectionner un autre dataset puis revenir avant toute nouvelle édition.

117. Exportation des composants#

Metadata, OTU et taxonomie sont exportées en CSV ; RefSeq en FASTA ; arbre en Newick.

118. Séparateur des exports CSV#

Les CSV utilisent le point-virgule ;, malgré l’extension .csv.

119. Export de metadata#

Une colonne SampleID est construite depuis les rownames. Les NA sont exportés comme cellules vides.

120. Export de l’OTU table#

L’orientation stockée est conservée et aucun champ ne documente explicitement taxa_are_rows dans le fichier.

121. Export de taxonomie#

Les identifiants taxonomiques sont exportés dans la première colonne et les valeurs manquantes comme cellules vides.

122. Export de RefSeq#

Les séquences sont écrites en FASTA avec leurs noms actuels ; Biostrings est requis.

123. Export de l’arbre#

L’arbre est écrit en Newick ; ape est requis.

124. Exportation et journal#

Chaque export ajoute une entrée dans edit_log et peut donc marquer le projet comme non sauvegardé.

125. Suppression des composants#

La modale affiche les composants présents et permet d’en sélectionner plusieurs avant confirmation.

126. Suppression de la metadata#

Le slot sam_data est retiré ; les analyses utilisant groupes ou covariables deviennent indisponibles.

127. Suppression de la taxonomie#

Le slot tax_table est retiré ; les analyses taxonomiques deviennent indisponibles.

128. Suppression de RefSeq#

Les analyses de longueur, GC ou séquence ne disposent plus des références.

129. Suppression de l’arbre#

UniFrac, Faith PD et les visualisations phylogénétiques deviennent indisponibles.

130. Suppression de l’OTU table#

L’interface autorise cette suppression, qui rend le dataset inutilisable dans la plupart des modules. Elle doit rester exceptionnelle.

131. Suppression simultanée de composants#

Plusieurs slots peuvent être supprimés en une fois, même si les composants restants deviennent incohérents.

132. Annulation d’une suppression de composant#

Cette section ne possède pas de mécanisme Undo. Il faut réimporter, restaurer le projet ou recharger un export antérieur.

133. Suppression et fichiers sur disque#

La suppression agit seulement en mémoire jusqu’à la sauvegarde du projet. Les fichiers sources et sauvegardes antérieures ne sont pas supprimés.

134. Enregistrer le dataset dans le registre#

Le champ de nom permet de réinscrire sous le même nom, créer une nouvelle entrée ou remplacer une entrée existante.

135. Nom laissé vide#

Le dataset est réinscrit sous son nom courant, devient actif et reçoit une entrée de journal. Le projet n’est pas sauvegardé sur disque.

136. Nouveau nom disponible#

Une nouvelle entrée reçoit l’état édité courant et devient active. La source reste présente, mais elle avait déjà été modifiée en place.

137. Nom déjà utilisé par un autre dataset#

Après confirmation, l’autre dataset est entièrement écrasé par l’état édité de la source. La source reste également dans le registre.

138. Nettoyage du nom du dataset#

Le nom est nettoyé par le helper commun ; les collisions sont évaluées après nettoyage.

139. Écrasement d’un autre dataset#

L’écrasement remplace toutes les tables, séquences, arbre, attributs, logs et provenance. Ce n’est pas une fusion.

140. Sauvegarde du projet complet#

Après édition, ouvrir Datasets et utiliser Sauvegarder le projet pour persister le registre sur disque.

141. Résolution des problèmes#

Les sections suivantes recensent les problèmes les plus fréquents et leurs causes réelles.

141.1. Le mauvais dataset est modifié#

Le sélecteur est synchronisé avec le dataset actif. Vérifier le nom affiché avant chaque action.

141.2. L’original a été modifié alors qu’un nouveau nom devait être créé#

Les éditions sont appliquées en place avant la copie. Restaurer une sauvegarde, un export ou le fichier original.

141.3. Le bouton Enregistrer n’a pas sauvegardé le projet#

Il agit uniquement sur le registre en mémoire. Sauvegarder depuis Datasets.

141.4. La metadata est apparue automatiquement#

Le dataset n’avait pas de sample_data; le module a créé une table minimale.

141.5. Modifier la colonne SampleID n’a pas renommé les échantillons#

Les vrais identifiants sont les rownames, pas la colonne affichée.

141.6. Une variable numérique est devenue texte#

Une valeur non numérique a probablement été saisie. Corriger toute la colonne ou réimporter une metadata correctement typée.

141.7. Un facteur est devenu character#

Les facteurs sont convertis dans l’éditeur. Réappliquer les niveaux dans R si nécessaire.

141.8. Une colonne ajoutée ne possède pas le bon type#

Elle est initialisée avec NA et son type dépend des valeurs saisies. Vérifier et convertir après remplissage.

141.9. Le fichier metadata ne met pas à jour une colonne existante#

La fusion ajoute seulement les nouvelles colonnes. Utiliser l’import complet ou modifier les cellules.

141.10. Aucun identifiant commun n’est trouvé#

Vérifier la première colonne, l’option rownames, la casse, les espaces et la correspondance des noms.

141.11. Le séparateur détecté est incorrect#

Choisir manuellement le séparateur lorsque le fichier est irrégulier ou contient des séparateurs dans ses valeurs.

141.12. Des valeurs OTU sont devenues NA#

La conversion numérique a échoué à cause de texte, symboles, espaces ou virgules décimales.

141.13. Les nombres décimaux avec virgule deviennent NA#

Le séparateur décimal attendu est le point. Corriger le fichier avant import.

141.14. Une colonne OTU ajoutée a désynchronisé la metadata#

L’échantillon n’a été ajouté que dans l’OTU table. Ajouter la metadata correspondante ou reconstruire l’objet.

141.15. RefSeq a disparu après une modification OTU#

Elle ne couvrait plus tous les taxons de la nouvelle OTU table.

141.16. L’arbre a disparu après une modification OTU#

Il manquait un taxon, le renommage a échoué ou ape était indisponible.

141.17. Des feuilles ont disparu de l’arbre#

Les feuilles supplémentaires absentes de l’OTU table sont supprimées automatiquement.

141.18. Les échantillons ont été renommés comme des ASV#

Le mauvais axe a été sélectionné. Restaurer une copie ou une sauvegarde.

141.19. Le préfixe ASV produit des noms inhabituels#

Le préfixe n’est pas strictement validé. Utiliser un préfixe simple.

141.20. La taxonomie ne correspond plus à l’OTU table#

Vérifier les rownames, les doublons et recharger les éditeurs. Utiliser setequal(taxa_names(ps), rownames(tax_table(ps))).

141.21. La première modification taxonomique ne s’est pas appliquée#

La première tentative affiche seulement l’avertissement. Fermer puis répéter l’action.

141.22. Un remplacement taxonomique a modifié plusieurs rangs#

La recherche agit sur toutes les colonnes. Examiner l’aperçu par rang avant confirmation.

141.23. NA est désormais considéré comme une vraie catégorie#

Il a été remplacé par du texte. Les agrégations peuvent maintenant traiter cette valeur comme un taxon renseigné.

141.24. La fusion taxonomique ne remplace pas Genus#

Genus existe déjà ; la fusion ajoute seulement les rangs absents.

141.25. Le séparateur taxonomique n’a pas été détecté#

Ce sous-module exige une sélection manuelle du séparateur.

141.26. L’import complet a écrasé des colonnes#

Il remplace l’ensemble du composant. Restaurer une sauvegarde ou préférer Fusionner pour un ajout.

141.27. L’import complet OTU a changé l’orientation#

L’import impose les taxons en lignes.

141.28. L’import complet refuse de nouveaux échantillons#

Les identifiants doivent déjà exister. Construire un nouveau phyloseq pour étendre l’univers des échantillons.

141.29. L’import complet refuse de nouveaux taxons#

Les rownames doivent appartenir à taxa_names(ps).

141.30. L’import FASTA est refusé#

Vérifier format, identifiants, couverture complète, doublons et disponibilité de Biostrings.

141.31. L’import d’arbre est refusé#

Vérifier Newick, feuilles inconnues, taxons manquants et disponibilité de ape.

141.32. L’éditeur affiche encore l’ancienne table après import#

Changer temporairement de dataset puis revenir pour recharger l’état local.

141.33. Une ancienne table supprimée réapparaît après édition#

Un sous-module local obsolète a pu réécrire son ancienne copie. Toujours forcer le rechargement après suppression ou import complet.

141.34. Télécharger un fichier a créé une modification non sauvegardée#

L’export est journalisé et modifie l’attribut edit_log.

141.35. La suppression d’une table ne peut pas être annulée#

Cette section n’a pas de Undo. Réimporter ou restaurer.

141.36. Le dataset ne fonctionne plus après suppression de l’OTU table#

L’OTU table est le composant central. Restaurer une version complète.

141.37. Annuler ne remonte pas plusieurs actions#

Un seul état précédent est conservé.

141.38. Réinitialiser ne revient pas au fichier original#

L’état initial correspond au chargement local du sous-module.

141.39. Le journal affiche des actions françaises dans une autre langue#

La trace interne est stockée en français.

141.40. Le total d’actions augmente après un export#

Les exports sont comptés comme actions journalisées.

142. Checklist avant une édition#

  • Vérifier le projet et le dataset actifs.
  • Dupliquer le dataset brut.
  • Sauvegarder le projet et exporter le dataset important.
  • Vérifier les composants et l’orientation OTU.
  • Fermer les autres sessions susceptibles d’écrire dans le même projet.

143. Checklist avant une modification de metadata#

  • Vérifier les rownames et ne pas les confondre avec la colonne SampleID.
  • Vérifier types, facteurs ordonnés, dates et valeurs manquantes.
  • Utiliser des noms de colonnes compatibles.
  • Contrôler de nouveau les types après l’édition.

144. Checklist avant une modification OTU#

  • Vérifier taxa_are_rows et l’axe des ASV.
  • Vérifier la nature des abondances et l’absence de texte.
  • Contrôler metadata, taxonomie, RefSeq et arbre avant tout ajout ou suppression.
  • Exporter l’objet avant un renommage massif.

145. Checklist avant un remplacement taxonomique#

  • Vérifier les motifs, la casse et les espaces.
  • Examiner le nombre de cellules par rang.
  • Comprendre la différence entre NA et texte.
  • Anticiper les effets sur les agglomérations.
  • Conserver la taxonomie originale.

146. Checklist avant un import complet#

  • Vérifier le dataset, le séparateur, la première colonne, les identifiants et la couverture.
  • Sauvegarder le composant précédent.
  • Comprendre que le composant sera remplacé.
  • Forcer ensuite le rechargement et contrôler le résultat dans Description.

147. Checklist avant la suppression d’un composant#

  • Exporter le composant et sauvegarder le projet.
  • Vérifier les modules dépendants.
  • Ne pas supprimer l’OTU table sans raison exceptionnelle.
  • Comprendre qu’il n’existe pas de Undo.

148. Checklist après Data Edition#

  • Ouvrir Description et vérifier dimensions, sommes, types, valeurs manquantes, taxonomie, RefSeq et arbre.
  • Vérifier l’alignement des identifiants et lire le journal.
  • Sauvegarder le projet dans Datasets.

150. Limites actuelles à connaître#

  • Les éditions sont immédiates et l’original n’est pas automatiquement préservé.
  • Enregistrer ne sauvegarde pas le projet.
  • Undo conserve un seul état et Reset dépend du chargement local.
  • Une metadata peut être créée automatiquement.
  • Les facteurs et classes complexes peuvent être perdus.
  • Le switch ASV n’est pas une transposition.
  • Les modifications OTU peuvent désynchroniser les composants.
  • Les remplacements taxonomiques agissent sur tous les rangs.
  • Les imports complets démarrent sans aperçu et n’étendent pas les identifiants.
  • Les sous-éditeurs peuvent conserver une vue obsolète.
  • L’export modifie le journal.
  • La suppression de l’OTU table est autorisée.
  • Aucun garde complet n’est exécuté après chaque action.

151. Parcours recommandé#

  1. Sauvegarder le projet.
  2. Dupliquer le dataset brut.
  3. Éditer la copie.
  4. Vérifier l’orientation OTU.
  5. Modifier la metadata et contrôler les types.
  6. Modifier l’OTU uniquement si nécessaire.
  7. Vérifier taxonomie, RefSeq et arbre après toute modification structurelle.
  8. Utiliser les aperçus taxonomiques.
  9. Forcer le rechargement après un import ou une suppression complète.
  10. Contrôler le résultat dans Description.
  11. Sauvegarder le projet et exporter le dataset final.
