OpenMetaBar — Methodological Guides

1. General overview#

The OpenMetaBar tab lets users launch and monitor a complete metabarcoding data-processing pipeline from FASTQ files.

The analysis is not executed directly inside the application. BarCodeR acts as a preparation, submission and monitoring interface:

  1. the user chooses the biological and technical context of the analysis;
  2. FASTQ files, the experimental design and the reference database are selected;
  3. BarCodeR checks the files and prepares their transfer;
  4. the user configures cluster resources and pipeline parameters;
  5. BarCodeR creates an isolated directory for the run;
  6. the OpenMetaBar pipeline embedded in the application is copied to the cluster;
  7. the required Singularity images are checked or installed;
  8. a Slurm job is submitted;
  9. the application monitors execution and detects generated files;
  10. a phyloseq object can then be imported into BarCodeR.

OpenMetaBar supports several technologies and analysis routes:

  • Oxford Nanopore Technologies, or ONT;
  • PacBio;
  • Illumina;
  • LotuS3;
  • NextITS;
  • the IDMABIO reporting route.

2. What OpenMetaBar does and does not do#

2.1. What OpenMetaBar automates#

OpenMetaBar automates, among other things:

  • preparation of the working directory;
  • initial file validation;
  • transfer of local files;
  • rewriting FASTQ paths in the design file;
  • generation of the Nextflow configuration;
  • preparation of Slurm resources;
  • pipeline deployment;
  • management of Singularity images;
  • job submission;
  • monitoring of Slurm status;
  • detection of results;
  • import of a phyloseq object.

2.2. What remains the user's responsibility#

The application cannot automatically determine:

  • whether the selected marker truly matches the primers used;
  • whether the entered expected length is biologically relevant;
  • whether a reference database is appropriate for the marker and organisms studied;
  • whether quality thresholds suit the sequencing technology;
  • whether the coding-sequence filter is relevant;
  • whether the chosen clustering or denoising method fits the study objective;
  • whether taxonomic parameters provide sufficiently reliable identification;
  • whether the requested Slurm resources are appropriate for the data volume.

Important principle — A default value proposed by the application is not necessarily a universal recommendation.

3. Workflow overview#

The recommended workflow is:

  1. Check or establish the cluster connection.
  2. Define the analysis context.
  3. Validate the context.
  4. Choose FASTQ files, the design file and the reference database.
  5. Correct or create the design file if necessary.
  6. Validate the files and prepare their transfer.
  7. Configure the run and Slurm resources.
  8. Validate the general configuration.
  9. Configure parameters specific to the selected route.
  10. Review the optional previews.
  11. Launch the analysis.
  12. Monitor the steps and execution logs.
  13. Review the results.
  14. Import the phyloseq object into BarCodeR.
  15. Manage the run from the history.

The context can be validated without connecting to the cluster. A connection is nevertheless required to browse remote files, validate and transfer files, check the remote directory, detect Slurm partitions, prepare containers, submit the run, monitor execution and inspect previous runs.

4. Choosing the analysis route#

The combination technology + marker + engine determines which sub-pipeline is executed.

4.1. Available routes#

Technology Marker Available engine Main route
ONT COI LotuS3 Standard ONT
ONT 16S LotuS3 Standard ONT
ONT 18S LotuS3 Standard ONT
ONT COI-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 16S-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 18S-idmabio LotuS3 + IDMABIO ONT IDMABIO
PacBio 16S LotuS3 PacBio 16S
PacBio ITS LotuS3 or NextITS PacBio ITS
PacBio LSU LotuS3 or NextITS PacBio LSU
Illumina 16S LotuS3 Illumina
Illumina ITS LotuS3 Illumina
Illumina LSU LotuS3 Illumina

The -idmabio variants are proposed only when the application recognises a compatible connection to the biglogin cluster.

4.2. Consequences of the selected route#

The context determines:

  • whether MiniBar is available;
  • whether the NextITS engine can be used;
  • which parameters are displayed;
  • which Singularity images are mandatory;
  • which pipeline steps are executed;
  • which outputs can be produced.

Changing the technology, marker or engine after validation invalidates the context. Dependent steps must then be checked again.

5. Connecting to the cluster#

5.1. Opening the connection window#

The button at the top of the tab shows the connection status:

  • Cluster not connected: no active SSH connection;
  • Active connection to check: SSH is open, but some cluster prerequisites have not been confirmed;
  • Cluster connected: the connection and the main required commands have been detected.

Click the button to open the connection window.

5.2. Information to provide#

The connection uses the server address, SSH port, username and, when required, a password. The password may be left empty when key-based SSH authentication is already configured and working.

5.3. Checks performed#

After connection, BarCodeR checks the availability of Bash, find, tar, sbatch, squeue, sacct, scancel, sinfo, Rscript, accessible Slurm partitions and some limits on time, memory and processors.

An SSH connection may therefore be open while the cluster is not yet considered ready to run OpenMetaBar.

5.4. The biglogin cluster case#

On the supported infrastructure, the connection can be made directly or through a bigm9 relay when a direct connection is unavailable. This mechanism is managed automatically.

5.5. Disconnection during a run#

Disconnecting the application does not cancel the Slurm job. Once submitted, the computation continues on the cluster. The run can be recovered from the history after reconnecting to the same cluster, using a compatible root directory and having the required permissions.

6. Defining the analysis context#

The first configuration card contains the parameters that determine the pipeline route.

6.1. Sequencing technology#

Oxford Nanopore Technologies

Selecting ONT displays COI, 16S and 18S markers, may expose IDMABIO variants, displays MiniBar demultiplexing and uses the ONT route with LotuS3.

PacBio

Selecting PacBio displays 16S, ITS and LSU markers, enables the LotuS3/NextITS choice for ITS and LSU, hides MiniBar and uses a dedicated PacBio route.

Illumina

Selecting Illumina displays 16S, ITS and LSU markers, uses LotuS3, hides MiniBar and supports single-end or paired-end files according to the design file.

6.2. Marker or target#

The marker is used to choose the route, suggest a database type, suggest a NextITS region, identify IDMABIO variants and adapt visible parameters. It does not verify that the primers in the design actually target that marker.

Marker Suggested database type
COI BOLD
16S SILVA
18S PR2
ITS UNITE
LSU SILVA

This suggestion changes the declared database type, but does not automatically select a different FASTA file.

6.3. Reference database type#

Available values are BOLD, SILVA, PR2, UNITE, NCBI nt and custom. The declared type mainly tells the pipeline how to interpret FASTA headers and build the taxonomy mapping.

The declared database type and the selected FASTA file are separate. They must be consistent. Declaring a personal FASTA as BOLD does not turn it into a BOLD database.

6.4. Analysis engine#

The engine selector appears only for PacBio + ITS and PacBio + LSU. Choices are LotuS3 and NextITS. In all other contexts, the selector is hidden and does not affect the route.

6.5. Validating the context#

Click Validate context to unlock file selection. Changing the technology, marker or engine afterwards locks this step again.

7. Choosing run files#

After the context has been validated, the Choose run files button becomes available. Three file categories must be defined: FASTQ files, the design file and the reference database. An additional chimera database is required for NextITS.

7.1. Choosing FASTQ files#

Local source

Local FASTQ files are selected using the application's file browser. They are not uploaded through a standard web upload: BarCodeR uses their real path and then transfers them to the cluster.

Consequently, the usual Shiny upload size limit does not apply, but the files must remain accessible until the transfer is complete.

Cluster source

FASTQ files may already be present on the cluster. They can be selected by entering a path or through the remote browser. An active SSH connection is required.

One or more FASTQ files

The application accepts multiple files and keeps them separate. They are not concatenated automatically. The basename is preserved, so two files from different directories with the same name cause a collision.

Problematic example:

/run1/sample.fastq.gz
/run2/sample.fastq.gz

Expected extensions are .fastq, .fastq.gz, .fq or .fq.gz.

Already demultiplexed FASTQ files

When each file already represents one sample, disable MiniBar for ONT, use one sample per design row and map each row to the correct FASTQ file.

Non-demultiplexed FASTQ files

When one file contains several samples identified by barcodes, enable MiniBar and enter the barcodes and primers for every sample. Several design rows may point to the same FASTQ file.

7.2. Choosing the design file#

The design file may be local, remote, or created/edited in the integrated editor. TSV and CSV formats are accepted.

Columns required by the pipeline

Column Purpose
Sample_ID Unique sample identifier
fastq_path Path to one or more FASTQ files
barcodeF Forward barcode
barcodeR Reverse barcode
primerF Forward primer
primerR Reverse primer

The columns must exist even when barcodes are not used. An explicit value such as NA may be preferable to an empty cell depending on the expected pipeline behaviour.

Warning — The integrated editor may consider a two-column table editable, while the full pipeline validation requires the six exact columns. A design described as “consistent” by the editor can still be rejected at launch.

Sample identifiers

Identifiers must be present, unique and preferably restricted to A-Z, a-z, 0-9, ., - and _.

Automatic correction transliterates accents, replaces invalid characters, cleans leading or trailing separators and adds suffixes to duplicates. Letter case is preserved.

Path column

The second column must be recognised as a path column. Accepted names include path, fastq_path, filepath, file_path, input_dir, directory, dir and folder. Use fastq_path directly to avoid ambiguity.

Before launch, this column is renamed fastq_path and paths are rewritten for the remote run directory.

Paired-end files

For an Illumina pair, fastq_path may contain two comma-separated files:

sample_R1.fastq.gz,sample_R2.fastq.gz

Both files must have been selected and their names must match exactly.

Matching the design and FASTQ files

Every referenced file must match a selected filename. Differences in extension, case, suffix or a typing error may trigger an error.

Single FASTQ case

When every row refers to the same raw file, the application can rewrite paths so every sample uses that remote FASTQ, notably before MiniBar demultiplexing.

7.3. Primers in the design file#

primerF and primerR are used for orientation. Enter them 5′ to 3′, with valid IUPAC nucleotide characters and no spaces. Degenerate bases are supported.

When orientation is enabled, the pipeline expects one unique primer pair per FASTQ file. It raises an error when no pair is found, several different pairs map to the same FASTQ, or a primer contains invalid characters.

7.4. Barcodes in the design file#

barcodeF and barcodeR are used by MiniBar. Barcodes that are too similar, combined with high error tolerance, increase the risk of incorrect sample assignment.

7.5. Choosing the reference database#

The database may be local or remote and must be a compatible FASTA (.fa, .fna, .fasta, .fas, optionally gzip-compressed).

It is used to create a cleaned FASTA, extract a taxonomic table from headers and perform taxonomic assignment.

Check that the file matches the marker, uses the correct alphabet, contains unique identifiers, has usable taxonomy in its headers, matches the declared type and is readable on the cluster.

8. Using the design editor#

8.1. Editing cells#

Cells can be edited directly. After each change, the application reassesses the minimum structure, the path column, sample identifiers and matching with selected FASTQ files.

8.2. Adding or deleting rows#

A row can be added and several rows can be deleted. Completely empty rows are ignored when saving but produce a warning.

8.3. Adding, renaming or deleting a column#

The editor supports all three operations. At least two columns must remain. A complete design must contain exactly Sample_ID, fastq_path, barcodeF, barcodeR, primerF, primerR.

8.4. Correcting sample names#

The correction button cleans characters, prevents empty identifiers and makes names unique. Review changes because these identifiers will appear in results and the phyloseq object.

8.5. Generating a design from FASTQ files#

This option is available only when MiniBar is disabled. The application initially creates SampleID and path.

This is not yet a complete design. Rename the columns to Sample_ID and fastq_path, add barcodeF, barcodeR, primerF, primerR, then fill the required values.

8.6. Saving the design#

Saving is blocked while the editor detects a structural error. It replaces the current selection with a temporary local file named design_edite.tsv. Full pipeline validation occurs later at launch.

9. Validating and preparing files#

The Validate and transfer button requires an active connection. This step checks selections, file existence, the beginning of FASTQ files, some design issues, sample names and remote disk space. It transfers local files to a staging area and keeps paths for files already on the cluster.

The disk-space check is preventive and may be approximate depending on the remote system. When complete, the main button displays Files ready.

10. Configuring the run and cluster#

10.1. Run root directory#

A unique subdirectory is created under this root for each run. The user needs permission to create, write, execute, read and clean files. The embedded pipeline is copied into the run directory and later removed according to the cleanup logic.

10.2. Slurm partition#

When sinfo is available, detected partitions are proposed. The partition affects resources, maximum duration, priority and account restrictions. A visible partition is not necessarily authorised for the current user.

10.3. Memory for LotuS3#

Memory must include a unit, such as 16G, 70G or 120G. Do not enter only 70, which Slurm may interpret as approximately 70 MB.

Too little memory may cause OUT_OF_MEMORY; excessive memory may increase queue time.

10.4. Cores for LotuS3#

The core count defines Slurm CPUs, LotuS3 threads and some resources for child processes. Requesting more cores does not guarantee proportional speed-up and may make the job harder to schedule.

10.5. Container module#

This field must exactly match the module providing Singularity or Singularity-CE, for example singularity-ce/4.1.0.

10.6. Nextflow module#

This field specifies the Nextflow version, for example nextflow/25.10.4. A missing or incompatible module prevents launch.

10.7. Run name#

The name helps identify the directory, Slurm job and history entry. The application automatically adds a date, session identifier and random suffix. Avoid very long names, special characters and sensitive information.

10.8. Keeping intermediate files#

The debug option keeps work/ after success. This directory helps inspect commands and diagnose issues but can be very large. Intermediate files are already retained after failure. work/ can later be removed from the history.

11. Understanding initial values#

The application starts with settings initially suited to ONT + COI: orientation enabled, length filter enabled, expected length 658, minimum quality 20, coding filter enabled and translation table 5.

These values do not automatically suit 16S, 18S, ITS or LSU. For those markers, review at least the coding filter, expected length, genetic code, amplicon type and taxonomic group.

The first change to some parameters displays a warning that the initial value is optimised. This only means a controlled initial value exists, not that it is optimal for every protocol.

12. MiniBar demultiplexing — ONT routes#

12.1. Enabling or disabling MiniBar#

Enable MiniBar when one FASTQ contains several barcode-labelled samples and the design contains the required information. MiniBar produces per-sample FASTQ files and metrics for demultiplexed and retained reads. Unknown or ambiguous reads are not published as assigned samples.

Disable MiniBar when FASTQ files are already separated by sample or demultiplexing was performed upstream.

12.2. Identification method — M#

Methods 1, 2 and 3 are passed directly to MiniBar with -M. They alter the internal assignment strategy based on barcodes and primers.

The application does not explain the algorithmic differences. Keep the method validated for the protocol, avoid changing it between comparable batches without justification, and review demultiplexing metrics after any change.

12.3. Maximum barcode errors — e#

A low value increases specificity but may lose noisy reads. A high value recovers more altered barcodes but increases the risk of confusing similar barcodes. 0 requires an exact match.

12.4. Maximum primer errors — E#

A higher tolerance recovers more noisy reads but may increase non-specific matches. A lower tolerance strengthens specificity but can remove valid reads.

12.5. MiniBar parameter — l#

The interface describes it as a search window, whereas the pipeline schema describes it as a minimum read length. The value is passed directly to -l.

Because of this discrepancy, leave the field blank unless a value has been validated, do not assign it an arbitrary interpretation, and compare metrics before and after any change.

13. Amplicon orientation#

13.1. Single-end reads#

For a single FASTQ, the pipeline finds primers, detects both orientations, places sequences in the primerF → primerR direction, removes primers and retains the internal region. Reads without a complete primer pair are discarded.

13.2. Non-degenerate and degenerate primers#

With primers containing only A/C/G/T, the step currently allows up to one mismatch. With degenerate IUPAC codes, degenerate-pattern matching is used without enabling that additional mismatch mode.

13.3. Paired-end reads#

For a FASTQ pair, the orientation step is skipped and reports SKIPPED_PAIRED_END. Reads are therefore not reoriented and primers are not removed by this process.

13.4. NextITS route#

NextITS has its own processing for ITS regions and primers; this general orientation step does not apply in the same way.

13.5. When to disable orientation#

Disable it when primers have already been removed, all sequences are already consistently oriented or upstream processing guarantees this preparation.

14. Filter order#

Filters are cumulative and applied in this order: quality, length, coding. Each filter receives only reads retained by the previous one. Several moderately strict settings may therefore become highly restrictive. The pipeline stops if no reads remain.

15. Length filter#

15.1. Activation and input#

When disabled, the entered length is ignored. When enabled, provide one or more comma-separated integers, for example 480 or 450,550.

15.2. Actual interval used#

The pipeline applies a ±100 nucleotide margin around each expected length.

For 658, the interval is 558–758. For 500,800, the intervals are 400–600 and 700–900.

15.3. Choosing a length#

The value depends on the region between primers, whether primers are still present at filtering time, biological variability, technology and target groups. 658 belongs to the initial COI context and must not be retained automatically.

15.4. Empty or invalid field#

In the current implementation, an empty or unparsable value may silently be replaced with 658. If the filter is enabled, do not leave the field blank unless that value is genuinely intended.

15.5. Paired-end reads#

The filter is applied separately to R1 and R2 before resynchronisation. It evaluates each read, not the merged amplicon. For 250-nt reads, an expected length of 658 would remove both mates.

15.6. Resynchronisation#

After filtering, pairs are matched again by identifier. Reads without a retained mate become orphans. Only complete pairs continue.

16. Quality filter#

The minimum threshold is passed to SeqKit. A higher value increases stringency and reduces read count; a lower value preserves depth but also more noise. The choice depends on the technology, sequencing generation and upstream preprocessing.

For paired-end data, filtering is applied separately to R1 and R2, followed by resynchronisation. If only one mate is removed, the other becomes an orphan.

17. Coding-sequence filter#

The filter retains reads with at least one reading frame that can be translated without an internal stop codon according to the selected genetic code. It tests the three frames in the supplied orientation.

It is mainly relevant for a coding region such as COI and is generally unsuitable for 16S, 18S, ITS and LSU. If orientation is disabled, coding sequences in reverse orientation may be rejected.

Value Genetic code
1 Standard code
2 Vertebrate mitochondrial
5 Invertebrate mitochondrial
11 Bacterial, archaeal and plastid

Table 5 is proposed for invertebrate mitochondrial COI, but is not suitable for every COI sequence or for other markers.

For paired-end data, the filter is applied separately to both reads before resynchronisation. Interpret this cautiously when each read covers only part of the coding region.

18. LotuS3 — clustering and assignment#

LotuS3 parameters are shown for all routes except PacBio ITS/LSU when NextITS is the main engine.

18.1. Platform#

Choices: auto, PacBio, 454, miSeq, hiSeq. In auto mode, BarCodeR does not force a value. An explicit value changes internal strategies and must remain consistent with the technology and preprocessing.

18.2. Amplicon type#

Choices: SSU, LSU, ITS, ITS1, ITS2, custom. It must match the region actually amplified, not merely the project's broad marker name.

18.3. Taxonomic group#

Choices: auto, bacteria, fungi, eukarya. An explicit value guides some taxonomic decisions. Auto is preferable for heterogeneous contexts or when no value has been validated.

18.4. Clustering or denoising#

Choices: UPARSE, Swarm, CD-HIT, UNOISE, DADA2, VSEARCH. These methods do not necessarily produce the same biological units. They may change the number of units, abundances, sensitivity to rare sequences and error treatment. Results from different methods should not be treated as directly equivalent.

18.5. Taxonomic assignment tool#

Choices: RDP classifier, BLAST, Lambda, UTAX, SINTAX, VSEARCH, USEARCH. The choice affects the algorithm, speed, sensitivity, handling of distant sequences and available scores.

18.6. RDP confidence threshold#

Visible only with RDP_classifier. A high value is more stringent and produces more unassigned sequences; a lower value increases assignments but may reduce robustness.

18.7. Keeping unclassified units#

0 removes unclassified units; 1 keeps them. Keeping them supports investigation of unknown diversity and later reassignment, but requires explicit handling in analyses.

18.8. Taxonomic exclusion#

The entered pattern excludes taxa. A broad expression may remove many assignments. Check database vocabulary, test the pattern and document the exclusion.

19. Saving demultiplexed reads#

Mode Effect
0 Do not publish specific demultiplexed FASTQ files
1 Keep all unfiltered demultiplexed reads
2 Keep demultiplexed reads and stop the pipeline
3 Keep quality-filtered demultiplexed reads

Mode 2 must not be used when a phyloseq object or a complete analysis is expected. Modes 1 and 3 increase disk usage but make read-level checking and reuse easier.

20. LCA and advanced assignment#

20.1. Assignment mode#

Counter-intuitive convention: 0 enables LCA; 1 uses the best BLAST hit.

LCA seeks a common ancestor shared by compatible hits and often gives a more conservative assignment. Best hit may appear more precise but is more sensitive to erroneous references, imbalanced databases or nearly equivalent hits.

20.2. Minimum coverage#

A value between 0 and 1. High coverage requires most of the sequence to align; low coverage accepts partial matches. High identity over a short fragment is not equivalent to high identity over the whole amplicon.

20.3. Rank-specific identity thresholds#

Initial example: 97,95,93,91,88,78. These thresholds are not universal mappings between identity and taxonomic rank. Divergence depends on marker, group, database and region length. Changing them directly changes the accepted taxonomic depth.

20.4. Agreement fraction#

A high value requires stronger consensus and may return a higher taxonomic rank. A low value accepts decisions with less agreement and may increase conflicts.

20.5. Phylogenetic tree#

0: no tree; 1: FastTree; 2: IQ-TREE 2. Tree building adds computation and requires a usable alignment. IQ-TREE 2 is generally more expensive.

20.6. Maximum read overlap#

This parameter mainly concerns paired short reads. It must be consistent with read length, amplicon length and the expected overlap between R1 and R2.

21. Standard ONT route#

Contexts: ONT + COI, 16S or 18S.

Depending on settings, the route performs design validation, optional MiniBar, per-sample FASTQ recovery, orientation, filters, mapping preparation, LotuS3, assignment and reports.

For COI, check actual length, primer presence, target organism, genetic code, coding filter and database. For 16S/18S, normally disable the coding filter, replace or disable 658, choose the amplicon type, group and a compatible database.

22. ONT IDMABIO route#

Contexts: COI-idmabio, 16S-idmabio, 18S-idmabio. These options appear only on a recognised compatible cluster. The route is triggered by the marker suffix, not the engine selector.

It repeats the ONT steps and adds ZOTU-hit validation, IDMABIO outputs, MAFFT alignments and a Word report.

22.1. Gene type#

Choices: auto, coding, non-coding. In auto mode, COI is treated as coding and the other markers as non-coding. An explicit value overrides this inference.

22.2. Retained BLAST hits#

Defines the maximum number of retained hits. A high value increases information, file size and potentially processing time; a low value may hide informative secondary hits.

22.3. Alignments per sample#

Controls how many alignments are displayed in the outputs. It is not the same as the total number of retained hits.

22.4. Report language#

Choices: French or English. This controls the generated Word report.

23. PacBio route with LotuS3#

Contexts: PacBio + 16S, or PacBio + ITS/LSU with LotuS3. MiniBar is not used.

Check that reads still contain primers if orientation is enabled, that expected length matches the provided reads, that the coding filter is disabled for 16S/ITS/LSU and that the quality threshold suits corrected PacBio reads.

Then configure the platform, amplicon type, group, clustering method, taxonomic tool and LCA options.

24. PacBio route with NextITS#

Available only for PacBio + ITS or LSU with the NextITS engine.

The route performs validation, enabled prefilters, NextITS, ITSx, correction and clustering, chimera detection, dedicated LotuS3 assignment, phyloseq generation and summaries.

24.1. ITS region#

Choices: ITS1, ITS2, LSU, SSU, ALL. LSU suggests LSU and ITS initially suggests ITS1, but this does not validate the region actually amplified.

24.2. ITSx group#

Choices: all, fungi, tracheophyta, metazoa. A group that is too restrictive may be unsuitable for heterogeneous environmental samples.

24.3. NextITS clustering#

Choices: UNOISE, VSEARCH, Swarm. The choice changes clustering or denoising. Outputs from different methods are not directly identical.

24.4. UNOISE option#

This checkbox enables a UNOISE denoising step. It is distinct from the general method selector.

24.5. Homopolymer correction#

Enables homopolymer polishing. This modifies sequences and should remain consistent across runs intended for comparison.

24.6. Chimera database#

It may be local or remote and must exist, be readable, have the expected format and match the group and region. The initially suggested path may belong to the development environment; select the database explicitly.

24.7. Primer consistency#

The route expects a consistent primer pair. Different pairs in one run may trigger an error or unwanted behaviour.

25. Illumina route with LotuS3#

Contexts: Illumina + 16S, ITS or LSU.

The design specifies one file for single-end data or two comma-separated files for a pair. Orientation is skipped for pairs, so primers are not removed by that step.

Quality, length and coding filters are applied separately to R1 and R2, followed by resynchronisation. The length filter does not operate on a merged amplicon. A read whose mate is removed becomes an orphan.

For 16S/ITS/LSU, normally disable the coding filter, replace or disable 658, and check the amplicon type, group and database.

26. Design and destination preview#

Previews are optional and initially disabled. The design/destination preview shows the run name, an example Run ID, the design, future directory, FASTQ destinations, rewritten design path, configuration, technology, marker, database type and path, partition, resources and Singularity cache.

The design preview shows the initial content; paths are only rewritten at launch.

27. Generated configuration preview#

This preview displays the Nextflow overlay built from the form: paths, enabled parameters, numerical values, LotuS3, IDMABIO and NextITS parameters, and the Singularity directory.

The file may contain parameters for other routes; their presence does not mean they will all be used. nf-schema nevertheless validates emitted values, so an invalid value may block the run before any process starts.

28. Pre-launch checks#

Context#

  • correct technology;
  • marker consistent with primers;
  • correct engine;
  • database type consistent with FASTA.

FASTQ files#

  • all files selected;
  • no duplicate basenames;
  • correct extensions;
  • correct R1/R2 order.

Design#

  • six required columns;
  • unique identifiers;
  • exact paths;
  • primers entered 5′ to 3′;
  • barcodes present when MiniBar is enabled;
  • consistent primer pairs.

Filters#

  • appropriate expected length;
  • relevant coding filter;
  • correct genetic code;
  • suitable quality threshold;
  • compatible orientation setting.

Cluster#

  • green connection status;
  • accessible directory;
  • authorised partition;
  • memory with a unit;
  • existing modules;
  • sufficient space.

NextITS#

  • existing chimera database;
  • correct region;
  • suitable ITSx group;
  • consistent primers.

29. What happens at launch#

BarCodeR rereads the context, checks FASTQ files, blocks duplicate names, rereads and checks the design, validates identifiers and databases, creates a Run ID, creates results/, work/ and meta/, rewrites the design, gathers FASTQ files, transfers files, prepares images, extracts the pipeline, generates the configuration and Slurm script, writes metadata, submits with sbatch, retrieves the Job ID and starts monitoring.

If another run is already being monitored in the session, confirmation is requested. The new submission does not automatically cancel the previous run.

30. Singularity images#

Depending on the route, OpenMetaBar uses images for SeqKit, LotuS3, reports, MiniBar, MAFFT, phyloseq and NextITS. They are managed under <remote_root>/_barcoder_singularity.

The application attempts to use or copy a shared image, prepare or download a missing image, and then verify its presence and size. Not every image is required for every route: MiniBar for ONT, MAFFT for IDMABIO, and NextITS plus the phyloseq environment for NextITS. A missing mandatory image blocks launch.

31. Reading the run timeline#

Displayed steps are: FASTQ selected, connection, design ready, remote directory, transfers, Singularity images, pipeline deployment, sbatch submission and Slurm monitoring.

The timeline combines local actions, SSH operations, submission status, Slurm status and file detection. Pending, running, success, warning and error states must be interpreted for the specific step.

32. Understanding Slurm states#

PENDING#

The job is waiting for resources. Possible causes include unavailable resources, priority, a busy partition, high memory/core requests, account limits or dependencies. Read the Slurm reason before changing the configuration.

RUNNING#

The job is executing. A temporary lack of new files does not necessarily indicate a stall.

COMPLETED#

The Slurm script finished successfully. Still check the Nextflow exit code, results, phyloseq object and reports.

FAILED#

Inspect the error log, Slurm outputs, .nextflow.log, the report and the run history.

OUT_OF_MEMORY#

Memory was exceeded. Identify whether the issue concerns global memory, a specific process, LotuS3, report generation or NextITS before increasing a value.

TIMEOUT#

The maximum duration was reached. Choose a more suitable partition, reduce complexity or request a higher limit.

CANCELLED#

The job was cancelled manually, by an administrator, by a rule or by a dependency.

Unknown state or missing job#

A job no longer shown by squeue may still have a final state in sacct. BarCodeR queries both when possible.

33. Execution log#

33.1. Local operations#

Contains BarCodeR actions: selection, validation, connection, directory creation, transfer, preparation, launch and file detection.

33.2. Monitoring#

Contains the Job ID, Slurm status, detected progress, new outputs, run completion and phyloseq presence.

33.3. Standard output and standard error#

They are not the two main tabs of the current log, but remain accessible in historical details, run files, error previews and downloads.

33.4. .nextflow.log#

This file details processes, commands, errors, resumes, work files and validation. It is a primary diagnostic source.

34. Produced results#

Depending on the route, results may be organised in:

  • Steps/files: preparatory files and published inputs;
  • Steps/demultiplexing_files: demultiplexing and metrics;
  • Steps/filters: orientation, quality, length, coding and orphan files;
  • Steps/lotus3: LotuS3 outputs;
  • Steps/nextITS: NextITS outputs;
  • Steps/lotus3_taxo: taxonomy associated with NextITS;
  • Steps/phyloseq: generation or storage of the NextITS phyloseq object;
  • Steps/tax_db: cleaned database and extracted taxonomy;
  • OMB_logs: summaries, reports, timeline, trace, graph, versions and parameters;
  • final_table/idmabio_outputs: IDMABIO tables, alignments and report.

The exact structure depends on the route and options.

35. Importing a phyloseq object#

BarCodeR searches for .rds, .rda or .RData files that may contain a phyloseq object. A suggestive filename does not guarantee a valid object.

During import, the application temporarily downloads the file, opens it, searches for phyloseq objects, checks compatibility, offers a choice when needed and adds the selected object.

A unique name is built from the run, file and possibly object name. Run parameters may be attached to preserve provenance.

A phyloseq object may be detected after a failed run. It may be partial or have been created before the failing step. Review logs and content before use.

36. Actions after submission#

36.1. Relaunch with adjustments#

Keeps files and parameters, allows edits and prepares a new submission. The previous run is not cancelled.

36.2. New analysis — start from scratch#

Resets files, context, analysis parameters and the timeline. Keeps the connection and several cluster settings. The submitted job continues and remains in history.

36.3. Do not relaunch#

Closes the panel without cancelling or changing monitoring. It can be reopened later.

37. Analysis history#

Scanning searches for runs under the configured root directory. Results depend on the path, permissions, metadata, files and Slurm availability.

History may show Run ID, directory, Job ID, state, dates, duration, FASTQ and sample counts, size, memory, CPU, phyloseq presence and cleanup status.

37.1. Details and resume monitoring#

Details show parameters, paths, exit codes, Slurm information, files and errors. Resuming monitoring reconnects the interface to the run without relaunching computation.

37.2. Browsing files#

Supports search, opening groups, previewing the last 200 lines of text files, downloading and importing a phyloseq object.

37.3. Cancelling a job#

Uses Slurm to cancel the main job and identifiable child jobs. The directory and files already produced remain present.

37.4. Cleaning a run#

Deletes intermediate files while normally preserving results/ and meta/. This irreversible action frees space but removes resume cache and diagnostic material.

37.5. Deleting a run#

Deletes the entire remote directory, including results, metadata, logs, intermediate files and phyloseq objects. Save required files first.

39. Final checklist#

Context#

  • Correct technology, marker and route.
  • Consistent database type and file.

Design#

  • Six required columns.
  • Unique, safe identifiers.
  • FASTQ files correctly referenced.
  • Correct barcodes and primers.
  • Consistent primer pairs.

Parameters#

  • MiniBar enabled only when needed.
  • Error tolerances justified.
  • Orientation compatible.
  • Appropriate length and non-empty field when enabled.
  • Suitable quality threshold.
  • Relevant coding filter and genetic code.
  • Correct amplicon type and group.
  • Clustering and taxonomic modes documented.

NextITS#

  • Correct region, ITSx group and chimera database.
  • Homogeneous primers.

Cluster#

  • Green connection.
  • Accessible root.
  • Correct partition.
  • Memory with unit and realistic core count.
  • Valid modules and sufficient space.

Traceability#

  • Informative run name.
  • Design preview checked.
  • Generated configuration checked.
  • Parameters stored with the project.

40. Interpretation and reproducibility principles#

Results depend simultaneously on raw files, demultiplexing, primers, filters, clustering method, database, taxonomic algorithm and thresholds. Runs using different parameters should not be compared without accounting for these differences.

To ensure reproducibility:

  • keep the design file;
  • keep the database or its version;
  • keep run parameters;
  • keep Nextflow reports;
  • document every change from initial values;
  • retain software versions;
  • retain metrics from every step;
  • do not interpret only the final phyloseq object.
