OpenMetaBar — पद्धति संबंधी मार्गदर्शिकाएँ

1. सामान्य परिचय#

OpenMetaBar टैब FASTQ फ़ाइलों से पूर्ण मेटाबारकोडिंग डेटा-प्रसंस्करण पाइपलाइन शुरू करने और उसकी निगरानी करने देता है।

विश्लेषण सीधे Shiny एप्लिकेशन के भीतर नहीं चलता। BarCodeR तैयारी, सबमिशन और मॉनिटरिंग इंटरफ़ेस के रूप में काम करता है:

  1. उपयोगकर्ता विश्लेषण का जैविक और तकनीकी संदर्भ चुनता है;
  2. FASTQ फ़ाइलें, प्रयोगात्मक design file और reference database चुने जाते हैं;
  3. BarCodeR फ़ाइलों की जाँच करता है और उनके transfer की तैयारी करता है;
  4. उपयोगकर्ता cluster resources और pipeline parameters निर्धारित करता है;
  5. BarCodeR run के लिए अलग directory बनाता है;
  6. एप्लिकेशन में शामिल OpenMetaBar pipeline cluster पर कॉपी होता है;
  7. आवश्यक Singularity images की जाँच या स्थापना होती है;
  8. Slurm job submit होता है;
  9. एप्लिकेशन execution की निगरानी करता है और बने हुए files पहचानता है;
  10. अंत में phyloseq object को BarCodeR में जोड़ा जा सकता है।

OpenMetaBar कई technologies और analysis routes का समर्थन करता है:

  • Oxford Nanopore Technologies (ONT);
  • PacBio;
  • Illumina;
  • LotuS3;
  • NextITS;
  • IDMABIO report route।

2. OpenMetaBar क्या करता है और क्या नहीं करता#

2.1. OpenMetaBar द्वारा स्वचालित कार्य#

OpenMetaBar निम्न कार्य स्वचालित करता है:

  • working directory की तैयारी;
  • files की प्रारम्भिक validation;
  • local files का transfer;
  • design file में FASTQ paths को दोबारा लिखना;
  • Nextflow configuration बनाना;
  • Slurm resources तैयार करना;
  • pipeline deployment;
  • Singularity images का प्रबंधन;
  • job submission;
  • Slurm status monitoring;
  • results की पहचान;
  • phyloseq object import।

2.2. उपयोगकर्ता की जिम्मेदारी#

एप्लिकेशन स्वतः यह निर्धारित नहीं कर सकता कि:

  • चुना गया marker वास्तव में प्रयोग किए गए primers से मेल खाता है या नहीं;
  • दर्ज की गई expected length जैविक रूप से उपयुक्त है या नहीं;
  • reference database marker और अध्ययन किए गए organisms के लिए उपयुक्त है या नहीं;
  • quality thresholds sequencing technology के अनुसार उचित हैं या नहीं;
  • coding-sequence filter उपयोगी है या नहीं;
  • clustering या denoising method अध्ययन के उद्देश्य के अनुकूल है या नहीं;
  • taxonomic parameters पर्याप्त विश्वसनीय identification देते हैं या नहीं;
  • माँगे गए Slurm resources डेटा की मात्रा के लिए पर्याप्त हैं या नहीं।

महत्वपूर्ण सिद्धान्त — एप्लिकेशन का default value सार्वभौमिक recommendation नहीं है।

3. कार्यप्रवाह का अवलोकन#

अनुशंसित क्रम:

  1. Cluster connection जाँचें या स्थापित करें।
  2. Analysis context निर्धारित करें।
  3. Context validate करें।
  4. FASTQ, design file और reference database चुनें।
  5. आवश्यक होने पर design file बनाएँ या सुधारें।
  6. Files validate करें और transfer तैयार करें।
  7. Run और Slurm resources configure करें।
  8. General configuration validate करें।
  9. चुने गए route के विशेष parameters configure करें।
  10. Optional previews जाँचें।
  11. Analysis launch करें।
  12. Steps और execution logs की निगरानी करें।
  13. Results की जाँच करें।
  14. Phyloseq को BarCodeR में import करें।
  15. History से run manage करें।

Context validation cluster connection के बिना किया जा सकता है। Remote files browse करने, files transfer करने, remote directory जाँचने, Slurm partitions पहचानने, containers तैयार करने, run submit और monitor करने तथा पुराने runs देखने के लिए connection आवश्यक है।

4. Analysis route चुनना#

Technology + marker + engine का संयोजन तय करता है कि कौन-सा sub-pipeline चलेगा।

4.1. उपलब्ध routes#

Technology Marker उपलब्ध engine मुख्य route
ONT COI LotuS3 Standard ONT
ONT 16S LotuS3 Standard ONT
ONT 18S LotuS3 Standard ONT
ONT COI-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 16S-idmabio LotuS3 + IDMABIO ONT IDMABIO
ONT 18S-idmabio LotuS3 + IDMABIO ONT IDMABIO
PacBio 16S LotuS3 PacBio 16S
PacBio ITS LotuS3 या NextITS PacBio ITS
PacBio LSU LotuS3 या NextITS PacBio LSU
Illumina 16S LotuS3 Illumina
Illumina ITS LotuS3 Illumina
Illumina LSU LotuS3 Illumina

-idmabio variants केवल तब दिखाई देते हैं जब एप्लिकेशन compatible biglogin cluster connection पहचानता है।

4.2. Route के प्रभाव#

Context तय करता है:

  • MiniBar उपलब्ध होगा या नहीं;
  • NextITS engine इस्तेमाल किया जा सकता है या नहीं;
  • कौन-से parameters दिखाई देंगे;
  • कौन-सी Singularity images अनिवार्य हैं;
  • कौन-से pipeline steps चलेंगे;
  • कौन-से outputs बन सकते हैं।

Validation के बाद technology, marker या engine बदलने पर context अमान्य हो जाता है और संबंधित steps फिर से जाँचने पड़ते हैं।

5. Cluster से connection#

5.1. Connection window खोलना#

टैब के ऊपर स्थित button status दिखाता है:

  • Cluster connected नहीं है: कोई active SSH connection नहीं;
  • Connection active है, जाँच बाकी है: SSH खुला है, लेकिन कुछ prerequisites पुष्ट नहीं हुए;
  • Cluster connected है: connection और मुख्य आवश्यक commands पहचाने गए हैं।

Button पर क्लिक करने से connection window खुलती है।

5.2. आवश्यक जानकारी#

Server address, SSH port, username और आवश्यकता होने पर password दर्ज करें। यदि SSH key authentication पहले से configured और कार्यरत है तो password खाली छोड़ा जा सकता है।

5.3. की जाने वाली जाँचें#

Connection के बाद BarCodeR Bash, find, tar, sbatch, squeue, sacct, scancel, sinfo, Rscript, उपलब्ध Slurm partitions तथा time, memory और CPU limits की जाँच करता है।

इसलिए SSH connection खुला होने पर भी cluster OpenMetaBar चलाने के लिए तैयार न माना जा सकता है।

5.4. biglogin cluster#

समर्थित infrastructure में connection सीधे या, direct connection उपलब्ध न होने पर, bigm9 relay से हो सकता है। यह प्रक्रिया एप्लिकेशन स्वतः संभालता है।

5.5. Run के दौरान disconnect होना#

एप्लिकेशन से disconnect होने पर Slurm job cancel नहीं होता। Submit होने के बाद computation cluster पर चलता रहता है। उसी cluster से दोबारा जुड़ने, compatible root directory और उचित permissions होने पर run history से पुनः पाया जा सकता है।

6. Analysis context निर्धारित करना#

पहला configuration card pipeline route निर्धारित करता है।

6.1. Sequencing technology#

Oxford Nanopore Technologies

ONT चुनने पर COI, 16S और 18S markers, संभव IDMABIO variants, MiniBar demultiplexing और ONT + LotuS3 route उपलब्ध होते हैं।

PacBio

PacBio चुनने पर 16S, ITS और LSU दिखाई देते हैं। ITS/LSU के लिए LotuS3 या NextITS चुना जा सकता है, MiniBar छिपा रहता है और PacBio-specific route चलता है।

Illumina

Illumina चुनने पर 16S, ITS और LSU दिखाई देते हैं, LotuS3 उपयोग होता है, MiniBar छिपता है और design file के अनुसार single-end या paired-end files समर्थित होते हैं।

6.2. Marker या target#

Marker route चुनने, database type सुझाने, NextITS region सुझाने, IDMABIO variants पहचानने और visible parameters अनुकूलित करने के लिए उपयोग होता है। यह design file के primers की वास्तविक specificity validate नहीं करता।

Marker सुझाया database type
COI BOLD
16S SILVA
18S PR2
ITS UNITE
LSU SILVA

यह suggestion केवल declared database type बदलता है; कोई नया FASTA file स्वतः चयनित नहीं होता।

6.3. Reference database type#

उपलब्ध विकल्प BOLD, SILVA, PR2, UNITE, NCBI nt और custom हैं। Declared type मुख्यतः pipeline को FASTA headers पढ़ने और taxonomy mapping बनाने की विधि बताता है।

Declared type और चुना गया FASTA अलग जानकारी हैं और दोनों का संगत होना आवश्यक है। Personal FASTA को BOLD घोषित करने से वह BOLD database नहीं बनता।

6.4. Analysis engine#

Selector केवल PacBio + ITS और PacBio + LSU पर दिखाई देता है। विकल्प LotuS3 और NextITS हैं। अन्य contexts में selector छिपा रहता है और route पर प्रभाव नहीं डालता।

6.5. Context validation#

Context validate करें पर क्लिक करने के बाद file selection खुलता है। बाद में technology, marker या engine बदलने पर यह step फिर lock हो जाता है।

7. Run files चुनना#

Context validation के बाद Run files चुनें button उपलब्ध होता है। FASTQ files, design file और reference database आवश्यक हैं। NextITS के लिए chimera database भी चाहिए।

7.1. FASTQ files चुनना#

Local source

Local FASTQ एप्लिकेशन के file browser से चुने जाते हैं। वे सामान्य web upload के रूप में नहीं जाते; BarCodeR वास्तविक path उपयोग करता है और फिर cluster पर transfer करता है।

इसलिए सामान्य Shiny upload limit लागू नहीं होती, लेकिन transfer पूरा होने तक files accessible रहने चाहिए।

Cluster source

FASTQ cluster पर पहले से मौजूद हो सकते हैं। Path दर्ज करके या remote browser से चुने जा सकते हैं। Active SSH connection आवश्यक है।

एक या अनेक FASTQ

एप्लिकेशन अनेक files स्वीकार करता है और उन्हें अलग रखता है; स्वतः concatenate नहीं करता। Basename सुरक्षित रहता है, इसलिए अलग directories में समान filename collision पैदा करता है।

समस्या वाला उदाहरण:

/run1/sample.fastq.gz
/run2/sample.fastq.gz

अपेक्षित extensions: .fastq, .fastq.gz, .fq, .fq.gz।

पहले से demultiplexed FASTQ

यदि प्रत्येक file एक sample है, ONT में MiniBar बंद करें, design में प्रति row एक sample रखें और सही FASTQ जोड़ें।

Demultiplex न किए गए FASTQ

यदि एक file में barcode द्वारा पहचाने जाने वाले कई samples हैं, MiniBar चालू करें और प्रत्येक sample के barcodes तथा primers दर्ज करें। कई design rows एक ही FASTQ की ओर संकेत कर सकती हैं।

7.2. Design file चुनना#

Design local, remote या integrated editor में बनाया/बदला जा सकता है। TSV और CSV समर्थित हैं।

Pipeline द्वारा आवश्यक columns

Column भूमिका
Sample_ID Unique sample identifier
fastq_path एक या अनेक FASTQ का path
barcodeF Forward barcode
barcodeR Reverse barcode
primerF Forward primer
primerR Reverse primer

Barcodes उपयोग न होने पर भी columns मौजूद होने चाहिए। Pipeline की अपेक्षा के अनुसार खाली cell की जगह स्पष्ट NA उपयोग करना उपयुक्त हो सकता है।

ध्यान दें — Integrated editor दो-column table को editable मान सकता है, लेकिन पूर्ण pipeline validation को छह exact columns चाहिए। Editor में “consistent” design भी launch पर reject हो सकता है।

Sample identifiers

Identifiers भरे हुए, unique और preferably A-Z, a-z, 0-9, ., -, _ तक सीमित हों।

Automatic correction accents transliterate करता है, invalid characters बदलता है, शुरुआत/अंत के separators हटाता है और duplicates में suffix जोड़ता है। Case सुरक्षित रहता है।

Path column

दूसरे column को path column के रूप में पहचाना जाना चाहिए। Supported names में path, fastq_path, filepath, file_path, input_dir, directory, dir, folder शामिल हैं। अस्पष्टता से बचने के लिए fastq_path उपयोग करें।

Launch से पहले column fastq_path नाम से लिखा जाता है और remote run directory के paths डाले जाते हैं।

Paired-end files

Illumina pair के लिए fastq_path में comma-separated files हो सकती हैं:

sample_R1.fastq.gz,sample_R2.fastq.gz

दोनों files चुनी हुई हों और filenames exact match करें।

Design और FASTQ matching

हर referenced file किसी selected filename से match होनी चाहिए। Extension, case, suffix या typing error समस्या पैदा कर सकता है।

Single FASTQ case

यदि सभी rows एक raw file की ओर संकेत करती हैं, एप्लिकेशन paths को rewrite कर सकता है ताकि सभी samples वही remote FASTQ उपयोग करें, विशेषतः MiniBar से पहले।

7.3. Design file में primers#

primerF और primerR orientation के लिए उपयोग होते हैं। इन्हें 5′→3′ दिशा में valid IUPAC nucleotide characters और बिना spaces के दर्ज करें। Degenerate bases समर्थित हैं।

Orientation enabled होने पर प्रत्येक FASTQ के लिए unique primer pair अपेक्षित है। Pair न मिलना, एक FASTQ के लिए कई अलग pairs या invalid character error पैदा करते हैं।

7.4. Design file में barcodes#

MiniBar barcodeF और barcodeR उपयोग करता है। बहुत समान barcodes और अधिक error tolerance गलत sample assignment का जोखिम बढ़ाते हैं।

7.5. Reference database चुनना#

Database local या remote compatible FASTA (.fa, .fna, .fasta, .fas, संभवतः gzip compressed) हो सकता है।

यह cleaned FASTA, headers से taxonomy table और taxonomic assignment बनाने में उपयोग होता है।

Marker compatibility, सही alphabet, unique identifiers, usable taxonomy headers, declared type consistency और cluster readability जाँचें।

8. Design editor का उपयोग#

8.1. Cells बदलना#

Cells सीधे बदले जा सकते हैं। हर change के बाद minimum structure, path column, sample identifiers और FASTQ matching फिर जाँचे जाते हैं।

8.2. Rows जोड़ना या हटाना#

एक row जोड़ी और कई rows हटाई जा सकती हैं। पूरी तरह खाली rows save पर ignore होती हैं, लेकिन warning देती हैं।

8.3. Column जोड़ना, rename करना या हटाना#

तीनों operations समर्थित हैं। कम-से-कम दो columns रहें। पूर्ण design में Sample_ID, fastq_path, barcodeF, barcodeR, primerF, primerR हों।

8.4. Sample names सुधारना#

Correction button characters साफ करता है, empty identifiers रोकता है और names unique बनाता है। Changes जाँचें, क्योंकि यही names results और phyloseq में आएँगे।

8.5. FASTQ से design बनाना#

केवल MiniBar disabled होने पर उपलब्ध। एप्लिकेशन प्रारम्भ में SampleID और path बनाता है।

यह पूर्ण design नहीं है। Columns को Sample_ID, fastq_path rename करें, बाकी चार columns जोड़ें और values भरें।

8.6. Design save करना#

Structural error होने पर save blocked रहता है। चयन temporary local file design_edite.tsv से बदलता है। Full pipeline validation launch पर होती है।

9. Files validate और prepare करना#

Validate और transfer के लिए active connection चाहिए। यह selections, file existence, FASTQ शुरुआत, design की कुछ समस्याएँ, sample names और remote disk space जाँचता है। Local files staging area में भेजता है और remote files के paths रखता है।

Disk-space check preventive है और कुछ systems पर approximate हो सकता है। पूरा होने पर button Files ready दिखाता है।

10. Run और cluster configuration#

10.1. Run root directory#

हर run के लिए unique subdirectory बनती है। User को create, write, execute, read और cleanup permissions चाहिए। Embedded pipeline run directory में copy होता है और cleanup logic के अनुसार हटता है।

10.2. Slurm partition#

sinfo उपलब्ध होने पर detected partitions दिखते हैं। Partition resources, maximum duration, priority और account restrictions प्रभावित करता है। Visible partition उपयोग के लिए authorised हो, यह आवश्यक नहीं।

10.3. LotuS3 memory#

Memory में unit होनी चाहिए, जैसे 16G, 70G, 120G। केवल 70 न दें; Slurm इसे लगभग 70 MB समझ सकता है।

कम memory OUT_OF_MEMORY दे सकती है; बहुत अधिक memory queue time बढ़ा सकती है।

10.4. LotuS3 cores#

Core count Slurm CPUs, LotuS3 threads और कुछ child-process resources निर्धारित करता है। अधिक cores समान अनुपात में speed नहीं देते और scheduling कठिन कर सकते हैं।

10.5. Container module#

Singularity या Singularity-CE देने वाले module से exact match होना चाहिए, जैसे singularity-ce/4.1.0।

10.6. Nextflow module#

Nextflow version, जैसे nextflow/25.10.4। Missing या incompatible module launch रोकता है।

10.7. Run name#

Directory, Slurm job और history पहचानने में सहायक। एप्लिकेशन date, session identifier और random suffix जोड़ता है। बहुत लंबे नाम, special characters और sensitive information से बचें।

10.8. Intermediate files रखना#

Debug option success के बाद work/ रखता है। यह commands और diagnosis के लिए उपयोगी लेकिन बहुत बड़ा हो सकता है। Failure के बाद intermediates पहले से सुरक्षित रहते हैं। बाद में history से साफ किया जा सकता है।

11. Initial values समझना#

एप्लिकेशन की प्रारम्भिक settings मुख्यतः ONT + COI के लिए हैं: orientation enabled, length filter enabled, expected length 658, minimum quality 20, coding filter enabled और translation table 5।

ये values 16S, 18S, ITS या LSU के लिए स्वतः उपयुक्त नहीं हैं। Coding filter, length, genetic code, amplicon type और taxonomic group पुनः जाँचें।

कुछ parameters पहली बार बदलने पर “optimised initial value” warning दिखाते हैं। इसका अर्थ केवल controlled initial value है, universal optimum नहीं।

12. MiniBar demultiplexing — ONT routes#

12.1. MiniBar enable या disable#

एक FASTQ में कई barcode-labelled samples और पूर्ण design information होने पर enable करें। MiniBar sample-wise FASTQ और demultiplexed/retained read metrics बनाता है। Unknown या ambiguous reads assigned samples के रूप में publish नहीं होते।

Files पहले से sample-wise हों या upstream demultiplexing हो चुका हो तो disable करें।

12.2. Identification method — M#

Methods 1, 2 और 3 -M के साथ सीधे MiniBar को भेजे जाते हैं और internal assignment strategy बदलते हैं।

एप्लिकेशन algorithmic differences नहीं बताता। Validated method बनाए रखें, comparable batches के बीच बिना कारण न बदलें और change के बाद metrics जाँचें।

12.3. Maximum barcode errors — e#

Low value specificity बढ़ाता है लेकिन noisy reads खो सकता है। High value altered barcodes recover करता है लेकिन similar barcodes confuse कर सकता है। 0 exact match है।

12.4. Maximum primer errors — E#

Higher tolerance noisy reads recover करती है लेकिन non-specific matches बढ़ा सकती है। Lower tolerance अधिक specific है लेकिन valid reads हट सकते हैं।

12.5. MiniBar parameter — l#

Interface इसे search window कहता है, जबकि pipeline schema इसे minimum read length बताता है। Value सीधे -l में जाता है।

इस inconsistency के कारण validated value के बिना field खाली रखें, arbitrary interpretation न करें और change से पहले/बाद metrics compare करें।

13. Amplicon orientation#

13.1. Single-end reads#

Pipeline primers खोजता है, दोनों orientations पहचानता है, sequences को primerF → primerR दिशा में रखता है, primers हटाता है और internal region रखता है। Complete primer pair के बिना reads हटते हैं।

13.2. Non-degenerate और degenerate primers#

केवल A/C/G/T primers पर वर्तमान step एक mismatch तक स्वीकार करता है। Degenerate IUPAC codes पर degenerate-pattern matching होता है, अतिरिक्त mismatch mode नहीं।

13.3. Paired-end reads#

FASTQ pair के लिए orientation skip होती है और SKIPPED_PAIRED_END मिलता है। इसलिए यह process reads reorient या primers remove नहीं करता।

13.4. NextITS route#

NextITS ITS regions और primers के लिए स्वयं processing करता है; general orientation step उसी रूप में लागू नहीं होता।

13.5. Orientation कब disable करें#

यदि primers पहले हट चुके हैं, सभी sequences एक दिशा में हैं या upstream processing इसकी गारंटी देता है, तो disable करें।

14. Filters का क्रम#

Filters cumulative हैं: quality, length, coding। प्रत्येक filter पिछले filter से बचे reads पर चलता है। कई मध्यम strict settings मिलकर अत्यधिक strict हो सकती हैं। Reads शून्य होने पर pipeline रुकता है।

15. Length filter#

15.1. Activation और input#

Disabled होने पर entered length ignore होती है। Enabled होने पर comma-separated integers दें, जैसे 480 या 450,550।

15.2. वास्तविक interval#

Pipeline प्रत्येक expected length के आसपास ±100 nucleotides margin रखता है।

658 के लिए 558–758; 500,800 के लिए 400–600 और 700–900।

15.3. Length कैसे चुनें#

Primers के बीच region, filter के समय primers मौजूद हैं या नहीं, biological variation, technology और target groups पर निर्भर करता है। 658 initial COI context का value है, इसे automatically न रखें।

15.4. Empty या invalid field#

Current implementation empty/unparsable value को silently 658 से बदल सकती है। Filter enabled होने पर field खाली न रखें जब तक वास्तव में 658 न चाहिए।

15.5. Paired-end reads#

R1 और R2 पर अलग-अलग filter होता है, फिर resynchronisation। यह merged amplicon नहीं बल्कि प्रत्येक read की length देखता है। 250-nt reads के लिए 658 दोनों mates हटाएगा।

15.6. Resynchronisation#

Filtering के बाद identifiers से pairs फिर match होते हैं। Retained mate के बिना reads orphan बनते हैं। केवल complete pairs आगे बढ़ते हैं।

16. Quality filter#

Minimum threshold SeqKit को भेजा जाता है। High value अधिक stringent और कम reads; low value अधिक depth तथा अधिक noise रखता है। Technology, sequencing generation और upstream preprocessing के अनुसार चुनें।

Paired-end में R1/R2 पर अलग filter और फिर resynchronisation होती है। केवल एक mate हटने पर दूसरा orphan बनता है।

17. Coding-sequence filter#

चुने genetic code के अनुसार कम-से-कम एक reading frame बिना internal stop codon translate होने पर read रखा जाता है। Current orientation के तीन frames test होते हैं।

यह COI जैसे coding region के लिए उपयुक्त है और सामान्यतः 16S, 18S, ITS, LSU के लिए नहीं। Orientation disabled होने पर reverse coding sequences reject हो सकती हैं।

Value Genetic code
1 Standard code
2 Vertebrate mitochondrial
5 Invertebrate mitochondrial
11 Bacterial, archaeal and plastid

Table 5 invertebrate mitochondrial COI के लिए initial suggestion है, लेकिन हर COI या अन्य marker के लिए नहीं।

Paired-end में दोनों reads पर अलग filter होता है। यदि हर read coding region का केवल हिस्सा cover करता है तो सावधानी से interpret करें।

18. LotuS3 — clustering और assignment#

PacBio ITS/LSU में NextITS main engine होने के अलावा सभी routes पर LotuS3 parameters दिखते हैं।

18.1. Platform#

Options: auto, PacBio, 454, miSeq, hiSeq। Auto में BarCodeR value force नहीं करता। Explicit value internal strategies बदलता है और technology/preprocessing से संगत होना चाहिए।

18.2. Amplicon type#

Options: SSU, LSU, ITS, ITS1, ITS2, custom। वास्तविक amplified region के अनुरूप होना चाहिए, केवल project marker name के नहीं।

18.3. Taxonomic group#

Options: auto, bacteria, fungi, eukarya। Explicit value कुछ taxonomic decisions प्रभावित करता है। Heterogeneous context या unvalidated case में auto बेहतर है।

18.4. Clustering या denoising#

Options: UPARSE, Swarm, CD-HIT, UNOISE, DADA2, VSEARCH। ये समान biological units नहीं देते। Unit count, abundance, rare-sequence sensitivity और error treatment बदल सकते हैं। अलग methods के outputs सीधे equivalent नहीं हैं।

18.5. Taxonomic assignment tool#

Options: RDP classifier, BLAST, Lambda, UTAX, SINTAX, VSEARCH, USEARCH। Algorithm, speed, sensitivity, distant sequences और scores प्रभावित होते हैं।

18.6. RDP confidence threshold#

केवल RDP_classifier पर दिखता है। High value अधिक stringent और अधिक unassigned; low value अधिक assignments लेकिन कम robustness दे सकता है।

18.7. Unclassified units रखना#

0 हटाता है; 1 रखता है। Unknown diversity और later reassignment के लिए उपयोगी, लेकिन downstream analyses में स्पष्ट handling चाहिए।

18.8. Taxonomic exclusion#

Entered pattern taxa हटाता है। बहुत broad expression अनेक assignments हटा सकता है। Database vocabulary जाँचें, pattern test करें और exclusion document करें।

19. Demultiplexed reads save करना#

Mode प्रभाव
0 विशेष demultiplexed FASTQ publish न करें
1 सभी unfiltered demultiplexed reads रखें
2 Demultiplexed reads रखकर pipeline रोकें
3 Quality-filtered demultiplexed reads रखें

Phyloseq या complete analysis अपेक्षित हो तो mode 2 उपयोग न करें। Modes 1 और 3 disk usage बढ़ाते हैं लेकिन checking/reuse आसान करते हैं।

20. LCA और advanced assignment#

20.1. Assignment mode#

Counter-intuitive convention: 0 LCA enable करता है; 1 best BLAST hit उपयोग करता है।

LCA compatible hits का common ancestor खोजता है और अक्सर conservative होता है। Best hit अधिक precise दिख सकता है, लेकिन गलत references, imbalanced database या nearly equal hits से प्रभावित हो सकता है।

20.2. Minimum coverage#

0–1 value। High coverage अधिकांश sequence alignment माँगता है; low coverage partial matches स्वीकारता है। Short fragment पर high identity पूरे amplicon पर high identity के बराबर नहीं।

20.3. Rank-specific identity thresholds#

Initial example 97,95,93,91,88,78। Identity और taxonomic rank का universal mapping नहीं है। Marker, group, database और region length पर निर्भर करता है। Change taxonomic depth बदलता है।

20.4. Agreement fraction#

High value मजबूत consensus माँगता है और higher rank दे सकता है। Low value कम agreement पर decision देता है और conflicts बढ़ा सकता है।

20.5. Phylogenetic tree#

0: कोई tree नहीं; 1: FastTree; 2: IQ-TREE 2। Tree computation बढ़ाता है और usable alignment चाहिए। IQ-TREE 2 अधिक costly होता है।

20.6. Maximum read overlap#

मुख्यतः paired short reads के लिए। Read length, amplicon length और expected R1/R2 overlap से संगत होना चाहिए।

21. Standard ONT route#

ONT + COI, 16S या 18S।

Settings के अनुसार design validation, optional MiniBar, sample FASTQ recovery, orientation, filters, mapping preparation, LotuS3, assignment और reports होते हैं।

COI के लिए वास्तविक length, primers, target organism, genetic code, coding filter और database जाँचें। 16S/18S के लिए coding filter सामान्यतः बंद करें, 658 बदलें/बंद करें और सही amplicon type, group तथा database चुनें।

22. ONT IDMABIO route#

COI-idmabio, 16S-idmabio, 18S-idmabio। Compatible cluster पहचानने पर ही उपलब्ध। Route marker suffix से trigger होता है, engine selector से नहीं।

ONT steps के साथ ZOTU-hit validation, IDMABIO outputs, MAFFT alignments और Word report जोड़ता है।

22.1. Gene type#

Options: auto, coding, non-coding। Auto में COI coding और अन्य non-coding माने जाते हैं। Explicit value inference override करता है।

22.2. Retained BLAST hits#

Maximum hits निर्धारित करता है। High value अधिक information, file size और संभव processing time; low value useful secondary hits छिपा सकता है।

22.3. Alignments per sample#

Outputs में कितने alignments दिखेंगे। यह total retained hits से अलग है।

22.4. Report language#

French या English; generated Word report नियंत्रित करता है।

23. PacBio + LotuS3 route#

PacBio + 16S, या PacBio + ITS/LSU with LotuS3। MiniBar उपयोग नहीं होता।

Orientation enabled हो तो reads में primers मौजूद हों; expected length वास्तविक reads से मेल खाए; 16S/ITS/LSU में coding filter बंद हो; quality threshold corrected PacBio reads के अनुसार हो।

फिर platform, amplicon type, group, clustering method, taxonomic tool और LCA options configure करें।

24. PacBio + NextITS route#

केवल PacBio + ITS या LSU with NextITS।

Validation, enabled prefilters, NextITS, ITSx, correction/clustering, chimera detection, dedicated LotuS3 assignment, phyloseq generation और summaries चलते हैं।

24.1. ITS region#

Options: ITS1, ITS2, LSU, SSU, ALL। LSU marker LSU सुझाता है और ITS प्रारम्भ में ITS1, लेकिन यह वास्तविक amplified region validate नहीं करता।

24.2. ITSx group#

Options: all, fungi, tracheophyta, metazoa। बहुत restrictive group heterogeneous environmental samples के लिए अनुपयुक्त हो सकता है।

24.3. NextITS clustering#

Options: UNOISE, VSEARCH, Swarm। Clustering/denoising बदलता है। Different methods के outputs सीधे identical नहीं हैं।

24.4. UNOISE option#

अलग UNOISE denoising step enable करता है; general method selector से अलग है।

24.5. Homopolymer correction#

Homopolymer polishing enable करता है। Sequences बदलती हैं; comparable runs में setting consistent रखें।

24.6. Chimera database#

Local या remote हो सकती है; मौजूद, readable, expected format और सही group/region की हो। Initial path development environment का हो सकता है; database explicitly चुनें।

24.7. Primer consistency#

Route consistent primer pair अपेक्षित करता है। एक run में अलग pairs error या unexpected behaviour दे सकते हैं।

25. Illumina + LotuS3 route#

Illumina + 16S, ITS या LSU।

Design single-end के लिए एक file या paired-end के लिए comma-separated दो files देता है। Paired data पर orientation skip होती है, इसलिए primers इस step से नहीं हटते।

Quality, length और coding filters R1/R2 पर अलग चलते हैं और फिर resynchronisation होती है। Length filter merged amplicon पर नहीं चलता। Mate हटने पर दूसरा read orphan बनता है।

16S/ITS/LSU में coding filter सामान्यतः बंद करें, 658 बदलें/बंद करें और amplicon type, group, database जाँचें।

26. Design और destination preview#

Previews optional और प्रारम्भ में disabled हैं। Preview run name, example Run ID, design, future directory, FASTQ destinations, rewritten design path, configuration, technology, marker, database type/path, partition, resources और Singularity cache दिखाता है।

Design का initial content दिखता है; paths launch पर ही rewrite होते हैं।

27. Generated configuration preview#

Form से बना Nextflow overlay दिखाता है: paths, enabled parameters, numerical values, LotuS3, IDMABIO, NextITS और Singularity directory।

File में अन्य routes के parameters भी हो सकते हैं; इसका अर्थ उपयोग होना नहीं। nf-schema emitted values validate करता है, इसलिए invalid value process शुरू होने से पहले run रोक सकता है।

32. Slurm states समझना#

PENDING#

Job resources का इंतज़ार कर रहा है। कारण: unavailable resources, priority, busy partition, high memory/core requests, account limits या dependencies। Configuration बदलने से पहले Slurm reason पढ़ें।

RUNNING#

Job चल रहा है। कुछ समय तक नई files न आना हमेशा blockage नहीं।

COMPLETED#

Slurm script सफलतापूर्वक समाप्त। फिर भी Nextflow exit code, results, phyloseq और reports जाँचें।

FAILED#

Error log, Slurm outputs, .nextflow.log, report और history देखें।

OUT_OF_MEMORY#

Memory limit पार हुई। Value बढ़ाने से पहले global memory, specific process, LotuS3, report या NextITS पहचानें।

TIMEOUT#

Maximum duration पहुँची। अधिक उपयुक्त partition चुनें, complexity घटाएँ या बड़ा limit माँगें।

CANCELLED#

Manual, administrator, rule या dependency से cancel।

Unknown या missing job#

squeue में न दिखने वाला job sacct में final state रख सकता है। BarCodeR संभव होने पर दोनों query करता है।

33. Execution log#

33.1. Local operations#

Selection, validation, connection, directory creation, transfer, preparation, launch और file detection।

33.2. Monitoring#

Job ID, Slurm status, detected progress, new outputs, completion और phyloseq presence।

33.3. Standard output और standard error#

Current log के मुख्य tabs नहीं, लेकिन history details, run files, error preview और downloads में उपलब्ध हैं।

33.4. .nextflow.log#

Processes, commands, errors, resume, work files और validation का विस्तृत log; मुख्य diagnostic source।

34. Produced results#

Route के अनुसार:

  • Steps/files: preparatory files और published inputs;
  • Steps/demultiplexing_files: demultiplexing और metrics;
  • Steps/filters: orientation, quality, length, coding और orphans;
  • Steps/lotus3: LotuS3 outputs;
  • Steps/nextITS: NextITS outputs;
  • Steps/lotus3_taxo: NextITS-associated taxonomy;
  • Steps/phyloseq: NextITS phyloseq generation/storage;
  • Steps/tax_db: cleaned database और extracted taxonomy;
  • OMB_logs: summaries, reports, timeline, trace, graph, versions, parameters;
  • final_table/idmabio_outputs: IDMABIO tables, alignments और report।

Exact structure route और options पर निर्भर करती है।

35. Phyloseq object import#

BarCodeR .rds, .rda या .RData files खोजता है जिनमें phyloseq हो सकता है। Filename valid object की गारंटी नहीं।

Import के दौरान file अस्थायी रूप से download, open, phyloseq objects खोजे, compatibility जाँची, आवश्यकता पर choice दी और selected object जोड़ा जाता है।

Run, file और object से unique name बनता है। Provenance के लिए run parameters attach हो सकते हैं।

Failed run में भी phyloseq मिल सकता है। वह partial या failure से पहले बना हो सकता है। उपयोग से पहले logs और content जाँचें।

36. Submission के बाद actions#

36.1. Adjust करके relaunch#

Files और parameters रखता है, modifications की अनुमति देता है और नया submission तैयार करता है। Previous run cancel नहीं होता।

36.2. New analysis — शुरुआत से#

Files, context, analysis parameters और timeline reset करता है; connection और कुछ cluster settings रखता है। Submitted job चलता रहता है और history में रहता है।

36.3. Relaunch न करें#

Panel बंद करता है, monitoring या job नहीं बदलता। बाद में दोबारा खोला जा सकता है।

37. Analysis history#

Scan configured root directory के नीचे runs खोजता है। Results path, permissions, metadata, files और Slurm availability पर निर्भर हैं।

History Run ID, directory, Job ID, state, dates, duration, FASTQ/sample counts, size, memory, CPU, phyloseq और cleanup status दिखा सकती है।

37.1. Details और monitoring resume#

Parameters, paths, exit codes, Slurm information, files और errors दिखते हैं। Resume monitoring interface को run से जोड़ता है, computation फिर शुरू नहीं करता।

37.2. Files browse करना#

Search, groups open करना, text files की अंतिम 200 lines preview, download और phyloseq import।

37.3. Job cancel करना#

Slurm से main job और identifiable child jobs cancel होते हैं। Directory और पहले बने files रहते हैं।

37.4. Run cleanup#

Intermediate files हटाता है और सामान्यतः results/, meta/ रखता है। Irreversible है: space बचता है, लेकिन resume cache और diagnostic material हटते हैं।

37.5. Run delete करना#

पूरा remote directory—results, metadata, logs, intermediates, phyloseq—हटता है। पहले आवश्यक files सुरक्षित करें।

39. Final checklist#

Context#

  • सही technology, marker और route।
  • Database type और file संगत।

Design#

  • छह required columns।
  • Unique और safe identifiers।
  • FASTQ सही referenced।
  • सही barcodes और primers।
  • Consistent primer pairs।

Parameters#

  • MiniBar केवल आवश्यकता पर।
  • Error tolerances justified।
  • Orientation compatible।
  • Length उचित और enabled होने पर field non-empty।
  • Quality threshold उचित।
  • Coding filter और genetic code relevant।
  • Amplicon type और group सही।
  • Clustering और taxonomic modes documented।

NextITS#

  • सही region, ITSx group और chimera database।
  • Homogeneous primers।

Cluster#

  • Green connection।
  • Accessible root।
  • सही partition।
  • Unit सहित memory और realistic cores।
  • Valid modules और पर्याप्त space।

Traceability#

  • स्पष्ट run name।
  • Design preview checked।
  • Generated configuration checked।
  • Parameters project के साथ सुरक्षित।

40. Interpretation और reproducibility#

Results raw files, demultiplexing, primers, filters, clustering method, database, taxonomic algorithm और thresholds सभी पर निर्भर करते हैं। अलग parameters वाले runs की तुलना इन differences को ध्यान में रखे बिना नहीं करनी चाहिए।

Reproducibility के लिए:

  • design file रखें;
  • database या version रखें;
  • run parameters रखें;
  • Nextflow reports रखें;
  • initial values से हर change document करें;
  • software versions रखें;
  • हर step की metrics रखें;
  • केवल final phyloseq object पर interpretation आधारित न करें।
